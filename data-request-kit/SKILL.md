# data-request-kit（数分需求单）

数分同学开工需要五样东西：**对象**（哪个页面/模块/功能）、**口径**（算什么、不算什么）、**周期与拆分**（多久、按什么拆）、**指标**（要哪些数）、**用途**（这数据拿去做什么决定）。表单的十三个字段就是围绕这五样设计的；一张让数分不用回头追问的单子，就是把这五样写清楚。

## 三条铁律

1. **先草稿表 → 用户确认 → 才提交。** 提交是往近万条的共享需求池写一行，会进数分的排期视图；提错了只能改状态为「取消」，抹不掉。所以 `dr.py submit` 默认 dry-run，`--yes` 只在用户看过草稿表之后加。
2. **每个字段标依据：原话 / 先例 / 推断。** 推断项必须进确认轮。聊天里一句短话不是决定——「这个纳入不了」既可能是结论也可能是反问，问一句比猜一次便宜得多。
3. **不猜范围。** 对比对象是谁、含不含归因、是不是补单、"下周五"是哪天、对接人是谁——不清楚就问，但一轮问完（一次 AskUserQuestion 装 2–4 个问题），别挤牙膏。

## 分工

- **你**：读上下文、判断需求类型、写文案、决定问什么、汇报。
- **`scripts/dr.py`**：表单契约、先例、校验、提交、回查、探选项。所有对表单和需求池的读写都走脚本；脚本没有的能力（读文档、下载图片、搜群）用 lark-cli 原生命令，见 `references/context-gathering.md`。脚本零依赖（python3 标准库 + lark-cli），不接触任何凭据。

| 你要干什么 | 命令 |
|---|---|
| 预检 lark-cli，拿当前用户（默认发起人） | `python3 scripts/dr.py whoami` |
| 看线上表单字段/选项，报漂移 | `python3 scripts/dr.py contract` |
| 姓名 → open_id / 单聊 id | `python3 scripts/dr.py user <姓名>` |
| 压平打印和某人的单聊 | `python3 scripts/dr.py chat <姓名或id> --since YYYY-MM-DD` |
| 发起人历史单 + 同主题历史单 | `python3 scripts/dr.py precedent [--keyword X] [--full]` |
| 校验 spec、打印草稿表 | `python3 scripts/dr.py validate spec.json` |
| dry-run / 真提交 + 回查 | `python3 scripts/dr.py submit spec.json [--yes]` |
| 探被锁字段的合法选项 | `python3 scripts/dr.py probe 交付形态 看板 表格 文档` |

## 流程

**0. 预检。** `whoami`（顺带确认 lark-cli 能跑；报找不到就 `npm i -g @larksuite/cli@latest`）、`contract`（线上字段为准，脚本快照可能过期；线上新增了必填字段就用 spec 的 `extra` 补）。开场顺带跑 `python3 ../prd-authoring-kit/scripts/register.py demand-mine --daily`（路径相对本 skill 目录；每天首次一次）：输出 SKIP、0 行、没有 lark-cli、或主 kit 未安装（文件不存在）都静默跳过；有行就按 `../prd-authoring-kit/references/13-workflow.md §七` 出建议表，🔴 写回逐行确认。

**1. 收集需求。** 来源通常是三种之一：和某人的聊天（`chat` 命令；看到截图先按打印出的命令下载、用 Read 看图再往下读——截图往往就是"对象"本身）、一份文档或周会纪要（`lark-cli docs +fetch --doc <url> --doc-format markdown --as user`）、用户口述。从材料里抽七要素：对象、指标、周期/拆分、对比对象、明确排除的东西、期限、已有产出。抽不出来的项进确认轮，不要脑补。细节见 `references/context-gathering.md`。

**2. 找先例。** `precedent` 看发起人过去怎么填（业务线、对接人、优先级——这是候选默认值，不是答案）；`precedent --keyword` 看同主题历史单，尤其是被取消/暂停的：说明上次口径没对齐或需求重复，这次要在描述里避开同一个坑，或者先跟数分对口径再提。

**3. 定类型。** 按"数分实际要做什么"选，不按"谁来要的"选：

| 数分实际要做的事 | 需求类型 |
|---|---|
| 跑一次数、给一份数字/表 | 取数需求 Ad-hoc Data Request |
| 数据 + 归因/结论/建议 | 分析需求 Analysis Request |
| 持续看、要搭 BI 看板 | 看板需求 Dashboard Request |
| 改底表 / 改口径 / 接新数据源（如新功能纳入归因口径） | 数分表变更 |
| 活动发奖名单 / 发奖核算 | 发奖需求 Award Request（选项名末尾带空格，脚本会自动匹配） |

三种容易判错的情形：
- **补单**（数据已经交付、事后补流程）：类型按实际做了的事定；描述里写明"已产出，链接"；预期交付时间贴近今天而不是按常规周期往后推——否则单子会一直显示「未启动」、delay 指标也会失真。
- **对比需求**（A 和 B 横向比）：每个对象都要显式在范围内，且两者的数据可得性可能不同（一个在归因口径里、一个不在）。要么拆成两单，要么在描述里写明各自能出什么。
- **"纳入不了 / 没有埋点"类事实**：写进背景的只能是已确认的事实和它的直接后果（"因此本单不含归因交易额"），不要顺手推出"所以要改底表"这种下一步——那是另一张单子，而且未必成立。

**4. 起草。** 按 `references/writing-guide.md` 写标题、背景、目标、描述四段，落成 `spec.json`（格式见 `assets/spec.example.json`）放在 scratchpad。`evidence` 里给每个关键字段写依据。

**5. 校验。** `validate spec.json`。它做本地规则 + 线上契约双重校验，并打出"草稿表"——那张表就是给用户看的东西，直接贴进回复。

**6. 确认轮。** 一次 AskUserQuestion 问完所有"推断"项和范围问题，每个问题给 2–4 个具体选项 + 你的推荐。典型要问的：范围/对比对象、需求类型、预期交付日期（把星期几写出来）、对接人是否沿用先例。用户的回答可能推翻某个问题的前提（比如你问"底表变更的交付日期"、他却回答"其实纳入不了"）——这时相关字段要重算，不要机械照填。

**7. 提交。** `submit spec.json --yes`。脚本会回查需求池并打印 record_id 与状态。报错先看脚本给的提示行（`references/form-contract.md` 有完整对照），不要盲目重试。表单网页需要登录，浏览器路径走不通，也不要让用户去登录。

**8. 汇报。** 模板：

```
已提交，记录 rec…，状态「未启动」，预期交付 YYYY/MM/DD（周X）。
<草稿表最终版>
留意：① 埋点/口径的不确定点 ② 历史同主题单的教训 ③ 本单明确不含的东西
要我通知 <需求方/数分> 吗？（发消息需要你点头）
```

「未启动」是需求池的初始状态，不是没提交成功。通知别人一律先问。若结论是"不用提单"（已有单、范围内没有需求），同样把依据（record_id、原话时间）写清楚。

## 不猜清单

碰到这些，问，别定：对比对象具体指哪个模块；"表现数据"要到哪一层（曝光/点击/转化/归因）；周期与拆分维度；补单还是新单；"下周五"这类相对日期（今天是周几决定它是哪天）；对接人（先例只是候选）；同一段聊天里同时有两件事时，哪句话在说哪件事。

反过来也成立：**材料里没有的，结论就是"没有"**。用户问"最近三天有没有让我补单"，答案可以是"没有，唯一一次是 8/27，且已提 rec…"——不要为了交出一张单子而把范围外的旧事翻出来当新需求；顺手发现的悬而未决事项另列一节，标明"这是新单，不是补单"。

## 投入度：查到什么程度就够

七要素里能从材料直接填的填上，填不上的进确认轮——不要为了填上它去通读整份 PRD 或口径表。读文档只在两种情况：对象叫什么不确定（要拿原名）、类型存疑（怀疑已有底表/看板/同对象单）。一张单子的调查以十几条命令为参考量；超过了通常说明该问用户，而不是继续挖。先例查到"同对象已有单"就是最有价值的一条发现，把它做成确认轮第一题，比再读三份文档更有用。

## 常见坑（详见 references/form-contract.md）

- 提交 payload 的 key 必须是**表单问题标题全称**，字段 id 和表字段名都会报 unknown field name；脚本已按 id→标题映射，你只管写 spec。
- 单选传纯字符串（与 record-create 规范相反）；日期 yyyy-MM-dd HH:mm:ss；回读显示 08:00 是时区解释问题，日期没错。
- 「需求目标分类」「交付形态」被 Base 字段权限锁住：API 读不到选项、校验也看不到，但按名字能写。已知选项在脚本里；提交报 option not found 就 `probe`。
- 表单问题标题 ≠ 需求池表字段名（「需求要达成的目标 Goals」vs「需求目标」），回查和先例用表字段名，脚本已处理。
- lark-cli 的 PATH 软链偶尔会断（指向不存在的 scripts/run.js），脚本自动回退到包内 `bin/lark-cli`。
