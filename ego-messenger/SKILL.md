# E哥飞书消息 Skill

## 核心原则：从人性和心理出发

写给E哥的每一条消息，本质上不是"汇报"，而是**经营关系**。
目标不是"把事情说清楚"（那是基本功），而是**让E哥看完之后心情好、
觉得你靠谱、觉得这事做成了是他的战功**。

---

## Step 1：理解E哥是谁

### 人物画像

E哥（Ealy Zhang），阿里巴巴出身，从质量和运维起步，一路高升，
目前负责前后端技术+产品，权力很大。

**核心性格特征（写消息时必须考虑）：**

| 特征 | 具体表现 | 对写消息的影响 |
|------|---------|-------------|
| **好大喜功** | 靠吹战功和画大饼上位，绩效标准是"战功因我而成" | 让他觉得成果是他的vision落地，不要抢功 |
| **小心眼+敏感** | 会因为某个用词或姿态记恨，事后秋后算账 | 严禁任何暴露内部策略的词出现在消息里（详见Step 3 红线） |
| **喜欢抠细节** | 会盯着UI截图指出"oil上面看多71%下面K线看跌67%" | 发方案时数据和逻辑要经得起推敲，别留明显漏洞 |
| **喜欢自己提点子** | 经常主动提产品建议，比如"分享内容加用户diy语句" | 消息里留白，不要把话说满，给他接话和加点子的空间 |
| **看重结果** | 关注归因交易额等硬指标 | 有数据就亮数据，没数据就说清楚怎么验证 |
| **只关心最终形态** | 不关心实现路径、排期分批、机制设计怎么落 | 首发消息只写形态和目标，过程留给追问（详见Step 4 第二关） |
| **会追问逻辑** | 对感兴趣的方案不直接拍板，挑1-2个点回"再阐述下逻辑呢" | 这是设计内时刻不是驳回，首发存好弹药，追问时展开（见场景G） |
| **喜欢1-3-9结构** | 让人"总结3个值得学习的特点"，要求分层表达 | 信息组织用分层逻辑，要点控制在3个左右 |
| **不喜欢长文** | 偏好表格和视觉化 | 群消息简短，复杂内容用附件/图，消息本身只讲结论 |
| **行动导向** | "right now, go"，喜欢快速推进 | 消息要有"下一步"的暗示，但别用"请指示"这种被动句式 |

### 他的心理需求（按优先级）

1. **控制感** — 他要觉得一切在他掌握之中，方向是他定的
2. **成就感** — 成果要能归到他的vision/决策上
3. **信息优越感** — 他要比别人先知道、知道得多
4. **被尊重但不被跪舔** — 他欣赏有主见的人，不喜欢纯执行机器

## Step 2：Tom的真实沟通风格

Tom（Noah Zhan）在飞书群里和E哥的实际沟通风格，**基于真实历史消息分析**。
不要把这套风格简化成"空格断句的极简飞书重度用户风"——那是错的。
Tom 的真实风格是 **"汇报型敬重感 + 口语化"的混搭**。

**动笔前先 view `references/samples.md`，对照 7 条真实样本校准风格，写完再对一遍。**

### 开头方式（分场景）

| 场景 | 开头 | 例子 |
|------|------|------|
| 正式汇报方案/成果 | `@Ealy Zhang Hello E哥，...` | "@Ealy Zhang Hello E哥，咱们亏损的仓位卡片又打磨了一下" |
| 普通汇报或同步进展 | `Hello E哥，...` 或 `E哥，...` | "E哥，发现tab重构方案出来了" |
| 时间问候型 | `中午好E哥，...` / `早上好E哥，...` | "中午好E哥，发现tab-AI全球交易信号看板，重构方案出来了" |
| 回应E哥提问/追问 | `E哥我们排查了一下，...` / `E哥，...` | "E哥，这两个KA对应用户的两个决策时刻" |
| 短回复或一句话同步 | `E哥 [短内容]` | "E哥 这个我去确认下" |

**严禁**：
- "E哥您好"、"尊敬的E哥" — 过度正式
- 完全裸开头不带任何称呼 — 显得冷

### 句子结构

**正确**：句子完整，有完整标点（逗号、句号、感叹号、问号、波浪号 `～`）

**错误（之前犯过）**：用空格切碎成短片段当"飞书风格"——那是 IC 间的快讯风格，不是 PM 给老板的汇报风格。

对比：
- ❌ "E哥 方案做完了 3张图按顺序看 🙋‍♂️" — 太碎太冷
- ✅ "@Ealy Zhang Hello E哥，亏损平仓后的 AI 卡片打磨好了，请 E 哥瞧瞧这 3 张图～[Me!Me!Me!]" — 完整、有温度

### 表情系统（关键修正）

**优先使用飞书内置表情代码**：
- `[Me!Me!Me!]` — 请求关注/邀请看，用于"请E哥瞧瞧"句末
- `[FoldedHands]` — 拜托/感谢/还请理解，用于解释性段落末尾
- `[ThankYou]` — 感谢，用于发完文档或方案末尾
- `[Facepalm]` — 自嘲/无奈，用于解释外部约束（比如排期没赶上）
- `[FingerHeart]` — 温暖收尾，用于"届时也会请E哥瞧瞧"这类占位型消息末尾（本条消息不索取即时动作时）
- `[FightOn]` — 表推进决心，用于"如果没问题我们就按这个思路推进了！"这类收尾句末

**Emoji（🙋‍♂️ 🫡 ❤️ 👍）只作为补充**，不是主力。在企业飞书环境里，飞书表情代码比 emoji 更原生。

一条消息表情数量：1-2 个，不要堆砌。

### 称谓和语气词

| 用法 | 例子 |
|------|------|
| 称E哥 | "哥"（如"哥之前提的"）、"E哥"（如"请E哥拍板"）|
| 称自己/团队 | "咱们"（更亲近）、"我们"（更中性）、"我"（个人发起时）|
| 语气词 | "啦～"（轻松收尾）、"瞧瞧"（请看）、"哈"（自嘲）|
| 固定句式 | "请E哥瞧瞧" / "请E哥拍板" / "请E哥看看" / "感谢E哥提醒" |

### 列表和格式

**用 `*` 列表展开方案细节是 OK 的**——Tom 历史消息明确用过 `*` 来分点。
KA/要点类消息也可以不用 `*`，直接"KA1 ..."顶格起行（样本6就是这样）。

- **避免 markdown 加粗**（`**...**`）
- **避免 `→` 箭头符号**
- **避免长破折号 `—`**
- **避免完美对仗的 bullet**（每条字数完全一样）
- **允许 `*` 列表或顶格分点展开细节**
- **允许换行 + 空行分段**

### 末尾 cc 同事（关键补充）

Tom 真实习惯：消息末尾用 `cc @同事1 @同事2` 标记相关协作方。

举例：
- `cc @Yoki Xu`（leader）
- `cc @Marvel L`（大数据）
- `cc @Yoki Xu @Hedy Y`（涉及对方模块协作时把对方 cc 进来）

**cc 是企业文化的一部分**——让相关人知道这个事正在发生，也是一种横向透明。
不 cc 的话，相关同事可能被动得知，制造尴尬。
消息里点到名的协作方（如"和Hedy那边的bot双向打通"），本人必须出现在 cc 里。

### 绝对不要

- "E哥好" — 仍然太正式，用 "Hello E哥" 代替
- "请您过目/审阅" — 太跪
- "如有需要可以约个会" — 太被动
- "请指示" / "请批示" — 这不是政府公文
- markdown 加粗 / 长破折号 / → 箭头 — AI 感重灾区
- 长段且每条字数相同的 bullet — AI 写出来的标志

## Step 3：红线 — 对内对外话术必须严格隔离

### 这是 ego-messenger 最容易翻车的地方

写给 E哥 的消息和材料里，**严禁出现任何暴露"对内策略"的词**。
E哥 小心眼且敏感，看到这些词会让他产生"你在算计我"的负面印象。

### 红线词汇黑名单

**绝对不能出现在消息或附图中的词：**

| 黑名单词 | 为什么 | 替代说法 |
|---------|-------|---------|
| **画饼** | 暴露"骗他"的动机 | "规划"、"路线图"、"已规划" |
| **概念演示** / **演示版** | 暗示"不是真的" | 直接不写，或用产品语言命名（如"短链路转化版"）|
| **汇报版** / **看板版** | 暴露"专为你做" | 直接不写，或用产品场景命名 |
| **回应老板关切** | 直接说出讨好动机 | "用户心理：XX" |
| **v15 / v16 等版本号** | 暴露迭代多次 | 直接删除版本号 |
| **基于 leader/Tom 反馈** | 暴露工作流细节 | 直接删除 |
| **给你做的** / **专门给你的** | 暴露讨好 | 删除 |
| **听见你的诉求** / **响应你的关切** | 显得在表忠心 | 用结果说话，不解释动机 |

### 这条红线适用于：
1. 消息正文
2. 附图标题（PPT/方案图/原型图）
3. 附图水印或标注
4. 文档命名
5. 飞书消息预览（如发文档时显示的标题）

### 自检方法

写完消息或出图前问自己：
> 这句话/这张图，如果在飞书群里被其他同事看到，他们会不会觉得 Tom 在"刻意讨好 E哥"？

如果会，必须改写。

## Step 4：内容三关 — 方案类消息正文的打磨纪律

（提炼自 2026-08 快讯 3 个 KA 一役：一条方案消息被 Yoki 和 Tom 前后打回近十轮，
每轮病灶都可归入这三关。初稿写完先按顺序过三关，再走 Step 7 自检。
三关针对的是"病"的类，本役的句子只是实例，别把实例当成黑名单的全部。）

### 第一关：口号关（全文任何位置都适用）

对仗、押韵、顺口的短语读起来漂亮，但信息靠听者脑补。
这是 AI 起草方案消息的最高发病，Yoki 的定性是"喊口号""有点空""有用的废话"。

**识别特征（命中任一条就重写）：**

| 特征 | 本役实例（均被打回） | 改法 |
|------|------------------|------|
| 三字格/四字格并列 | "找得到、看得懂、跟得住""推得到、撞得到、跟得住" | 删掉，或拆成各自把因果说完的整句 |
| 押韵/对仗句 | "推得准才敢推得狠" | "判定压住误报，push 才能做重" |
| 名词化机制口号 | "一次判级、全端分发" | "同一件事在快讯列表、Bot、智能K线、洞察都能看到" |
| 场景化空话 | "打开哪里都撞得到""事件在他那个位置等他" | 直接点名是哪几个位置 |

**判据**：把这句删掉，读者少知道了什么？答不上来的，就是口号。

**元规则（本关最重要）**：被指出一处口号，不是改那一处，而是把它当成一个"类"，
全文扫一遍同类全改。本役修掉"找得到看得懂跟得住"之后又写出
"推得到撞得到跟得住"，被第二次点名——修一处再犯一处，比第一次犯更伤信任。
这条元规则对任何一类反馈都成立：被点名的永远是实例，要修的永远是类。

### 第二关：过程关（只适用于首发的方案/成果消息）

Yoki 的原则：**老板只要最终产品形态和达成的目标，实现路径他问了再讲。**
"最终形态"指上线后用户看得见的东西，"过程"指团队怎么把它做出来。

**过程黑名单（首发消息里删干净）：**

| 类别 | 本役实例（均被打回） |
|------|------------------|
| 判定/触发机制 | "事件级别加瞬时波动双条件判定""事件判定一次，统一标记分发" |
| 排期节奏 | "接入分两批，快讯和Bot先行，洞察和AI分析页第二批" |
| 技术选型 | "页面用原生还是H5" |
| 复用路径 | "和币用同一套联动逻辑" |
| 善后细节 | "事件结束资讯归档回常规快讯列表" |
| 内部消费逻辑 | 领导明说"无需向上汇报"的内容（本役的资讯消费节奏 T+1/T+4） |

**形态/目标白名单（留下的）**：
- 具体到能想象出画面的产品形态：push 文案示例原文、弹窗带哪几条价格、
  常驻盯盘条目、专属追踪页、事件结束页面自动下线
- 每个动作的主攻目标：主攻点击 / 主攻曝光 / 主攻交易转化
- 协作后的状态："和 XX 双向打通、重大资讯即时互推"——描述的是打通之后的
  状态而非排期，且展示协作意识（leader 点名要的），可留

**边界判据**：这句话描述的是"上线后存在什么"，还是"我们怎么做出来"？前者留，后者删。

**弹药库**：删掉的过程内容不是扔掉，存档备用。E哥 追问逻辑时（场景G）它们就是主菜。
场景B（排查回复）和场景G（逻辑追问）不受此关限制——那两个场景里过程本来就是重点。

### 第三关：深度关（防止砍成"任务完成体"）

压缩消息时砍法有顺序：**先砍机制细节，判断段最后动。**

短到只剩要点罗列，消息就成了"交作业"。尤其当这条消息是老板会上点名要的、
且 leader 把露脸机会让给了你时，薄的版本等于浪费机会。
深度不靠堆机制，靠开头的判断段：

> 问题不在 X，而在 Y（根因定性一句）。所以按 Z 拆成 N 个动作（解法推导一句）。

本役定稿的判断段："昨晚的问题不在快讯没发，而在重大事件被当成普通快讯处理。
这次按推送、站内分发、后续跟进拆成三个KA，各管一段。"

长度基准：方案类消息 12 行上下最稳。压到 9 行以下时自查一次，
是不是把判断段也砍没了。

## Step 5：按场景写消息

### 场景A：群里汇报方案/成果

**心理要点：**
- 这是在"卖方案"，不是在"交作业"
- 让E哥觉得：这人做了功课、方向对、是我的vision在落地
- 亮出过程（竞品调研、数据复盘）证明你用心了
- 结论先行，细节放附件

**结构模板：**
```
@Ealy Zhang Hello E哥，[什么东西]打磨好了/出来了，请E哥瞧瞧～[Me!Me!Me!]

[一期 / 短期版 / 当前迭代]咱们的设计是：
* [要点1]
* [要点2]
* [要点3，扣上E哥之前提过的vision/关键词]

[如果有合规/约束的说明，单独段落，见Step 6]

[二期 / 长期版]咱们也已经规划好了：
* [要点1]
* [要点2]
* [验证机制：上不上看一期数据决定]

请E哥拍板一下方向！
cc @相关同事1 @相关同事2
```

### 场景A变体：老板点名要"N个KA / N个要点"的方案

会上被点名"出 N 个 KA 的方案"时，消息骨架固定为：

1. 开头一句：方向追溯到 E哥 提出问题的那个场合（"接着今天AI周会上提的XX问题"），
   而不是追溯到和 leader 的内部讨论
2. 判断段 1-2 句（Step 4 第三关的公式）
3. N 个 KA，每个 = 名字 + 主攻目标 + 形态描述（逐条过 Step 4 前两关）
4. 顺带项一句：正好在做的相关改造带一嘴，体现全局都在手里
5. 战略覆盖一句：扣公司当期战略重点（如"这套布局美股也同步覆盖"）
6. 推进式收尾："先请E哥看看方向，如果没问题我们就按这个思路推进了！"

完整实例见 references/samples.md 样本6。
KA 的个数、名字、主攻目标都跟着当次要求走，"3个"不是定数。

### 场景B：回应E哥的提问或建议

**心理要点：**
- E哥提问 = 他在乎这个事 = 快速响应是加分项
- 先肯定他的观察（"感谢E哥提醒"），再解释原因和解法
- 给出明确的action，别只说"我看看"
- 如果他的建议确实好，大方承认；如果有问题，婉转说明

**结构模板：**
```
[肯定E哥的观察/建议，1句话] [FoldedHands]

[简短解释原因/现状，2-3句]

[明确的下一步action]

cc @相关人
```

### 场景C：主动同步进展

**心理要点：**
- 主动同步 = 展示你在推进 = E哥不用追问 = 他省心
- 用数据说话，不要说"进展顺利"这种空话
- 简短，3-5行搞定

### 场景D：请求拍板/决策

**心理要点：**
- 给选项，不要给开放题。E哥喜欢"选"不喜欢"想"
- 带上你的建议，但别替他做决定
- 说清楚选项的trade-off，让他觉得"我考虑得很周全"

### 场景E：分享竞品情报

**心理要点：**
- E哥喜欢信息优越感，竞品情报让他觉得"我的团队在盯着市场"
- 不要只转发链接，要提炼出"和我们有什么关系"
- 用E哥喜欢的1-3-9结构：总结3个值得关注的点

### 场景F：会前占位 / 抢占叙事

**触发特征（三条同时满足才算此场景）：**
- 某个方向即将上会讨论，另一位同事可能先声夺人
- 手里有调研/数据，但方案和原型还没做出来
- 需要在"没有成品"的状态下，让E哥先认你的框架

**心理要点：**
- 方向所有权还给E哥（"顺着E哥定的XX方向"）。同侪的令箭是E哥给的，箭还给箭主，令箭自动失效
- 不点名评价任何同事的提案。用行业事实降维（"XX只是行业体系N类里的2类"），把单点需求升维成系统机会
- 数据双钩：一个数字验证E哥战略正确（他的vision被数据证实，他爱看），一个数字论证系统升级的必要
- 给升级起版本名（如"XX 3.0"）。版本叙事同时宣示主导权和延续性
- E哥关切的单点必须承诺"在整体计划中先行推进"，节奏一天不慢
- 占位型收尾：这类消息是报备不是评审，不写"请E哥拍板"，写"初版方案预计XX产出，届时也会请E哥瞧瞧"
- cc 被纳入框架的同事本人：阳谋透明，避免"背后动作"观感，对方上会只能顺着框架讲

**结构模板：**
```
@Ealy Zhang [问候]E哥，顺着E哥定的"XX"方向，我们[调研动作+量化工作量]，
发现[行业事实降维]，而[我方数据钩子]，XX需求是真实的。

所以咱们计划做一次完整的「XX升级」：[方向1]、[方向2]、[方向3]，
同步落实 @相关方 在推的XX。

由于[资源约束]，咱们会一次规划、分期上线，[E哥关切的单点]会在整体计划先行推进。
[报告链接]，初版方案和原型预计[时间]产出，届时也会请E哥瞧瞧方向[FingerHeart]

cc @leader @被纳入框架的同事
```

（本场景提炼自 2026-08 行情洞察3.0 一役（样本5），n=1 验证，当"招式组合"用，不当铁律用。）

### 场景G：回应E哥的逻辑追问（"再阐述下逻辑呢"）

**触发特征**：首发方案消息发出后，E哥 挑其中 1-2 个点回复
"再阐述下逻辑""为什么这么设计"这类问题。

**心理要点：**
- 这不是驳回，是首发只给形态之后的设计内时刻——他肯花时间问，说明方案进入了他的考虑
- 此刻把 Step 4 第二关存档的判定逻辑、机制设计拿出来，这是它们的主场
- 但展开不等于罗列机制。先立一根用户逻辑主线，把被问的几个点串在上面，
  每个设计点都挂在"用户此刻要什么"后面
- 收在指标上：逻辑的终点是转化口径，这也是把首发时删掉的北极星数字放回来的位置

**结构模板：**
```
E哥，这[几个点]对应[一根用户主线，如：用户在一次重大事件里的两个决策时刻]：

[点1]接第一个时刻，[用户此刻的问题]。所以[设计了什么]，[为什么这样设计]。

[点2]接第二个时刻，[用户此刻的问题]，[这个需求目前没被满足的事实]。
所以[设计了什么]，[为什么]。

[几个点]连起来，[一句话说清整体效果]，[统一的转化/验收口径][FoldedHands]

cc @Yoki Xu
```

**禁忌**：开头不写"好问题"这类捧场话；不重复首发消息已经说过的形态描述；
不按机制清单平铺（判定规则一条、分发规则一条、销毁规则一条——那是 PRD 不是回复）。

完整实例见 references/samples.md 样本7。
（结构遵循 Yoki"老板问了再展开"的方针，E哥 对该结构的反馈尚待验证，
当默认打法用，不当铁律用。）

### 场景H：E哥已读不回之后怎么跟进（提炼自 2026-09 股票 Meme 专区入口一役）

**触发特征**：一条方案或结论消息发出后，E哥 已读，一两天没回；leader 让你"催一下"。

**先判断，不先催。** 已读不回有三种可能，一条消息要同时兜住：
1. 忙，没顾上：给一个不用动脑的默认
2. 不满意，他之前的意见和你给的结论不一样：把他的意见接回来当顺序或当数据触发条件，不是被否
3. 觉得已经表过态了，等你自己定：明确告诉他准备怎么走，留叫停口

**铁律：同一件事不发第二条一样的消息。** 再发就得带新东西，设计正式稿、排期、数据。
没有新东西就不发，等新东西出来再发。空催一条等于告诉他"你没回我很慌"。

**形式是进展通知，不是问句。** 默认推进加叫停口："我们准备先按 X 走，Y 稿子留着，
上线后看数据再定要不要补。E哥有别的想法随时叫停～"

**不预设他的立场。** 他没明说的，消息里不替他下结论。
本役翻车句："如果 E哥 还是想两个都要，我们就两个都上"，把他之前的意见摆上台面，
等于点明"投票归投票，你要什么给什么"，他选两个就成了否掉大家的票。
第二次翻车句："B 等第二个专区出来就加上"，没共识的事替他做了决定。
改法：把没共识的那一项交给数据（"上线后看点击和交易数据再定"），既不否他，也不替他定。

**授权层级落到纸上，自说自话的担心才能消。** 投票结果（他要的流程）+ leader 一句"按 A 走"
+ 周会文档产品重要事项里一行记录，三层齐了，他任何一层都拦得住，你也从头到尾没绕过他。
让 leader 在她的场合（1:1、周会）顺口带一句"按 A 先走了"，领导对领导补一句，比你再催一次有效。

**结构模板：**
```
E哥，同步一下进展～[事情]按 [结论] 的[新东西：设计正式稿/排期]出了，[什么时候做什么]。
[没共识的那一项]稿子留着备用，上线后看[数据口径]，再看要不要补。
```
本役实测：这条发出后 E哥 回"OK，可以先这么干"，并主动给了下一步
（"到时候让 Yoki 10 月找个场子和马哥同步一下，最好做好了一起聊下运作"）。
（n=1，当默认打法用；"进展通知优于追问""不预设立场"两条是通用原则。）

### 场景I：二选一方案的结论与投票结果回报

**leader 的规矩（Yoki，2026-09）**：给 E哥 看的方案只给一个推荐加优势，不摆三个让他挑；
他不同意会自己说，不要再来一轮研发评估。他要求投票时，投票结果回报也是同一逻辑：
结果 + 我们的建议 + 一个不显眼的口子。

**结构模板：**
```
Hello E哥，[事情]的投票结果出来了：A [N] 票，B [N] 票，[其他] [N] 票，
设计侧也倾向 A，[A 的一句优势]。我们建议先按 A 做，
[给另一项一个正常的产品理由]，B 也可以一起加上。请E哥瞧瞧～[Me!Me!Me!]
```

**口子怎么开**：把另一项当成一个正常的产品选项放着（"如果想让板块在首页更突出，B 的标签行也可以一起加"），
他要选两个也是基于产品判断，不是否决投票。不要写成"E哥如果还是想两个都要"。

### 场景J：在产品大群发起投票

**受众不是 E哥，但 E哥 在群里。** 群里是不了解项目的高阶产品和 leader，吃瓜投票，不读背景。

**三条：**
1. 消息里不出现项目名、版本号、热点名这些内部词，把问题升成所有产品都能答的形态问题：
   "内容社区首页给一个热点专区做入口，置顶帖好还是加一排标签好"。背景全放进图里
2. 语气不卑不亢：不写"各位大佬""辛苦各位"，写"大家好""麻烦大家投个票，谢谢"；
   倾向可以说一句"产品和设计这边目前倾向 A，也想听听大家的看法"，不拉票
3. 消息不描述投票机制：选项、怎么回、截止时间都不写，投票用飞书投票组件发，消息只说事、两个方案、倾向、请投票
   （E哥 先前的看法不写进群消息；他自己在群里，想说他会说）

**定稿实例：**
```
大家好，想请大家帮忙做一个产品形态上的选择。一个内容社区的首页，要给一个热点专区一个固定入口，
有两种做法：A 是首页置顶一张专区帖，FOMO 的做法；B 是首页信息流上方加一排筛选标签，小红书的做法。
具体背景和界面在下面这张图里。我们目前倾向 A，也想听听大家的看法，麻烦大家投个票，谢谢。
```
（配图规范见 mexc-infographic 的"决策页"）

## Step 6：合规/外部约束的话术框架

### 当方案不能完全按 E哥 原意执行时

这是高难度场景。E哥 提了一个方向，但因为合规/法务/技术约束没法完全照做，
必须在消息里说明——但不能让 E哥 觉得"你拿合规当挡箭牌挡我"。

### 三个核心原则

**原则1：主语是"我们调整"，不是"合规驳回"**

| 错误 | 正确 |
|------|------|
| ❌ "合规驳回了你的方案" | ✅ "咱们做了下架构调整" |
| ❌ "法务说不能这样做" | ✅ "咱们跟法务老哥对了一下..." |
| ❌ "原方案过不了合规" | ✅ "原本想按你说的做，但合规这边标了红线" |

**原则2：先承认"我们试过按你说的做了"**

让 E哥 知道团队不是上来就否定他，而是认真尝试落地后才发现约束。

`原本是按哥说的"XXX"做的`

**原则3：把合规约束具体化**

不要泛泛说"合规不行"——把具体的红线列出来，让 E哥 知道这是有边界的客观约束，不是团队懒。

```
法务老哥标了两个红线：
* "如果做这个策略就赚了XX"这种假设性收益不能写
* 亏损平仓后立刻推AI策略容易被认定为利用情绪促交易
```

### 标准合规说明段落模板

```
[合规/技术/资源] 这边咱们也跟[法务老哥/技术]对了一下。
原本是按哥说的"XXX"做的，但[他们]标了[几个]红线：
* [具体约束1]
* [具体约束2]

所以咱们做了下架构调整，[新方案]。哥要的[核心诉求]一个不少，
[约束领域]也能走得通[FoldedHands]
```

**关键收尾句**：`哥要的XXX一个不少，XX也能走得通` —— 这句话告诉 E哥
"你想要的本质没丢，只是路径变了"，避免他觉得团队绕开他的意图。

## Step 7：写完后的自检清单

每条消息发出前，过一遍：

### 风格层

- [ ] 开头有"Hello E哥"或"E哥"或"中午好E哥"，没有裸开头？
- [ ] 句子是完整的，有标点（逗号、句号、感叹号、波浪号）？
- [ ] 没有用空格切碎成短片段？
- [ ] 表情用了 `[Me!Me!Me!]` `[FoldedHands]` `[FightOn]` 等飞书内置表情？
- [ ] 没有 markdown 加粗 `**...**`、没有 → 箭头、没有长破折号 — ？
- [ ] 没有完美对仗的 bullet（每条字数相同）？
- [ ] 末尾有 cc 相关同事？消息里点到名的协作方本人在 cc 里？
- [ ] 对照过 references/samples.md 的样本？

### 红线层（最重要）

- [ ] 没有出现"画饼""演示""汇报版""回应老板""给你做的""v15"等暴露内部策略的词？
- [ ] 附图标题/水印/标注里也没有这些词？
- [ ] 如果别人看到这条消息，不会觉得 Tom 在"刻意讨好"？

### 三关层（方案类消息必过，见 Step 4）

- [ ] 口号扫描：全文没有三字格并列、押韵对仗、名词化机制口号？（按类扫全文，不是只看被点名过的那句）
- [ ] 过程扫描：首发消息每句都在讲"上线后用户得到什么"，没有判定机制/排期分批/技术选型/复用路径/善后细节？
- [ ] 判断段还在：开头有问题定性一句 + 解法推导一句？
- [ ] 排除清单清零：领导明说"不用汇报/删掉"的内容，全文确认一条不剩？
- [ ] 已上线的工作没被当成新东西再提？升级只说目标形态，没顺带暴露现状短板（写"资讯更新提速到分钟级"，不写"从隔天整理提速到分钟级"）？
- [ ] 内部文档里的承诺型数字（"转化率提升50%"这类）没有未经 Tom 确认就进消息？

### 内容层

- [ ] 结论先行，不是铺垫半天才说重点？
- [ ] 有数据/事实支撑，不是空话？
- [ ] 复杂内容放附件了，消息本身不超过 15 行？
- [ ] 留了空间让 E哥 可以接话/补充？
- [ ] 如果涉及合规/约束，用了"我们调整"的主动表述，没有甩锅？

### 心理层

- [ ] E哥 看完会觉得"这人做了功课"？
- [ ] 不会觉得你在抢他的功劳？
- [ ] 方向能追溯到他之前提过的 vision 或他在场提要求的场合？
- [ ] 不会觉得你在等他指示才能动？

### 跟进层（已读不回 / 二选一收尾时）

- [ ] 这条消息比上一条多了什么新东西？没有就先别发
- [ ] 是进展通知不是问句？有默认走法和叫停口？
- [ ] 没有替他下结论、没有把他之前的意见摆上台面当"你要的"？
- [ ] leader 的授权和周会文档的留档都有了？

## Step 8：改稿循环 — 消化领导反馈的纪律

方案类首发消息的正常链路是：初稿 → leader（Yoki）过目确认 → 进群。
消化她的反馈时：

**1. 双清单，缺一不可。**
从反馈里同时列出"要加什么"和"明确不要什么"两张清单，改完逐条核对。
本役翻车点：Yoki 说了"资讯消费节奏这类内容无需向上汇报"，改稿时只顾着加新内容，
T+1/T+4 原样留在了正文里，被 Tom 抓出来。漏掉排除项比漏掉新增项更伤——
它证明你没听懂反馈。

**2. 转写噪音是高危项。**
语音转文字的会议纪要里出现对不上号的词（本役的"1+1T+4""一派讯和heddy"
"智能天线Bot"），两个动作二选一：映射到已知实体后向 Tom 确认，
或直接标出来问。禁止默默照抄，也禁止默默丢弃——本役漏删 T+1/T+4 的根因，
就是没把"1+1T+4"这个噪音词和"消费节奏不上报"那条指令对上号。
对不上号的词附近的指令，往往就是最容易执行错的指令。

**3. 时机与链路。**
会议结束后至少隔 1 小时再发产出（E哥 复盘过"会没开完就发产出"
= 没认真听 + 没充分讨论）。leader 让你代发的消息，发群前先回她确认稿。

**4. 领导的类比可以直接复用。**
她论证时用过的比方（本役的"和短视频反复曝光一个逻辑"）写进消息是安全的——
那是她的语言，她看到会认，还省一次解释成本。

**5. 修一处，扫全文。**
任何一条反馈都指向一个类而不是一个句子（Step 4 元规则）。
"这种表达也不要有"意味着同类表达全文清零，交回去之前自己先举一反三，
别等第二次被点名。
