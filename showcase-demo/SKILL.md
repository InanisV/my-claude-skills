# Showcase Demo 生成器

把产品材料变成"会上一键放完、老板看得懂、讲得出底层"的可交互 HTML demo。
这套方法论从 MEXC 广场 demo 三轮迭代中提炼（v1 结构跑通 → v2 设计还原+自动播放 →
v3 双入口+二期画饼，获管理层认可），核心不是"写页面"，而是**把一次汇报
设计成一条可自动播放的故事线**。

## 0. 成品长什么样（北极星）

单文件 HTML，浏览器直接打开，左右分栏：

```
┌─────────────────┬──────────────────────────┐
│ ▶ 一键完整演示   │        演示视角徽章        │
│ ⏸暂停 ■停止 倍速 │   ┌────────────────┐     │
│                 │   │   iPhone 壳     │     │
│ 章节卡 × 6–8     │   │  像素级复刻的    │     │
│ （点击单章重放）  │   │  产品界面       │     │
│                 │   │  + 虚拟手指     │     │
│ 旁白字幕（讲稿）  │   │  自动点击/打字   │     │
│                 │   └────────────────┘     │
│ 事件日志（三色）  │                          │
│ 数据依据（口径）  │                          │
└─────────────────┴──────────────────────────┘
```

四件套与汇报标准的映射，写代码前先想清楚：

| 组件 | 对应汇报标准 | 本质 |
|---|---|---|
| 章节卡 + 旁白 | 左边功能逻辑、use case | 这是**讲稿骨架**，不是按钮 |
| 真机壳界面 | 右边交互变化、呈现形式 | 这是**设计稿的活化**，不是示意图 |
| 事件日志 | 底层怎么取用数据 | 接口/AI/审核/运营链路实时滚动 |
| 数据依据 foot | 口径锚点 | 老板追问时的证据出处 |

## 1. 输入盘点与开工确认

三类输入各有用途，缺哪类就向用户要哪类（说清楚要来干什么）：

- **PRD（前端 + 后台都要）**：剧本与口径之源。前端 PRD 出界面元素与交互规则；
  后台 PRD 出事件日志的数据链路（接口、审核流、AI/Agent 任务、幂等/快照等
  机制词）。后台链路往往藏着最能打动管理层的暗线（如"热点→Agent 生成→双审→
  进流"），主动挖。
- **UI 设计稿**：像素还原之源。优先级：**真机截图 > Figma 链接 > 无稿**。
  Figma MCP 的 View 席位调用限额很低，抓紧第一次调用拉"总览板"；.fig 源文件
  无法解析，直接请用户导出截图。没稿的页面按 PRD + 已有截图风格补，并明确
  告知用户哪些页面是补的。
- **对话结论 / 用研报告 / 竞品分析**：叙事与"画饼背书"之源。二期/愿景章的
  每一张概念卡都应该能在旁白里引用一条数据或结论（"用研 53 条提及"比
  "我们计划做"有力得多）。用户提到的对话记录若不在项目文档里，读不到就
  明说，基于可得材料先做，把假设标出来请用户核对。

材料读完后用 AskUserQuestion 确认四件事（受众明确时可合并少问）：
**① 受众与场合**（老板宣讲 / 团队评审 / 外部展示——决定详略与语言）；
**② 章节范围**（核心功能 + 亮点，6–8 章为宜，多了讲不完）；
**③ 亮点线**（AI / 增长 / 数据，哪条单独成章重点讲）；
**④ 要不要画饼章**（管理层宣讲通常要，标"概念示意"与交付范围区隔）。

## 2. 剧本设计（先写剧本，后写代码）

章节是一条故事线，不是功能清单。经典结构：

```
入口/定位 → 基础盘（核心浏览/消费） → 亮点线①（如 AI 供给）
→ 创作/生产闭环 → 互动闭环 → 亮点线②（如 AI 回应） → 增长闭环 → 二期画饼
```

每章 3–8 步。每一步是一个四元组 `{narr 旁白, log 日志, tap/do 动作, wait 时长}`：

- **旁白就是讲稿**：一步一个论点，加粗关键词（`<b>`），演示者照着念就能讲。
  写完通读一遍，不通顺的旁白 = 不成立的故事线。
- **日志讲机制**：接口带 method/路径/参数/耗时（`GET /square/feed?snapshot_id=…
  → 200 · 8 帖（86ms）`）；AI/算法、审核/运营用不同颜色区分（见 ui-kit）；
  真实机制词（request_id 幂等、快照分页、乐观更新回滚）比泛泛的"调用接口"
  可信十倍——全部从 PRD 里抄，不编造。
- **Demo 压缩要标注**：审核 24h 压成秒级、"每 15 条插 1 张"压成第 2 条后插入，
  都在旁白或页脚注明口径，防止被当成真实承诺。
- **画饼章纪律**：界面打"2.0 概念示意"角标 + 页脚声明"非本期交付范围"；
  每张概念卡的旁白带数据背书；饼可以大，但每一口都有出处。

时长标准：标准速 2–3.5 分钟，另配加速档（speed×0.55）。超了就砍步骤，
不要砍等待时间——旁白读不完的 demo 等于没有旁白。

## 3. 界面复刻（设计稿在手 = 像素级还原）

v1 最大的教训：**结构相似 ≠ 还原**。用户给了设计稿，就逐张对照着抠：

- 底色是纯黑 `#000` 还是深灰 `#0B0E11`；卡片分隔是 hairline 还是留白
- 图标语言：**一律内联 SVG，禁用 emoji 当图标**（emoji = 玩具感）；
  状态栏信号/wifi/电池也用 SVG 画
- 动作行的**顺序**（如 💬 评论在前还是 👍 点赞在前）、计数封顶规则（999+）
- 按钮形态（白底黑字胶囊 vs 描边）、页签形态（下划线 vs 胶囊）、
  cashtag/链接的品牌蓝、时间格式（相对 vs 绝对）
- 头像：无真实素材时用"径向渐变 + 首字母"，品牌号可以 SVG 画 logo——
  比 emoji 圆脸可信
- 键盘、弹层、海报这类"氛围组件"值得做：发布器里一块 CSS 键盘、分享面板里
  一张带二维码的海报，还原度感知提升远超成本

具体配方（tokens、图标库、手机壳、键盘、投票卡等）见 `references/ui-kit.md`，
起手先读它，不要从零写样式。完整可运行范例见
`references/example-mexc-square-v3.html`——结构、命名、体量都以它为基准。

## 4. 自动播放（展示型 demo 的硬要求）

给老板演示的 demo，默认**一键跑完**，现场不做手动操作（v2 的教训：手动交互
在会上是负担不是亮点）。引擎完整代码在 `references/engine.md`，直接搬：

- 大按钮 `▶ 一键完整演示（N 章 · 约 X 分钟）`；章节卡可单独重放（重放前
  重置本章状态，保证幂等）
- **虚拟手指**（ghost cursor）：移动 → 缩放脉冲 → 执行动作，让观众看见
  "谁在点哪里"；打字用逐字符 typewriter；下拉/滑动用位移动画模拟
- **空格 = 暂停/继续**：演示者讲到关键处停住细讲，这是最常用的控制，
  按钮和快捷键都要有
- 倍速档（标准 / 加速 ×0.55）；手动自由点击仍然保留（自动播放之外界面照常可点）
- 工程上最容易踩的坑（暂停丢步、计时器泄漏、重放不幂等）engine.md 里
  都有对应写法，别重新发明

## 5. 验证（交付前必须全程跑通）

用 Playwright 无头浏览器当"观众"完整看一遍，纪律：

1. console error + pageerror **零容忍**
2. 点加速档 → 点一键播放 → 每 5s 截图直到终章旁白出现（超时即 bug）
3. 关键状态定向截图（用 evaluate 直接构造状态）：各章节末态、弹层、空态
4. 把截图**用眼睛看**（拼图后人工核对）：对照设计稿查还原度，别只看"有没有报错"

验证脚本模板见 `references/engine.md` 末节，改路径和终章标记就能用。

## 6. 交付与版本纪律

- SendUserFile 交付（render 预览）；能持久化为桌面 artifact 就顺手做
  （通道断开则跳过，文件为准）
- 🔴 **交付那一轮记一行使用采集（正式一步，别跳）**：demo HTML **交付给用户的当轮立即执行**，
  按同级目录的 `../prd-authoring-kit/references/11-usage-telemetry.md` 执行（**它是采集的唯一真源**：
  命令文本、平台形态（Kiro/Claude 单行 + 结尾 echo；Codex 分步裸跑）、五条铁律、写入契约都在那儿，
  **本 skill 不复制命令**），**模式列填「demo」**，**需求名按该文件 `§需求名 = 跨技能统一去重键` 取**
  （会话里有该需求的飞书 PRD → 用 PRD 文件标题；其次 Jira 主卡 summary 去掉端前缀；再次用户口头的
  需求名——**同一需求的写 PRD / 建卡 / demo 必须落同一个名字**，否则按需求去重的统计失真）。
  🔴 **该文件不存在**（本机没装 prd-authoring-kit）→ **静默跳过**：不提示用户、不报错、不凭记忆拼命令。
  铁律照搬：尽力而为、失败静默、绝不打扰用户、只在 `lark-cli auth status` ok 时记、绝不为采集触发扫码、
  零敏感（只记 时间/使用人/需求名/平台/模式 五列，**不记 demo 内容、截图、文件路径或任何链接**）；
  **一轮交付只记一行**。
- **大改动新建 vN 文件，不覆盖上一版**——用户可能要在会上对比或回退；
  用户明说"不要影响 vX"时更是铁律
- 项目档案（project doc）更新：版本、章节表、依据材料、待核对假设——
  下个会话要能无缝接手
- 交付信息里给"怎么讲"：建议章节顺序、哪里按空格停、哪个章节对应老板
  最关心的指标

## 7. 三轮迭代的教训（写给未来的自己）

1. **先问"谁看、在什么场合、谁操作"**。展示型 demo 和体验型 demo 是两个物种：
   前者要自动播放+旁白，后者要自由交互。第一版默认做展示型。
2. **设计稿在手就必须像素级还原**。用户不会说"请还原设计稿"——他们默认你会。
   收到截图先逐张读，列出每屏的布局/图标/组件清单再动手。
3. **画饼要带背书**。管理层章节里"社区 53 条回帖要投票"比"我们规划了投票"
   有说服力一个量级。用研、竞品、数据报告都是弹药，主动检索项目文档。
4. **旁白即讲稿**。demo 做完先自己"读"一遍旁白，读不顺 = 故事线有问题，
   回去改剧本而不是改样式。
5. **迭代时聚焦用户的两三句反馈**，其余不动。反馈"没还原"就重做界面层，
   反馈"要自动"就重做交互层，别顺手重构没被点名的部分。
