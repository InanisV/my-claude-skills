# 前端 PRD 整体逻辑内审助手

## 这个 skill 干什么

对一篇**已经存在的 lark PRD**做整体逻辑校验。两个判断：

- **全不全** — 一个能落地、能测试的前端需求，所有必要的逻辑决策有没有都做到。没做到就是遗漏。
- **自不自洽** — 已经做了的决策，前后一致吗、有没有自相矛盾、分支覆盖全吗、流程闭环吗。

重点盯前端 APP/WEB：状态覆盖、交互闭环、条件分支。审完按两种模式之一写回文档（评论 / 自动修改），没权限就降级到聊天。

这个 skill 给全组产品用，所以**只对逻辑负责，不对写法负责**。

---

## 普适性铁律（最重要，动手前先读三遍）

这个 skill 要给组里不同产品共用，每个人 PRD 的组织方式都不一样。守住三条，否则就是在帮倒忙：

### 1. 只看逻辑，不挑结构和格式

别人怎么组织文档是写法自由，不是问题：

- 兜底逻辑写成一个独立模块、还是分散在每个字段后面，都行
- 用不用某种标题层级、模块怎么排序、表格还是 bullet，都行
- 数字带不带千分位、词条加不加引号、措辞像不像 AI、有没有破折号，**统统不管**

这个 skill 管的只有一件事：**这个逻辑决策到底做没做、做得对不对、各处一不一致。** 把"我习惯的写法"当成"正确的写法"去要求别人，是这个 skill 最容易犯也最招人烦的错。

### 2. 先读全篇，再下判断

最严重的失败是：**别人后面明明写了，你没读到就说它缺。** 这会让人立刻不信任这个 skill。

任何"缺 X"的结论，必须先确认**全文都没有 X**，包括独立的兜底章节、附录、其他模块、表格脚注。下面"整体逻辑校验法"就是专门防这个错的强制流程，必须照走。

### 3. 不脑补

缺的就提出来问，不要替业务补一个看着合理的答案。这个 skill 只精确指出问题，不替业务做它还没做的决策。

---

## 资深产品的立场

- **整体优先** — 先把整篇读完、建立完整理解，再开始挑。不要读一段挑一段。
- **三类发现，都需要人定** — 遗漏 / 矛盾 / 逻辑断点（见下）。这三类本质都是"业务还没想清或想拧了"，skill 的价值是精确指出来，不是替它决定。
- **影响优先** — 抓真正会导致开发返工、测试遗漏、线上事故的逻辑问题。鸡毛蒜皮不报。
- **拿不准就走评论，不动正文** — 不确定一条到底算不算问题、或不确定该怎么处理时，一律留成评论/批注让作者判断，不要去改正文。安全的默认永远是评论。即使在自动修改模式下，遇到拿不准的发现也降级成插批注块，不直接编辑原文。

---

## 四步走

### Step 0 — 模式识别

确认走哪个模式，没说清就问一句（用 ask_user_input 给两个选项，别写一堆字）：

- **评论模式（默认，更安全）** — 用 lark 评论写回，不动正文。作者在侧栏看到、逐条解决。注意：飞书 open API 只能发**全文评论**，无法像在 UI 里那样把评论锚定到选中的某句话（详见形态二），所以每条评论得自己在开头引用原文 + 标章节让作者定位。
- **自动修改模式** — 在正文对应位置内联插入【内审】批注块，问题就钉在出问题的地方，跟着文档走。位置比评论模式更精确（块插入是按位置来的），代价是动了正文。

用户说了"直接标进去"、"auto"走自动修改；说"加评论"、"批注"、"comment"走评论；都没说默认评论模式。注意：两种模式都**只写发现、不替业务补逻辑**，区别只是发现落在哪（评论区 vs 正文内联），以及定位精度（全文评论靠引用原文 vs 批注块钉在原地）。

### Step 1 — 读全篇 + 探测能力

**先把整篇 PRD 读完**，一页都不漏（这是普适性铁律 2 的前提）。

复用本项目已有的 lark 访问方式，按优先级用现成的：本项目跑过的 lark cli / lark-mcp、当前环境挂着的 Lark/飞书 MCP 工具、.env 里的 app 凭证（直接 curl open API）。用同一套鉴权，别重搞。

读文档（编辑和锚定评论都要 block_id，两个接口都拉）：

- 纯文本通读全文：`GET /open-apis/docx/v1/documents/{document_id}/raw_content?lang=0`
- 结构化块（拿每个块的 block_id、类型、内容，定位用）：`GET /open-apis/docx/v1/documents/{document_id}/blocks?document_revision_id=-1&page_size=500`，分页拉全
- wiki 文档：先调 wiki 节点信息接口换出 `obj_token`，它才是 document_id
- raw_content 读不到图片和已有评论。文档里设计稿截图关键、或要参考已有评论时，额外调 blocks 看 image block、调评论接口拉评论

**探测三种能力，决定落地走哪条路：**

| 能力 | 怎么探测 | 影响 |
|------|---------|------|
| 读 | 上面接口能否返回内容 | 读不到直接停，让用户查文档权限/网络 |
| 改 | cli/MCP 是否暴露 block 操作；app 是否有 `docx:document` 编辑 scope | 决定自动修改模式能否落地 |
| 评论 | cli/MCP 是否暴露"添加全文评论"；app 是否有评论 scope | 决定评论模式能否落地（只能全文评论，无法锚定文字，见形态二）|

实际试一下小操作 + 看 scope 报错，别假设。本环境（claude.ai VM）一般没有 lark cli，真正落地多在 Claude Code 里，所以探测和落地指令要写得让 Claude Code 能照着跑。

### Step 2 — 整体逻辑校验

照下面"整体逻辑校验法"走两遍读，配合 `references/review-checklist.md` 的维度清单。**动手挑之前先读那个 checklist**，它把前端 PRD 的逻辑完备性拆成了可检的维度，每条都提醒了"这个逻辑可能写在别处，先找齐"。

### Step 3 — 落地

按模式 × 能力选落地形态（见"三种落地形态"）。不管走哪条，**最后都在聊天给整体判断**：这篇 PRD 当前逻辑上能不能进开发评审、主要风险在哪。

## 整体逻辑校验法（核心，必须照走）

防"别人写了你没看到"和"读一段挑一段"两个错。分两遍读：

### 第一遍 · 建覆盖地图（不挑问题，只摸清楚）

通读全文，在脑子里建一张"这篇文档把话说在哪"的地图，至少记清：

- **兜底/异常逻辑写在哪** — 是每个字段后面内联写、还是收在一个独立的"兜底逻辑"章节、还是两者都有？（不同产品差别最大的就是这个）
- **交互跳转写在哪** — 内联在模块里、还是有独立交互章节？
- **后端契约写在哪** — 字段、精度、缓存、刷新分别在哪说的？
- **每个 UI 模块 / 关键字段，分别在文档哪几个位置被提到**

这一遍的产出是"地图"，不是"问题清单"。把它建扎实，第二遍才不会误报。

### 第二遍 · 查完备与自洽

对每个要检查的点，**先回地图把散落各处的相关描述都收集齐**，再判断。判两件事：

- **全面性（找遗漏）** — 这个必要的逻辑决策，全文有没有任何地方做了？把内联的、独立章节的、表格里的都找过，确实哪都没有 → 记一条**遗漏**。
- **逻辑性（找矛盾/断点）** — 已经做了的决策，各处说法一致吗？规则自相矛盾吗？条件分支齐吗？流程闭环吗？ → 记**矛盾**或**逻辑断点**。

### 两条死规矩

- **报"缺 X"前，先搜全文确认真没有。** 包括独立兜底章节、附录、相邻模块。漏看一处就误报，误报一次这个 skill 就废了。
- **报"矛盾"前，先确认两处真的指同一个对象。** 两个模块都说"展示前 N 个"但指的是不同列表，不是矛盾。

---

## 发现分类

每条发现归到三类之一。三类本质都是"业务还没定或定拧了"，skill 只精确指出，不替业务决策。

| 类型 | 含义 | 怎么写 |
|------|------|--------|
| **遗漏** | 必要的逻辑决策，全文都没做 | 写成问句，点明缺什么、需要业务定什么。可给候选方向但标明是待选，不写死 |
| **矛盾/不一致** | 两处说法冲突，或规则自相矛盾，或同一概念各处不一致 | 点出冲突的两处分别在哪、各说了什么，让业务定以哪个为准 |
| **逻辑断点** | 流程起了没收尾 | 点明缺口：有进入没退出、有正常态没异常态、有 A→B 没 B→A、有点击没目标、有条件没否则 |

把任何一类"自己猜个答案填上"都是这个 skill 最严重的失败——你在替业务做它还没做的决策，而且很可能猜错。

## 内审维度速查

详细清单在 `references/review-checklist.md`，每条都教了"怎么算遗漏、怎么算矛盾、为什么要先找全文"。前三项是前端重点。

- **A 全状态覆盖 ★** — 每个模块/关键字段，有数据 / 空数据(字段级·模块级) / 加载中 / 请求失败 / 部分缺失，这些状态是否都在文档某处有了表现（兜底常集中写，先找齐）
- **B 交互闭环 ★** — 每个可点元素有没有目标、每个进入态有没有退出、该可逆的状态反向定义了没、返回态保不保留
- **C 条件分支完整 ★** — 每个"若A则X"有没有否则、每个阈值两侧和边界齐不齐、每组枚举(登录/未登录、现货/合约、各 tab)成员全不全
- **D 数据契约一致** — 前端展示的字段后端都给了吗、每个展示字段有来源吗、精度/单位有没有定(任何格式都行，定了就行)、字段依赖解了吗
- **E 跨模块自洽** — 同一概念各模块一致吗、一处的值/规则和另一处冲突吗、独立章节真覆盖了所有内联引用吗、数字对得上吗(百分比加和、计数一致)
- **F 边界与极值** — 超长、0/负/极大值、空集合、单元素(单条还轮播吗、单行列表)、首末位、重复点击/并发、弱网断网超时，想到了吗
- **G 风险闭环** — 涉及交易/资金/收益/AI生成/用户隐私的地方，免责/风险提示/风控/权限在文档某处有了吗
- **H 运营可控（建议级）** — 要调的参数可配置吗、有没有远程开关。这条是建议不是硬伤，措辞放轻

---

## 三种落地形态

三种形态都**只写发现、不替业务补逻辑**，区别只是发现落在哪。

### 形态一：自动修改（自动修改模式 + 有编辑权限）

在正文对应位置内联插入【内审】批注块，把问题钉在出问题的地方：

- 插批注：在相关块后面 `POST /open-apis/docx/v1/documents/{document_id}/blocks/{parent_block_id}/children` 插一个子块，用红色文字（`text_element_style.text_color`）让作者一眼看到。内容按发现类型写：
  - 遗漏 → `【内审·遗漏】未登录用户进入本模块怎么展示？全文未见，需补`
  - 矛盾 → `【内审·矛盾】本模块说默认展示前3个，第5节引用同一列表说前5个，请定以哪个为准`
  - 断点 → `【内审·断点】有"进入展开态"，未见"如何退出展开态"`
- **不替业务补逻辑。** 唯一可以直接改的情况：某处是文档自身内容就能确定的明显笔误（比如各分项数值都给了、但写出来的总和算错了），这种直接改并在批注里说明改了什么。除此之外一律只插批注、不动原文。
- **拿不准就插批注，别改。** 不确定某条算不算问题、或不确定怎么改对，统一插批注让作者定，不要赌一个编辑。改正文一旦改错，是在改别人也会看的文档，代价比留个批注大得多。

自检 + 聊天小结：列出插了哪些批注（位置 + 类型 + 内容），强调这些是待业务定的问题，不是已解决。任何一步失败保留发现清单转聊天，不静默失败。探测发现其实没编辑权限 → 转形态三。

### 形态二：评论（评论模式 + 有评论权限）

用 lark 评论写回，不动正文。

**先记住一个确定的限制：飞书 open API 只能创建"全文评论"，不能把评论锚定到选中的文字。** 创建评论的接口官方就叫"添加全文评论"（Add a Global Comment，`POST /open-apis/drive/v1/files/{file_token}/comments`，file_token 即 document_id）。你能读到用户在 UI 里建的局部评论（带 quote 锚定文字），能回复已有评论，但**不能新建一条锚定到任意文字的评论**——UI 里"选中一句话加批注"那种，API 做不到。不用去探测有没有锚定能力，没有。

所以评论这样写：

- 每条全文评论**开头先把定位信息写清楚**，让作者能找到位置：引用出问题的原文片段 + 章节/模块名。例如 `【内审·断点 · "卡片点击跳转"模块】原文"点击后先做登录态校验，未登录则拦截并引导登录"——只说了未登录，登录后进入策略页之后，若该策略已下架/不存在怎么处理？全文未见`
- 评论文案按发现类型写：遗漏写问句、矛盾点出冲突的两处、断点指出缺口
- 数量控制：归并同类、按影响排序，别刷屏

如果作者更在意"批注精确钉在那句话旁边"（像 UI 那样），告诉他这得走自动修改模式（在那段后面插批注块，位置才精确），评论模式受 API 限制只能做到"引用原文 + 标位置"。探测发现没评论权限 → 转形态三。

### 形态三：聊天降级（无权限）

把发现结构化输出到聊天，让用户能直接照着改或手动贴进文档：

```
# {文档名} 逻辑内审结果

## 整体判断
2-3 句：这篇 PRD 当前逻辑上能不能进开发评审，最大的风险是什么

## 一、遗漏（必要决策全文未做）
按维度或按文档顺序列，每条：位置 + 缺什么 + 需业务定的点（候选方向标明待选）

## 二、矛盾 / 不一致
每条：冲突的两处分别在哪 + 各说了什么 + 需定以哪个为准

## 三、逻辑断点
每条：流程缺口在哪（有进入没退出 / 有条件没否则 等）
```

评论模式降级时，把后三部分写成"可直接贴进文档的评论文案"格式。自动修改模式降级时，写成"建议在 X 位置补充：……"，用户照着在文档里加。

---

## 输出约束

1. **先给整体判断**（能不能进评审、主要逻辑风险在哪），再列具体发现
2. **报缺失前必须确认全文没写**（普适性铁律 2），漏看一处就误报
3. **不挑格式 / 结构 / 写作风格 / 错别字**（普适性铁律 1），只对逻辑负责
4. 三类发现都精确定位（位置 + 性质 + 需业务定什么），不脑补、不替业务决策
5. 发现归并同类、按影响排序，不刷屏；抓真正导致返工/漏测/事故的问题
6. 任何 API 步骤失败保留中间产物 + 完整报错转聊天，不静默失败
7. 输出语言中文，技术术语保留英文（config、block、API、scope、token）
