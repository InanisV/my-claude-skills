# Self-Review Gate —— 自检（两种模式）

> **先分模式再动手**：
> - **模式A·只自检（纯逻辑内审）**——用户**只说**"自检这份 PRD / 评一下 / 帮我看看这份需求逻辑"（`00` 模式表「只自检」行），没有要写飞书、没有要升级草稿。**只跑 `checks-logic/` 镜像的纯逻辑内审，不跑门禁 18 条、不打门禁分**，报告**直接回对话、不写任何文档 / 评论**。见下方「模式A」。
> - **模式B·发布前自检**——写 / 升级模式起草完、任何要写进飞书的稿，发布前跑：**门禁 18 条 + 逻辑内审第二道门两道门都跑 + 打分**。见下方「模式B」（原完整流程，一字不变）。

---

## 模式A·只自检（纯逻辑内审 · 独立入口）

> **定位**：这是**给产品自己看的纯逻辑内审**——只审"逻辑全不全、自不自洽、闭不闭环"，**不涉及发布准入**。所以**不跑门禁、不打门禁分、不碰飞书**。读入 PRD 可以是 lark 链接 fetch 或粘贴文本，**均只读**；发现**只回对话**，报告格式照 dify 内审报告同款（去 T 版）。
> **例外（一句指引即可）**：用户在只自检时**明说**"要门禁分 / 要过门禁 / 能不能过准入 / 打个门禁分"→ 那是发布前口径，转走下方**模式B**完整流（两道门 + 18 条 + 打分），别在模式A里硬凑门禁分。

> **⚠️ 本模式头号失败模式（先读死，它比任何技术性异常都致命）**：**"通读一遍觉得完整 → 直接下 0 条 / ✅完整"。** 前沿模型也栽在这——它真读了正文、真心觉得没问题，于是渲染出和认真枚举者一模一样的诊断行，却跳过了"逐对象逐维度落格"这一步，把只有穷举才现形的缺口（复用模块归属、模板/契约映射对不上、逐模块状态兜底、跳转上下文接不住）平滑掉。**破法只有一个：把"枚举网格"当成产出报告前的强制工作物**——不是可选的思考辅助，是不填满就不许下结论的闸。整体通读**恰恰是 L1 判定规则明令禁止**的（"不要因为文档整体看起来完整…就默认覆盖了"）；本模式用单 agent 跑，最容易把 `checks-logic` 那 4 路独立窄镜头的对抗枚举坍缩成一遍holistic通读，必须靠下面的强制中间产物把每个窄镜头逼回来。

### 三条铁律（只自检模式，先记死）
1. **不跑门禁、不打门禁分**：18 条 checks 语义检查、结构扫描器、复杂度分档、score 与 🟢🟡🔴 分数档位**一律不跑不出**——那是发布准入口径，只自检不涉及。只自检的"档位"只来自 `checks-logic` 的 scorer gate（可进评审 / 修改后评审 / 打回重写），不是门禁分。
2. **不写任何文档 / 评论 · 只读只回对话**：读入 PRD **只读**（lark 链接用 `lark-cli` fetch，或直接用用户粘贴文本），发现**只回对话**——绝不 block patch、绝不写飞书评论、绝不改稿、绝不建子表。**唯一例外**：出完报告后按 `references/11-usage-telemetry.md` 记一条使用到**独立的使用记录表**——那不是被审 PRD、不碰它一个字，不算违反"只读"；同样尽力而为、失败静默、不打扰。
3. **T 可测性维彻底不跑、不提及**：`L4` 不加载；报告**无「三、可测性」节、无任何 T 痕迹**（T 组计数、"可测性 N"、T 警告、T 条目都不出）。只跑 **A/F/B/C/E 五维**。

### 七步流程
1. **读入（只读）**：拿到 PRD 正文——lark 链接用 `lark-cli` fetch（只读不改），或直接用用户粘贴的文本。正文 0 字 → 结论视为无效，回一句"没读到正文"，不硬判（对齐 `checks-logic/00-pipeline §五` 无效运行）。
2. **L0 结构地图**：加载 `checks-logic/L0-structure-map.md`，通读全文产出"模块 + 一句话职责"清单（≤20 行），只做定位、不评判、不出 finding。**这份模块清单同时是下一步枚举网格的"行来源"——步骤 3 每个维度都要拿它逐模块过一遍，不许只挑看着可疑的模块。**
3. **机械枚举 → 先产出「枚举网格」再判覆盖（强制工作物 · 禁跳）**：加载 `checks-logic` 的 L1/L2/L3 三路镜像原文当判据（逐个加载，不用近似转述代跑，不加载 L4）。**下结论前，每一维必须先把"被枚举对象"逐个列出来、再逐个落"✓有原文锚点 / ✗缺口"两态之一——这张网格是产出报告的前置条件，填不满不许进步骤 4。** 枚举对象的最小口径：
   - **B（`L2-branch-closure.md`）**：逐个可点元素 / 状态标签 / 进入态 → 每个落"目标✓? 退出✓? 返回✓?"，任一未定义即缺口。
   - **C（`L2-branch-closure.md`）**：逐个条件 / 若-当 / 阈值 → 每个落"'否则'分支✓? 两侧边界归属✓?"，边界或反面未写即缺口。
   - **E（`L3-cross-module.md`）**：逐个跨模块值依赖 + **逐处"沿用现有 / 复用 / 归属声明 / 以现有为准"措辞** → 每个过下面的〔归属声明硬闸〕。**并含悬空引用（`08 §0.6` 悬空引用扫描，全文级）**：逐条规则句引用的 具名机制（XX 门槛/筛选/校验）/映射表（XX 词表/映射）/时间窗（XX 时段/周期/窗口）/集合（XX 池/队列/候选集）→ 回查全文有无 判定规则/结构样例/边界口径/进出定义，无定义即缺口（记 E 维）。
   - **A/F（`L1-fallback-boundary.md`）**：逐个有数据的 UI 模块 → 六状态（初始 / 加载 / 空 / 部分 / 成功 / 失败）逐格；逐个极值 / 边界量 → 上下界与越界各落一格。
   - 每格只认原文锚点：**"整体看起来完整 / 某模块应该会处理 / 有归属声明"都不算 ✓**（L1 逐字："必须有原文依据才算覆盖"）。盯着清单查、不开放式发挥；异常通道显式上报，**绝不静默当 0 条问题**。
   - 呈现可精简（网格是工作步骤、不进报告主体），但**必须真列真填**——诊断行要回填"枚举: B N对象 / C N条件 / E N依赖 / A·F N模块"证明每格都访问过。
4. **〔归属声明硬闸〕逐条过，非软提醒**（照 `checks-logic/00-pipeline §三`）：步骤 3 里枚举到的**每一处**"沿用 / 复用 / 归属声明 / 以现有为准"，都必须单独拎出来跑这个二分判定，不许整体扫一眼略过——
   - 只有两类 **且** 附一句原文说明"现有逻辑确覆盖本上下文的新点"，才算覆盖：① **约束归属**（PRD 写了"不得违反这些硬性边界"这类收口句）；② **平台标准原语的值**（前端调现有服务拿布尔 / 枚举即可的那种）。
   - 🔴 **库检索可用时加一道实证（`12-context-recall.md`）**：对全篇的"沿用现有逻辑 / 复用现有 X"声明**抽 1 条**，走 L1→L2→L3 找到那条现有逻辑的历史 PRD 切片，核一句"它确实覆盖本上下文"——**抽中的那条按实证判，不再按措辞判**。**超预算（`12` 双闸）或库里查不到 → 在报告里标注「归属声明未实证」，别硬跑**；本条只加实证、不改下面的二分判据。
   - 两类都不占、或占了却没有那句原文说明 → **该处默认判缺口**。裸归属声明（尤其上下文相关卡片 / 状态兜底 / 空态 / 契约↔模板映射）**一律不算覆盖**，即便声明看着很笃定。
   - **复用声明 × 新契约 交叉核对（E 的高发死角，务必单列）**：凡"复用 / 沿用现有〔组件 / 模板 / 页面 / 接口 / 现成 UI〕" **同时** PRD 又给这个现成物定义了要承载的**新内容 / 数据契约**（新的字段最小集、放宽或收窄的取值门槛、新允许的数据形态、比原来更多 / 更少的输入），必须有原文确认"现成物吃得下该契约的**每一种**允许形态"；只写"复用现有 X / 本期不改 X 样式"而没这句确认 → **判缺口**。**"本期不改样式 / Out of Scope"不豁免这条**——不改的是那个现成物，但你喂给它的契约变了。判据一句话：**契约允许的形态集 ⊄ 现成物已知能处理的形态集 = 契约 > 能力 = 缺口**（实测漏网根因：门槛放宽出一种更精简形态、却复用一个未确认支持该形态的现成组件）。
5. **先 aggregate 轻去重，再 LC 合并同类项**（两个计数别混）：先按 `00-pipeline §一` aggregate 轻去重——此时条数即诊断行的「合并后 N 条」；再加载 `checks-logic/LC-merge-dedupe.md`，按判据一/二/三砍 70-80% 噪音、只留硬骨头、合并同根因、每条带 `src_ids` 溯源，只出 高 / 中 两档——LC 前后条数即诊断行的「合并 N→M」。
6. **双钥匙 + 定档（按 `checks-logic/00-pipeline.md` 的 scorer，不打门禁分）**：
   - **双钥匙**：`confirmed=True` 需终审判高 **AND** 初审判高；单层高 → `confirmed=False`（进"待复核"、按中计档，不翻结论档位）。
   - **定档只数 `confirmed=True` 的逻辑高危 `logic_high`（维 A/B/C/E/F；T 独立轴、且本模式根本不跑）**：`logic_high>=8`，**或** `>=5 且【A/B/C/F 有高】+【E 有高】两大类` → **打回重写**；`>=1` → **修改后评审**；否则 → **可进评审**。
   - **大类档位（band）**：前端逻辑覆盖(A/B/C/F) / 跨模块自洽(E) 各自：有高→`🔴 有硬伤`；否则有中→`🟡 待补充`；否则→`✅ 完整`。（可测性 band 不出。第三档镜像 `00-pipeline §五` 原文作「健全」，dify 渲染态实际显示「完整」——模板从渲染态，非措辞漂移。）
   - **〔0 条反糊弄闸〕✅完整不是兜底默认、是挣来的**：某一维要落 `✅完整` / 该维 0 条，前提是步骤 3 该维的枚举网格**已逐行列出、且每行都是 ✓有原文锚点**。**"整体看起来完整 / 应该会处理 / 有归属声明"不构成 0 条依据**；**枚举对象数 < 该维应有对象数（诊断行 N 对不上模块/条件清单）即视为没真跑，不许下 0 条**——回步骤 3 补齐网格，别把欠枚举渲染成 ✅完整。「整体判断」字段只许陈述"逐格枚举后的覆盖结论"，不许写"文档整体看着完整 / 有归属声明所以没问题"这类holistic叙事。
7. **收尾采集（本清单的正式一步，别跳）**：🔴 **报告出完的当轮立即执行，不等"会话最终回复"**（`00 §恒定规则 8` 2026-08 改：按动作判、不按回合判——多支线会话里"最终回复前"这个锚永不触发）——报告一成形就先记这一条，再回复用户，按 `references/11-usage-telemetry.md` 记一条使用（模式填「自检」）——写的是**独立使用记录表**，不碰被审 PRD 一个字，**不违反铁律 2 只读**（其「唯一例外」句即为此步授权）；失败静默、绝不因此打扰用户或触发扫码。

### 对话输出模板（固定 · 照 dify 内审报告去 T 版）
> 三分区、条目标签、"→ 改:"句式、诊断行的组计数与合并漏斗**照 dify 原样**；**只去掉**「三、可测性」节与一切 T 痕迹（T 组计数、"可测性 N"）。枚举网格是产出前的强制工作步骤、不进报告主体，只在诊断行回填"枚举:"字段证明真跑过。

```
《<PRD标题>》逻辑内审报告

内审结论: <按 scorer gate 三选一，见下「结论行两种写法」>

▎维度判定  前端逻辑覆盖<✅完整 | 🟡待补充(N中) | 🔴有硬伤(N高)>  跨模块自洽<✅完整 | 🟡待补充(N中) | 🔴有硬伤(N高)>
▎✅ 已覆盖到位: <完整的维度列举，无则省略此行>

**整体判断**
<一两句：逐格枚举后的逻辑覆盖结论 + 阻塞与否 + 可否进评审 + 另有 N 条建议（非阻塞）；不许写"整体看着完整/有归属声明所以没问题">

**一、开发前需明确（N 条）**   （= 双钥匙 confirmed 高；0 条写"无。"）
- [闭环/分支/自洽/状态/边界] <US定位>|<主题>: <问题描述>
  → 改: <具体可落地建议>

**二、建议补充（N 条）**   （= 中档 + 单层高·待复核；条目格式同上）
- [闭环/分支/自洽/状态/边界] <US定位>|<主题>: <问题描述>
  → 改: <具体可落地建议>

📄 诊断  读取正文 <N> 字 | 枚举: B<N>对象·C<N>条件·E<N>依赖·A·F<N>模块 | A组N条|B组N条|E组N条|合并后N条|合并N→M条
共 N 条发现: 阻塞 N、待复核 N、建议 N。本报告只对逻辑负责，不涉及格式、排版、文案风格。
```
- **结论行两种写法**：`gate=可进评审`（0 条开发前需明确）→ `✅ 达到内审标准 · 可进评审`；`gate=修改后评审` 或 `打回重写`（有开发前需明确项）→ `🔴 有开发前需明确项·先补齐再提审`。
- 🔴 **止损心法（防越描越黑）**：只要「一、开发前需明确」= 0 条，就是"可进评审·完事"。「二、建议补充」有几条是**正常的**（高召回评审对任何真实 PRD 都有非阻塞长尾），**不代表没过、也不必逐条改**——挑给产品作可选打磨即可，别为把建议追到 0 而把 PRD 越改越复杂（那是治丝益棼）。
- **条目标签 → 维度**：`[状态]`=A、`[边界]`=F、`[闭环]`=B、`[分支]`=C、`[自洽]`=E（**无 T 标签**）。
- **分区归属**：「一、开发前需明确」= `severity=高 且 confirmed=True`（两层都判高）；「二、建议补充」= 中 + 单层高·待复核（标"待复核·初审X/终审Y"）；**无「三、可测性」节**（铁律 3）；低优先级可折叠或省略。
- **诊断行**：`枚举:` 段回填步骤 3 各维实际枚举到的对象数（对不上模块/条件清单即没真跑，回步骤 3）；`A组`=L1(A/F) 条数、`B组`=L2(B/C)、`E组`=L3(E)；**无 T 组、无"可测性 N"**；"合并后"=aggregate 轻去重后条数，"合并 N→M"=LC 终审前后条数；共 N 条按 阻塞(confirmed 高) / 待复核(单层高) / 建议(中) 三计。

## 模式B·发布前自检（写 / 升级模式内用 · 保持两道门 · 内容不动）

> 下面是发布前完整流程：门禁 18 条判定 + 逻辑内审第二道门 + 打分，一字不变。**写 / 升级模式起草完、任何要写进飞书的稿都跑这里；只自检独立入口走上方「模式A」。**

> 在写飞书前，用门禁的**原始 18 条检查**（`references/checks/` 原文）过一遍，达标才发布——把 PRD 变成"对着真卷子做完对完答案"，**显著提高一次过概率**（不等于保证；审查器模型可能有出入）。
> 找不到 checks 原文时，退回用 `01-authoring-rules.md §2/§3` 内联评并在报告注明"未用 checks 原文"。
> **基线**：`references/checks/` 是门禁原文镜像（归属审查方产品 @coast.lin），基线 **2026-07-08**（`crypto_data_source` / `external_dependency_declaration` / `implementation_ambiguity` / `internal_consistency` 四条于 2026-07-07 收范围——接口契约细节归技术方案，见下方新规 7；其余 14 条与 2026-07 初版一致；审查器 SKILL 升至 0.11.0）；门禁若升级需重新校准（报告会带这行）。

## 审查器新版行为（2026-07，写作与自检都要知道）

真实审查器（prd-review skill）在 18 条语义检查之外新增了这些机制，直接影响怎么写、怎么判：

1. **AI 阅读友好度判定**：审查器先判 PRD 是否"AI 阅读友好"（标题层级清晰、核心章节可定位、无大段口语散文、无需脑补即可逐条判定）。不友好 → 审查器自行"无损转写"后再评，且报告公开标注「未使用 AI 阅读友好的 PRD 格式」。转写依赖审查器归纳、有走样风险——**kit 产出必须直接达到 AI 友好**（分层标题 + 列表化 + 具名章节），跳过转写才最稳。
2. **复杂度分档（2026-07 更新）**：审查器**先填「估算依据表」**（功能点数 / 端数 / 高风险面 / 新数据模型·状态机有无 / 外部依赖数）再据表套档 `simple / medium / complex`。simple 只跑 4 项核心（矛盾/逻辑漏洞/可开发/可测试）+ 精简结构检查（判定条件见 `00` 判体量区）。**确定性护栏：命中 资金 / 交易 / 告警推送 触发词即强制抬到 ≥medium**；**护栏不含埋点——埋点是常规需求、可判 simple**，不因含埋点而升档（旧口径「涉埋点不判 simple」已作废）。kit 轻量档 ≈ simple 档的写作面。
3. **判定档位（变化）**：有 P0 → 🔴 有条件通过（修完 P0 可推进）；得分 <60 → 🔴 不通过；**无 P0 即通过**，≥80 🟢、60–79 🟡。P1 不再阻塞"通过"决策、只扣分。
4. **硬互斥封顶**：确认 1 个 `hard_mutual_exclusion` 封顶 79 分（🟡），2 个及以上封顶 74。→ 内部一致性是 🟢 的硬前提。
5. **跨检查去重**：同一位置同一问题多检查命中只扣最高一条（不会被重复扣死，也别指望"修一处赚多分"）。
6. **评论回写**：评审报告会以飞书评论回写到 PRD 文档上（就绪度档位 + 问题清单）。
7. **接口契约细节 = 技术方案职责（2026-07 新规，四条 check 同步收范围）**：接口名、调用方式（GET/POST）、request body、response 结构**不是 PM 在 PRD 里必须交付的内容**——写到「**谁提供 + 什么类数据/接口 + 待联调确认**」颗粒度即达标，给了契约细节算**加分项**（记进亮点/通过依据），缺了**不得判 issue**。落到具体检查：`external_dependency_declaration` 占位即通过；`crypto_data_source` 只要能识别数据来自哪个系统/数据域**或由谁提供**即通过；`implementation_ambiguity` 不把缺接口细节算实现歧义；`internal_consistency` 不把占位标注算内部矛盾。→ 正面写法见 `01 §0.5` 依赖接口条、`02` 后端逻辑先问闸。
8. **软化呈现**：报告以**就绪度档位领衔**（可开工 / 基本可开工 / 建议完善后开工），分数保留但不作唯一门面；问题用建设性措辞（「待完善项」而非「缺陷」）；**同一问题被多个检查命中，报告只呈现最高优先级的一条**（呈现去重，与第 5 条的扣分去重是两件事）。kit 自检报告同律，见步骤 5。

> kit 发布门槛**维持从严不降**（标准档 P0=0 且 P1=0）：审查器"无 P0 即通过"是它的底线，不是我们的目标——P1 照扣分，堆几个就掉出 🟢（<80）。从严档位恰好锚定 🟢。

## 自检的两栏口径（先理解）

- **① 门禁判定**：完全按 checks 18 条原文评，决定门禁是否退回。带 **★** 的是 kit 标注的 P0 重点项：`core_feature_specificity` **完全缺失**仍属 **kit 从严升格**（引擎 default P1，kit 按 P0）；`crypto_fund_idempotency` **完全缺失** 2026-07 起**引擎 default 已是 P0**，kit 与门禁同级、不再是升格（★ 保留只为提示"这是 P0 重点，别漏"）。其余按门禁原文严重度。**门禁 P0 永不静默放行。**
- **② kit 加严**（俗称"第二道门"：门禁不查、kit 额外加的逻辑内审六维 **A/F/B/C/E/T** + 幂等键有效性）。分两级：
  - **结构性断点** = **默认阻塞发布、强烈建议修**（门禁本身能过）。**判据（从严）：缺失会让某输入下系统行为无法唯一推导（研发要猜）就是断点**——进入态无退出/可逆转换缺反向/漏 loading/缺关键分支"否则"/幂等键粒度盖不住声明不变量，均属此。**拿不准是否核心 → 默认按断点。**
  - **细节项** = 建议、不阻塞。**仅**当"该枚举成员/时机在任何输入下都不改变对错、只影响展示完备度"才可归此。**细节项不是给真实断点降级的通道**：凡本质是缺分支/缺退出态/缺反向/幂等无效，措辞成"细节"也仍按断点。
  - **放行程序（硬约束，堵自我放行）**：结构性断点 **agent 不得自行放行**。仅当①报告已把该具体缺陷+失败时序+风险明确呈报用户，②用户被明确告知后仍显式要求发布——才可放行，且③报告结论行必须写一行 `⚠️ 用户带风险放行：<缺陷一句+失败时序>`，缺此行视为未放行。**默认动作是修，不是放行。**

> 事实与严重度分开：**读 check 原文判「事实」（pass/fail）；「严重度」按步骤2清单的 kit 口径**（部分 check 原文无 P0 字样、只在输出模板有 `P0|P1|P2` 占位枚举，属正常——以清单为准，不是"凭记忆"）。

- [ ] **命中 B 端路径时**（`02` B 端管理后台路径）：逐列表页核四件套（筛选默认值/分页/列格式/操作条件/详情逐字段）——空项=问产品的清单，不是留白的理由。
- [ ] **元素表机械自检（有界面的需求；纯后端/管道/纯埋点类跳过，报告注明"无界面载体"）**——规则写在 `02`/`07` 但没人机械核过，实测全篇空转，故落成勾选项：
  - **① 载体**：正文 `<table` 出现次数 **≥ 元素表个数**（数一遍再勾）。**0 张内嵌 HTML 表 = 全写成管道表了 → 不合格**，按 `07 §五.1` 回炉（管道表的 `<br>`+连字符是假列表）；无 CLI 纯文本降级交付除外（`07 §六` 本就禁 HTML 表）。
  - **② 列**：四列齐（原型/元素/说明/后端说明）且**「原型」列在表内**——文末**不得**有独立「原型图/最新原型」堆图章节（见 `02` 元素表指引、`06` 贴图小节）。
  - **③ 颗粒度**：随机抽 **2 个元素**（轻量档抽 1 个）核：是否 **≥2 个规则组**、每组 **≥2 条具体 bullet**。**一个元素只写一句散文 = 不合格，回炉**（组名自拟、有几组写几组，见 `07 §五.2`）。🔴 **顺带核格内形态**：抽到的行逐格看——**格内出现第二个分号 = 该拆成列表或嵌套**，「后端说明」列一视同仁（`07 §五.1`）。命中 B 端路径时四件套与本条**兼容**——四件套是该页元素表的内容清单，核完四件套照样按本条核颗粒度。🔴 **组数下限随行粒度让位**：元素行按 ⑤ 拆到字段级后，**单字段/单控件行 1 组 + 2–3 条 bullet 即合格**，「≥2 组」按整体行与交互复杂的元素核——拆细了还硬凑组名是注水（见 `07 §五.2`）；底线始终是"不写成一句散文"。

  - **⑤ 元素行粒度**（与 ④ 是两层：④ 切 UI 单元、本条切单元内的字段/控件/状态）：🔴 **判据是「覆盖」不是「行数」**——对着该 UI 单元的原型/设计稿**逐个点过去**：每个可见字段·控件·区域、每个交互行为、每个状态，在表里都能找到写它的那一行 → 合格；点到某个元素在表里查无此行 = 漏行，补。**写死的元素也要有行**（否则研发不知道是写死还是接口给），弹窗/表单/按钮的多状态要枚举全（见 `02 §元素行粒度`）。**症状 grep**：说明格出现顿号列举句（「展示 A、B、C」）= 拆分不足，把被列举项各拆一行。
    🔴 **反向护栏（同等重要，别为了"看起来细"注水）**：**不是行越多越好**——设计稿上没有的元素别造行；同一元素别拆成多行重复写；纯装饰、无任何规则可写的元素并进整体行一句带过即可。**最终标准只有一条：研发照着能唯一实现、QA 照着能唯一验证**（= 门禁 `developer_confusion` 的核心）；讲清楚了就够，凑行数与写一句列举同样不合格。

  - **⑥ UI 文案中文化 + 形态合规（两把 grep 都要跑）**：
    - **⑥a 语种**：正文 grep 英文 UI 文案（按钮/页签/提示语，如 For You、Following、More、Open in App）——**命中即不合格**：UI 文案一律译成中文并用中文引号「」框（规则见 `07 §二`），英文只出现在 `Localisation` 表的对照列；**后端字段名/错误码/接口名不在此列**（它们本就是英文，且各有其家——错误码在**错误码表**、数据来源指针在元素表「后端说明」列，见 `07 §二之三`）。
    - **⑥b 形态（2026-08 补，实测漏网）**：UI 文案**禁用代码样式（反引号 / `code` 标签）与英文引号 `"…"` 包裹，一律中文引号「」**（`07 §二`）。**grep 正文 `` `"…"` `` 与 `` `中文…` `` 两种形态**——反引号里包着的是**中文界面真字**（按钮名/页签名/提示语/选项名）即命中，**命中即改**成「…」。🔴 **豁免照「技术标识各有其家」总纲（`07 §二之三` 节末），别误伤**：埋点表的事件名与属性键、错误码表的码、Localisation 表的 i18n key、元素表「后端说明」列的数据来源指针、公式与配置 key、表格区间引用（`A1:E23` 这类）——**它们在自己的家里、本就该是 code 样式**，不在本条范围。判据一句话：**反引号里是「用户在界面上看得见的中文字」= 命中；是「研发用的标识符」= 豁免**。实测根因：⑥ 旧版只 grep 英文文案，**中文 UI 文案被 code 样式包住时一条都抓不到**，于是整篇 PRD 的界面文案全渲染成技术标识（权威形态见 `examples/example-copytrading-PASS.md`，146 处 UI 词条零反引号；`example-mini-lightweight.md` 已于 v1.5.1 同步修正）。

    - **a. 字面 grep**：①grep `必传|可空`——**聚集成表**的段落命中即不合格（🔴 **Data Requirements 埋点表的「是否必传」列豁免**，那是 `09` house 骨架的固有列，别误杀）；②grep `消费|联调|错误码|字段契约`——**只在它作章节名、或作叙述主语（整段在讲服务架构）时命中**，四类不算：**(0)** **错误码表的表名/表头/小节标题**（「错误码表」「错误码 | 触发场景 | 用户文案」）——那是产品交付物，正是达标形态（`07 §二之三` ✅ 错误码表条）；**(i)** 依赖占位后缀「（待联调确认）」——那正是达标形态；**(ii)** 元素表「后端说明」列的数据来源指针与职责归属句（`07 §二之三` 保护清单第 6 条）；**(iii)** 系统/管道类需求按 `02` 骨架写的「**本系统**消费什么（格式/字段/时机）」——那是业务口径，命中的是「XX 服务消费 YY 队列」「由 XX 服务下发」这种**他方服务架构叙述**。

    - **c. pattern grep（字面 grep 的漏网层，实测：`必传|可空` 全清零了，token 一个没动）**：①**枚举 token** `[A-Z]{2,}_[A-Z_]{3,}`（`CURSOR_EXPIRED` / `IDEMPOTENCY_CONFLICT`，实测 24 种 31 处）；②**snake_case 字段名聚集**（`content_id` / `symbol_id`，实测 `content_id` ×13）。🔴 **判据是「聚集或作叙述主语」，不是单次出现**——同段/同表冒出一串 token、或拿 token 当句子主语才算；**四类豁免（都是"技术标识在自己的家里"，总纲见 `07 §二之三` 节末）**：**(0) 表头含「错误码」的表格区域**——即 `07 §二之三` ✅ 的**错误码表**（`错误码 | 触发场景 | 用户文案 | 前端动作`），**一码一行的 token 全豁免**：码 → 文案的映射是产品交付物，不是替技术方案定契约；🔴 **豁免只到这张表的边界为止——同一批 token 只要出现在正文叙述或验收行里，照抓不误**（正文与验收引场景/文案、不引码）；**(i) Data Requirements 埋点章**——`standard_*` 事件名与**全部属性键**（`element_name`/`button_name`/`jira_id`/`module`/`is_in_login_status`… 以 `09 §2 埋点规范`＋`§5 输出埋点表` 为准，house 规范就要求英文，别逐个列白名单）；**(ii) `04 步骤 6` 技术方案对齐后回填的真实 key**——Localisation 的 i18n key（`mc_xxx`）与配置项总表的 config key，那是**与研发对齐后的终口径**，不是替技术方案定契约；**(iii) 元素表「后端说明」列那 1–3 条数据来源指针**（`07 §二之三` 保护清单第 6 条）。命中 → 按 `07 §二之三` 改写成「**触发情形 → 用户/运营看到的文案与动作**」，字段名换业务中文。
    - **d. - [ ] **复杂度预判**：先写一行**估算依据表**（`功能点数 | 端数 | 高风险面 | 新数据模型·状态机有无 | 外部依赖数`），再据表写下本篇预计档位 `simple/medium/complex`；**涉资金/交易/告警推送命中护栏 → ≥medium**（门禁按 ≥medium 跑全量 18 条）；**涉埋点不升档、可判 simple**（埋点类检查照跑、最多 P1）。kit 自检**不得据 simple 减项**（幂等/埋点等域检查照跑）。

## 步骤 2 · 逐条评判 18 条（① 门禁判定栏）

> **分档读法（`00` 分档加载清单同款，提速用）**：**标准档 18 条原文全读全判**；**轻量档/纯埋点档只读 10 份裁剪集**——下表里 7 条能判 **P0** 的全集（`developer_confusion` / `internal_consistency` / `implementation_ambiguity` / ★`core_feature_specificity` / ★`crypto_fund_idempotency` / `crypto_data_source` / `crypto_alert_cooldown`；后三条按步骤1 的 `is_fund`/`is_crypto_data`/`is_push` 开关判适用，**不适用也要在报告写明，别靠"轻量需求应该不涉 crypto"的隐式假设跳过**）+ `success_metric_quantification` + `acceptance_testable` + `acceptance_derivable`，正好覆盖轻量门槛（`P0=0` + 成功指标有判定口径 + 每 US-R 有验收）。**裁的是读取，不是判定**：未读的纯 P1 检查在报告里如实记「未全评·轻量裁剪」，**不许渲染成 pass**（P1 本就不阻塞轻量档、score 也不作门槛，故对结论零影响）；一旦升为标准档、或用户要真实 P1 数/门禁分，**回头补读全 18 条**。

对每条（跳过不适用域检查），读 `references/checks/<file>` 判事实，按下表定严重度：
```
check_id | pass(✅/❌) | 严重度(P0/P1/P2/none,按本清单) | location | why | fix
```

| check | 严重度口径（kit 清单，即使原文无 P0 字样也以此为准） |
|---|---|
| developer_confusion | **P0**（源 check 原文明写"不通过（P0）：核心流程分支研发必须任意选择"）；**但**主流程清晰、只是从属功能提示策略/异常兜底有差异 → 源 check 自带降级，最多 **P1** |
| internal_consistency | **P0**（源 check 明写）；仅 **`hard_mutual_exclusion`**（同一触发条件两套互斥实现）判 P0，属边界歧义 `boundary_ambiguity` 的 ≤P1 |
| implementation_ambiguity | 仅 `hard_mutual_exclusion` 时 **P0**，否则 ≤P1 |
| **★ core_feature_specificity** | **P0**（kit 从严，引擎 default P1；缺失=功能不可推导，等价 developer_confusion） |
| **★ crypto_fund_idempotency**(is_fund) | **缺幂等段落 = P0**（与 01 §2 一致；2026-07 起引擎 default 亦为 P0）；**键粒度盖不住声明不变量的有效性问题 = ② kit 加严·资金安全** |
| crypto_data_source(is_crypto_data) | **缺失 = P0**（2026-07 起门禁 default P0，由 P1 升格）；**占位即通过**——写清"来自哪个系统/接口/数据域"**或**"由谁提供"就算达标，不要求接口名/字段级契约 |
| crypto_alert_cooldown(is_push) | **缺失 = P0**（2026-07 起门禁 default P0，由 P1 升格）：可高频外发的推送/告警必须写冷却或去重口径 |
| exception_coverage·scope_boundary·target_user·external_dependency·success_metric·acceptance_testable·acceptance_derivable | 缺失 **P1**（acceptance/metric 不触发 P0；`external_dependency` 占位形态即通过，缺接口契约细节不判 issue） |
| tracking_*（4 条） | 缺失 **P1 封顶**——埋点是数据需求、不阻塞功能开发，**即便你判了 P0 引擎也会确定性降为 P1**，别按 P0 卡发布 |

> **判读纪律**：严重度以**本清单 + `checks/` 原文措辞**为准，不以引擎 `default_severity` 为天花板——`default_severity` 是"agent 没给严重度时的兜底值"，引擎只把**低于**它的抬升、不把 P0 压下来（唯二例外：`internal_consistency`/`implementation_ambiguity` 非硬互斥时软化为 P1，tracking_* 确定性封顶 P1）。四维归属（完整性30/可量化30/边界20/技术可行20）：`target_user`·`core_feature`·`tracking_requirement`·`tracking_goal` 属完整性；`acceptance_*`·`success_metric`·`developer_confusion` 属可量化性；`scope_boundary`·`exception_coverage`·`crypto_alert_cooldown`·`tracking_platform` 属边界；`external_dependency`·`implementation_ambiguity`·`internal_consistency`·`crypto_data_source`·`crypto_fund_idempotency`·`tracking_feasibility` 属技术可行性。

> **幂等三分支口诀（横跨①②，一次记清）**：① 没写幂等段落 → **① P0(★)**；② 写了但"每人一次"声明与键机制在**同一句话直接自相矛盾** → **① internal_consistency P0**；③ 写了不打架、但**键粒度 < 声明不变量粒度**（只 `event_id` 却声明"每人一次"）→ **② 资金安全·幂等有效性**（步骤2.5 四栏反证，默认修、可知情放行）。**只有第③种在 ② 的可放行范围；①的两种是 P0，永不静默放行。**

**评判纪律（对抗式）：**
- 判 pass 前先扮演挑刺审查器写出"最可能被判问题的最弱点"，再决定。
- 分支/兜底类走 `check_internal_consistency.md` 三步：写触发A/触发B；触发A≠触发B（0 vs 空、正常 vs 兜底、依赖层 vs 业务层）→ 最多 boundary_ambiguity(P1)。**边界**：若"唯一性声明"与"实现机制"在**同一处措辞里直接自相矛盾**（纯文本冲突）→ internal_consistency **P0**；若只是**幂等键粒度不足以保证声明的不变量**（机制有效性、非文本矛盾）→ 走 **② kit 加严·资金安全**（步骤2.5 四栏反证，默认应修）。
- "存疑给通过"只用于 **acceptance_testable / acceptance_derivable 这两条**。
- **机械 fail 触发**：某功能系统行为 **<2 句** / 缺 0 与空分支 / 命中模糊词黑名单(自动/智能/合理/按需)无触发规则 → 判该功能 P0。
- 尊重源 check 豁免（exception 不穷举、external_dep 内部自研豁免、tracking 的"无需埋点"豁免）。

> **Claude Code 可选加速**：对 18 条并行起子 agent 各读一条再汇总。其它平台**内联逐条等价**，不得跳过。

> **范围铁律（防过度严格）**：审产品逻辑、不审实现规格——接口字段/类型/路径、用什么组件容器、埋点字段、i18n 文案 **不在此报**（埋点见 `09`、i18n 见 `10`）。curator 三关：实现细节砍 / 有合理默认能继续则砍 / 矛盾看"发错是不是线上 bug"。

**以下为速查摘要（写作时提醒用），判据仍以 `checks-logic/` 镜像原文为准——自检跑镜像，不跑这段。**

- **A 全状态覆盖**：每个 UI 模块过 有数据 / 字段级空 / 模块级空 / **加载中(loading)** / 请求失败 / 部分缺失。**机械触发（断点）**：存在异步写或首次拉取的模块，未定义 loading/pending 态及其间可交互性（按钮是否禁用防重复提交）→ 断点。
- **B 交互闭环**：每可点元素有目标；每进入态有退出/返回态；可逆转换定义反向；跳走后返回态（保留/刷新/重置）。**机械触发（断点）**：枚举全文出现的状态标签（running/paused/stopped/加载/失败/空…），每个**非终态**若缺"离开该态"的显式转换（触发条件+目标态+系统行为+验收）→ 断点。
- **C 分支穷尽**：每"若A"有"否则"；每阈值定义两侧+边界归属（`=50%` 落哪边）；每组枚举成员齐全。
- **E 跨模块自洽（旧版最缺，务必跑）**：模板/条目数量对得上（表列 7 行为、后端 4 template_name = 死结）；前端要用的**值** vs 该值拿不拿得到（PRD 标"不返回/待确认"= 死结）；同一概念多章节口径一致、数字加得起来；约束归属唯一（别三处各写"算法/前端/用户"决定）。**机械触发（断点）**：同名按钮/入口在不同章节的跳转目标或交互行为不一致（如一处写弹窗、一处写原生流程、验收又合并成第三种）→ 断点。**死结 = 断点。**
- **F 边界极值 / T 可测性**：F=空集/单元素/超长/0负超大/连点并发/弱网；T=虚词（智能/合理/动态/自动/千人千时）+ "隐含取值没给具体值"；T 另查：**后端逻辑中每个带数值阈值的规则至少映射一条验收**（构造命中/不命中输入的可测断言），否则记遗漏；**分段格式模式（{N}min/{N}h、KMBT、滚动窗口）无 边界+取整+时区/窗口起点 且未引用 `07 §一` 默认口径 → 记遗漏（研发必问级，默认修）**。详见 `08`。
- **跨维度死结（串联看）**：可达性链（推荐→页→数据依赖→空白页）、前置-达成链（月中上线往期不可补→徽章达不到）。
- **生效时机/状态迁移**：规则生效 立即/延迟/定时/跨周期 + 存量数据处理已写；复杂状态机配 mermaid stateDiagram。
- **资金安全·幂等有效性反证（必做）**：对每个 发放/入账/扣减/状态翻转，填四栏——`幂等键=? · 声明的唯一性不变量=?（如"每人一次"）· 一条用两个不同键值触发两次生效的时序 · 该时序被什么挡住`。第四栏为空 → 断点。**记住：event_id/request_id 只防重投，防不住"每人一次"；每人一次要另加 per-user 唯一键或发放台账。**
- 下单/交易类必查极值：0/负/空集、首末位、重复点击防抖、竞态、弱网。

> **断点 = ② 结构性断点**：进入态无退出/缺反向/漏 loading/缺关键"否则"/幂等无效性 → **默认阻塞发布、可知情放行**；C 的非核心枚举齐全度、生效时机细节 → 建议、不阻塞。
> **细节项轻量扫描**：同一字段的兜底措辞出现 ≥2 处且不一致（如一处"无需补 0"一处没写）→ 细节项提示，建议收敛为一处定义或「通用显示口径」块（`07 §五`）。

## 步骤 3 · 汇总

- ① 门禁判定：P0 / P1 / P2 数（一条只计最高严重度一次；判 P0 不再计 P1/P2；**跨检查去重**同新版门禁——同一位置同一问题被多条检查命中只留最高优先级一条再计数，避免高估）。
- ② kit 加严：第二道门六维 **A/F/B/C/E/T** 有无**结构性断点**、幂等有效性反证是否通过。

## 步骤 4 · 判定与修复

**放行三原则（权威，其余文件皆指向此）：** ① 门禁 P0/P1 = 硬门槛，**永不静默放行**；② 结构性断点 = **默认阻塞、仅用户知情后可放行**（带风险留痕）；细节项 = 仅建议、不阻塞。

**发布门槛：**

0. **前置（两档通用）·推断申报**：`01 §0.5` 推断申报清单已清——清单为空，或产品已逐条拍板；**未清视同缺口，不进发布**。
0. **前置（两档通用）·复述自查**：按 `02` 顶部「复述上限」的机械自查法跑一遍——**top 高频 保证/定性 短语 N 个，各出现 ≤2 处**（含「前端写死 / 不可点击 / 无后端」这类需求性质定性句）；**任一 ≥3 处 → 先收敛再发布**。
0. **前置（两档通用）·纯净度扫描**：grep `口径已锁定|单真源|设计差异|唯一定义处|以本 PRD 为准|覆盖旧口径` 类句式 → **正文零命中**（`01 §0.5` 交付物纯净度；命中 = 挪对话简报或删）。扫描对象是**发布正文**——这些词出现在本 kit 指引行 / `## PRD Quality Gates` 说明块里属正常，那两类由 `06` 步骤 0 净化另行删除。
- **标准档**：① 门禁 `P0=0 且 P1=0`；② 第二道门无**结构性断点**（默认；资金安全/状态机结构缺陷可用户知情放行）。
- **轻量档**（1 US-R、不新增/改动 发奖·行情取数·主动推送链路；涉资金但纯入口/文案/展示位、不碰发奖逻辑亦可，**但幂等段落仍须完整、缺失照 P0**）：① 门禁 `P0=0` + 成功指标有判定口径 + 每 US-R 有验收（其余 P1 不阻塞轻量档）。score 仅信息性、不作门槛。🔴 **门槛能裁，交付形态不裁**——收尾必须给出步骤 5 的「**轻量档三行简报**」（门禁判定+依据条数 / 步骤 0 逐项 ✅❌ / 分档裁剪说明）；只回一句「轻量档，P0=0/P1=0」**视为自检没跑**。

不达标 → 按 fix 就地改 → 重跑受影响检查 → 直到达标或用户知情放行。**修复两纪律（实测不守会边修边造新 P1）**：
1. **概念改齐**：每改一个口径，先 grep 全文该概念的所有出现处（元素表/字段表/数据依赖/验收/mermaid/埋点说明），一次全改齐——只保留一个定义点、其余处引用或同措辞；只改一处=制造双轨（一处双轨可吃 3 个 P1）。
2. **hedge 标记清零**：发布前 grep `待确认|与研发确认|待对齐|待补|上线前对齐|后续确认`——每处三选一：①当场定值——**仅限规格级细节**（埋点枚举、交互默认等，且方向已被产品确认）；**产品级决策（要不要做某个态/某条校验/某条规则）未拍板不得当场定值**，回 `01 §0.5` 申报闸问产品；②整条删除（研发域话题不提就没得咬）；③归属声明（"由 X 在代码层维护/在技术方案回填"）。悬空 hedge 在送审稿里全是 P1 靶子；只有真外部待定（接口链接/上线时间）可留且极简。**门禁 P0 永不静默放行**。kit 加严的**结构性断点默认阻塞发布**（资金安全/状态机结构缺陷，可用户知情放行）；**细节项**仅建议、不阻塞。修复优先级：门禁 P0 → 门禁 P1 → ② 结构性断点 → 细节项 → P2。

## 官方引擎软集成（装了就用，没装按现状）

**探测**：`ls ~/.claude/skills/prd-review-skill/review_engine 2>/dev/null || ls "$CLAUDE_CONFIG_DIR/skills/prd-review-skill/review_engine" 2>/dev/null`。命中即本机装有 coast 官方 prd-review skill，**模式B 的评分改用官方引擎**（零三方依赖，只需 python3）；未命中 → 按 `references/checks/` 镜像自判打分（现状流程，一字不变）。

**用法（三步，须在 skill 根目录跑——`review_engine` 是 python 包）**：

```bash
cd ~/.claude/skills/prd-review-skill
python3 -m review_engine plan <prd.md> --complexity simple|medium|complex > plan.json   # ① 出本篇需判定的检查项 + 各自规则全文
# ② agent 逐项自判，写 results.json：{"<check_id>": {"pass": bool, "issues": [{...}]}, ...}
python3 -m review_engine score <prd.md> results.json --complexity <同上> --source-format ai|human   # ③ 官方分数 + 报告
```

- `plan` / `score` 的 stdout 是 JSON、状态信息走 stderr；`--complexity` 缺省 `medium`，引擎会自行套高风险护栏抬档并在 stderr 提示。
- **以引擎输出为准**：score/verdict/decision/issue 严重度都取引擎结果，kit 的镜像自判退为 fallback 与交叉校验（两者结论打架时，报告写明分歧，按引擎结论定门禁、按 kit 从严项定发布）。
- **不变的部分**：② 第二道门（`checks-logic` 六维 + 幂等有效性）**引擎不查、照跑不误**；kit 发布门槛（标准档 P0=0 且 P1=0）不因引擎出分而放宽。
- 引擎用法细节以其自带 `review.skill.md` / `README.md` 为准；kit **不打包**引擎本体，命令跑不通就退回镜像自判，别去装、别改它。
