# Check: 验收标准可推导性

## 检查对象
核心功能描述与验收标准之间的对应关系。

## 判断标准（宽松，优先给通过）
- 通过：只要能从描述推导出**大致稳定的测试方向**，即算通过（不要求逐功能一一对应、不要求措辞精确）。
- 不通过：仅在以下情况判不通过——
  1. 核心功能**完全没有任何**可推导的验收线索；或
  2. **同一输入域内**出现真实矛盾，导致无法唯一推导预期结果。
- 不同输入域的并列分支、措辞差异、覆盖不全的边界细节，都**不**构成不通过。

## 判断步骤（必须按此顺序）
1. 枚举文档中出现的所有不同输入域、系统状态或调用路径（例如：不同取值、正常路径 vs 异常兜底路径、不同系统层级）。
2. 对每个输入域分别判断：该域是否有对应的唯一处理结果？验收口径是否可推导？
3. 只有当同一输入域内的处理行为在文档中互相矛盾，导致无法唯一推导预期结果时，才判为不通过。
4. 不同输入域各自已有定义时，即使处理方式不同，也是并列分支，不构成“无法推导”。

## ✗ 典型不通过案例
- 功能描述写了“支持批量导入”，验收标准却只写“系统可正常运行”，无法推导导入成功的判定结果。
- 验收标准存在，但与功能描述脱节，无法判断在什么输入、什么条件下应出现什么输出。
- 功能规格提到多个关键行为，但验收标准只覆盖其中一部分，剩余行为没有可验证结果。

## ✓ 典型通过案例
- 每个核心功能都能从描述中推导出可执行的测试断言，如“创建成功后列表可见”“重复提交不会生成重复记录”。
- 功能描述与验收标准是一一对应或稳定映射的，QA 不需要猜测预期结果。

## 豁免与边界
- 功能规格与验收标准服务不同读者，措辞不要求逐字一致；只要两者可以同时为真且能稳定推导结果，就算通过。
- 不要求 PRD 提供完整测试用例矩阵，只判断是否能推导出稳定测试口径。
- 存疑时默认给通过（benefit-of-the-doubt）：只要能推断出大致测试方向，记为通过；细节不足由报告扣分体现，不必判 fail。
- 本检查不再触发阻塞（P0）。即便判不通过，也只作为 P1「开发前建议补充」，不会单独把 PRD 卡成阻塞。

## ✗ 典型误判（few-shot 负例）
以下场景属于不同输入域的并列分支，各域验收口径可分别推导，不应判为不通过：

- 文档写了“字段值=某特殊值时走处理链路 A”，同时写了“字段值为空/未返回/非法值时走降级链路 B”。
  → 两条链路分属不同输入域，各自预期结果明确，验收口径可分别推导。
- 文档写了“正常链路中参数必须透传”，同时写了“参数提取失败后继续调用并降级记录日志”。
  → 正常路径与异常兜底路径是不同调用路径，各自预期结果已定义。
- 文档写了“依赖接口返回错误码时业务层降级返回内置限制”。
  → 接口层错误码与业务层处理结果是不同系统层级的定义，两者可同时成立。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
