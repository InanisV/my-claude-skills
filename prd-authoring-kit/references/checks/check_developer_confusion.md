# Check: 开发者与 QA 视角可推导性

## 检查对象
全文功能规格，从研发实现和 QA 验证两个视角评估可推导性。

## 检查方式
分两个视角判断：

**开发者视角**：假设你是接到这份 PRD 的全栈工程师，需要独立实现所有功能。
是否存在你无法从 PRD 推导出唯一实现路径、必须猜测或向 PM 确认才能继续的关键决策点？

**QA 视角**：假设你是独立 QA，需要从这份 PRD 设计验收测试。
是否存在你无法从 PRD 推导出明确预期结果、无法判断测试是否通过的核心验收点？

## 判断标准
- 通过：所有核心流程的关键分支都有明确定义，研发和 QA 不需要猜测。
- 不通过（P0）：存在 1 个或以上核心流程分支，研发必须任意选择才能实现，或 QA 无法构造唯一判定断言。
- 不通过（P1）：存在非核心细节需要猜测，不影响主流程正确实现和主路径测试。

## 禁止误判规则
- 若文档已分别定义 `0`、`null`、空值、非法值、未返回` 的处理方式，**不得**把这些不同输入合并后再判为“无法推导”。
- 若文档已分别定义“正常链路参数透传”和“提取失败后的继续调用/降级链路”，**不得**把它们判成同一分支下的两套实现。
- 若同一接口被主功能和展示型从属功能复用，而差异仅体现在是否 toast、是否静默降级或是否沿用原逻辑展示，默认最多记为 `P1`，**不得**判为 `P0`。

## ✗ 典型不通过案例
- 两处对同一规则给出互斥定义，研发必须选其一。
- 超限后的处理流程有多种理解，且 PRD 未给出消除歧义的约束。
- 验收标准写“符合预期”，但 PRD 未定义在什么输入下应输出什么。
- 文档同时写“同一输入值应禁止提交”和“同一输入值应自动改写后继续执行”，且没有优先级说明。

## ✓ 典型通过案例
- 每个关键分支都有触发条件和唯一处理结果。
- 验收标准可以直接映射为“给定输入 X，系统输出 Y”的可执行断言。
- 文档明确区分“正常路径参数透传”和“上游提取失败后的异常兜底继续调用/降级记录日志”，研发可以按调用链落地，不需要额外猜测。
- 同一接口被主功能和依赖它的展示型从属功能复用时，若文档已说明主功能按限制拦截、从属功能为避免无关打扰而采用不同提示策略，也算可推导。
- 上游依赖接口可能返回 `500` 或调用失败，但业务系统文档明确规定“捕获失败后降级为内置口径继续返回给用户”，这表示“内部依赖失败”与“最终业务结果”被分层定义，不算开发者困惑。
- 文档明确写明 `0` 是受限场景的特殊值，而 `null/空值/非法值/未返回` 走另一套降级链路时，研发可直接按值域分支实现，不算困惑。

## 豁免与边界
- 纯技术实现细节（框架、数据结构、日志格式）不在本检查范围。
- §2.x 概述与 §5.x 详细规格的层级差异不算歧义；详细规格是权威来源。
- 不要求 PRD 枚举所有测试用例，只判断核心路径是否可推导。
- 若主功能流程本身清晰，只是依赖该接口的从属功能在异常场景下采用不同提示策略（例如是否 toast、是否静默降级），通常最多记为 P1，不应直接判为 P0。
- 文档若明确区分 `0`、`null`、空值、缺失等不同返回值的处理方式，不要把它们混为一个“边界不清”的问题。
- 仅当主流程的核心输入、核心输出或阻断条件无法唯一确定时，才可判为 P0；异常兜底分支或从属功能的提示差异默认从严降级为 P1 评估。
- 评估时要按调用链推导：正常链路、上游提取失败后的异常链路、依赖该接口的从属功能链路可以是不同分支；如果文档已经给出各自分支的触发条件与处理顺序，不应因为存在兜底链路就判为开发者困惑。
- 若 `0`、`null`、空值、非法值分别具有不同业务含义（例如 `0` 表示命中特殊限制、`null` 表示上游未返回），应先按文档定义区分语义，再判断是否存在真实困惑，不能先合并再下结论。
- 若文档已经说明“依赖接口失败时系统继续走降级返回”，不要把依赖接口的 HTTP 错误码与最终业务返回行为混为一个问题。
- “参数在正常请求中必须传入” 与 “上游提取不到参数时继续调用或降级并记录日志” 可以同时成立；前者是正常路径契约，后者是异常路径兜底，不构成开发者困惑。
- 数值 `0` 默认视为一个有明确业务语义的有效值；除非文档明确写“0 视为空值/非法值”，否则不要把 `0` 与 `null/空值/未返回` 混为一类判断。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
