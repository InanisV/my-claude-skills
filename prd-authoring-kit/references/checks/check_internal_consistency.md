# Check: 跨章节内部一致性

## 检查对象
全文中对同一规则、参数、行为、阈值、职责边界的多处定义。

## 判断标准
- 通过：同一规则或参数在全文只有一套定义；若多处提及，语义保持一致，不会让研发或 QA 得到互斥结论。
- 不通过（P0）：两处或以上对同一规则给出互斥定义，且没有明确的优先级声明或“以某章节为准”的说明。
- 不通过（P1）：存在疑似矛盾，但需要结合上下文进一步确认；若只是概述层级与详细规格层级的粒度差异，不算矛盾。

## 禁止误判规则
- 只有当**相同触发条件**被要求产生**相反行为**时，才可判为冲突。
- 若文档已分别定义 `0`、`null`、空值、非法值、未返回` 的处理方式，**不得**把它们混为同一输入条件后再判冲突。
- 若文档已分别定义“正常链路参数透传”和“提取失败后的继续调用/降级链路”，**不得**把这两条不同触发条件的链路判为互斥。
- 若同一接口被主功能和展示型从属功能复用，而差异仅体现在提示策略或是否静默降级，**不得**直接判为 P0 冲突。

## ⚠ conflict_type 典型误判
- "`=0` 时改为1继续" vs "返回为空/非法时降级" → 触发条件不同，应为 `boundary_ambiguity`。
- "接口失败返回 `500`" vs "业务层降级并返回内置限制" → 同一路径的两层描述，应为 `boundary_ambiguity`。
- "正常路径下参数必须传入" vs "参数缺失时继续调用/兜底" → 不同触发条件，应为 `boundary_ambiguity`。

## ✗ 典型不通过案例
- 同一接口在一处写 `POST`，另一处写“通过 GET 请求”。
- 同一计算规则在不同章节分别写成 `min` 与 `max`，或一个写“向上取整”，另一个写“向下取整”。
- 同一 UI 超限行为，一处写“隐藏”，另一处写“置灰但可见”。
- 同一缓存或时效阈值，一处写“5-10 分钟”，另一处写“30 秒”。
- 同一异常边界，一处写“改为 1 继续”，另一处写“完全禁止提交”。
- 前后端职责在不同章节被明确写成两套互斥分工。

## ✓ 典型通过案例
- 同一规则在多处重复出现，但表达方式不同、语义一致。
- 详细规格对概述做展开补充，且不会推翻概述中的行为边界。
- 存在多处描述，但文档明确说明“以 §X.X 为准”，足以消除冲突。
- 一处描述正常链路参数透传，另一处描述上游提取失败后的继续调用/降级与日志策略；两者触发条件不同，可同时成立。
- 一处定义 `0` 的受限兼容逻辑，另一处定义 `null/空/非法值` 的降级逻辑；若文档已区分输入语义，不算冲突。
- 主功能与依赖该接口的从属展示功能对同一失败场景采用不同用户提示策略，但限制来源与后端兜底口径未变，通常视为一致。
- 一处列出上游依赖可能返回 `500`，另一处规定业务系统捕获后降级继续返回结果，这属于依赖层与业务层的分层定义，不算冲突。

## 豁免与边界
- §2.x 概述与 §5.x 详细规格的层级差异不算矛盾；若详细规格是对概述的展开，应视为一致。
- 同一行为在不同章节用不同措辞表达，但可同时为真、语义一致，不算矛盾。
- 用“例如”引入的举例与其他章节举例不同，不自动构成矛盾。
- 纯技术实现细节差异不在本检查项范围内，除非已经影响到产品行为定义。
- 正常路径要求某参数透传，而异常路径又规定“上游提取失败时继续请求/降级并保留日志”时，若两者触发条件不同且可同时成立，不算矛盾。
- 文档若分别定义 `0`、`null`、空值、缺失等不同返回值的处理方式，不应将它们混为同一规则后再判冲突。
- 主功能场景与依赖该接口的从属功能场景可以采用不同的用户提示策略；若差异仅体现在是否 toast、是否静默降级，且主流程限制口径仍一致，通常最多记为 P1，不应直接判 P0。
- 判断一致性时要沿调用链区分“正常路径”“上游失败后的兜底路径”“依赖该接口的从属功能路径”；若这些路径触发条件不同、可同时成立，不应混为同一规则后判互斥。
- 若文档明确把主功能链路与展示型从属链路拆开描述，且差异仅体现在是否沿用原逻辑展示、是否 toast、是否静默降级，不应把它们合并成同一条规则来判互斥。
- “必须传入参数”描述的是正常链路契约；“参数提取失败时继续调用/降级/记录日志”描述的是异常链路兜底。若文档未要求两者在同一触发条件下同时成立，不应判冲突。
- 若文档没有明确写“0 视为空值/非法值”，则应默认 `0` 与 `null/空值/未返回` 分属不同语义分支，不能把它们混为一条规则后再判冲突。

## 输出格式
返回 JSON：
`{"pass": bool, "severity": "P0|P1|P2|none", "issues": [{"location": "...", "description": "...", "severity": "P0|P1|P2|none", "why": "...", "fix": "...", "conflict_type": "hard_mutual_exclusion|boundary_ambiguity|single_unclear|none"}]}`

`conflict_type` 判断规则：
- `hard_mutual_exclusion`：相同触发条件被要求产生互斥结果，例如 `POST` vs `GET`、`min` vs `max`、同一输入既“继续处理”又“完全禁止”。
- `boundary_ambiguity`：不同触发条件的链路差异被混写，但不构成互斥，例如正常链路 vs 异常兜底链路、`0` vs `null` 的不同语义分支。
- `single_unclear`：单处表述不够精确，需要进一步确认，但没有形成两套互斥定义。
- `none`：仅在通过时使用。

`conflict_type` 判断程序（必须按此顺序）：
1. 分别写出两处描述各自的触发条件（"触发 A：..."，"触发 B：..."）。
2. 如果触发 A ≠ 触发 B（例如：一处为"返回值=0"，另一处为"返回值为空/null/非法"；或一处为"正常参数透传"，另一处为"参数提取失败后的兜底"；或一处为系统层错误码，另一处为业务层降级处理结果），则必须判为 `boundary_ambiguity`，不得判为 `hard_mutual_exclusion`。
3. 只有触发 A = 触发 B 且行为互斥时，才可判为 `hard_mutual_exclusion`。
