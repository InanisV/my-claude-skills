# Check: 埋点诉求技术可实现性

## 检查对象
PRD 中每一条埋点诉求，判断它在「客户端埋点」这一技术手段下是否真的能采集到。

## 核心前提（务必先理解）
埋点只能记录**用户在客户端的行为**，能力边界是以下四类：
- 曝光（元素/页面被展示）
- 点击（元素被点击/交互）
- 页面访问（PV / 进入某页面）
- 资源加载结果（前端发起的请求成功/失败/耗时等可在客户端观测的结果）

埋点**无法**直接采集：服务端内部状态、实时计算结果、其他用户/全局的聚合数据、未在当前客户端发生的事实。这类诉求需要走服务端日志或数据仓库，不能靠埋点实现。

## 判断标准
- 通过：所有埋点诉求都落在上述用户行为可观测范围内，技术上可通过标准埋点事件采集。
- 不通过（任一即算）：
  - 存在「用埋点统计服务端状态/后台计算结果」的诉求，例如「埋点记录某订单的最终结算金额」「埋点采集风控系统的判定结果」「埋点统计全站某指标的实时总量」。
  - 诉求要采集的不是「当前用户在客户端的动作或可见结果」，而是需要后端数据才能得到的事实，却被写成埋点需求。

## 豁免与边界
- 「用户在客户端看到/点击了某个由后端返回的值」是可以埋点的（采集的是曝光/点击行为本身，可把该值作为事件属性），不要误判为不可实现。
- 数据指标的口径计算（如转化率 = 点击数/曝光数）由数据侧用埋点原始事件二次计算即可，PRD 只要能拆出可埋点的原子行为就算通过。
- PRD 不涉及埋点，或 **明确声明本次需求无需埋点**（如埋点/数据章节注明「本需求无需埋点」「无埋点诉求」）时，直接判通过（severity=none）；即使含「埋点」字样也不报问题。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
