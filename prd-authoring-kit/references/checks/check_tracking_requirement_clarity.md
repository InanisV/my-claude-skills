# Check: 埋点诉求清晰度

## 检查对象
PRD 中与数据埋点 / 事件上报相关的描述，通常集中在【埋点诉求】【数据与埋点】【埋点事件】等章节，也可能散落在功能详情里。

## 判断标准
- 通过：埋点诉求逐条说明了「要采集什么用户行为、用于分析什么」，每条诉求能让研发/数据同学知道该埋哪个页面、哪个元素、什么动作（曝光 / 点击 / 页面访问 / 资源加载结果）。
- 不通过（任一即算）：
  - PRD 明确提出要做埋点，但没有任何【埋点诉求】章节或等价说明，只在别处一句「需要加埋点」带过。
  - 埋点诉求存在但极度空泛（如仅写「核心功能加埋点」「关键路径打点」），未指明采集对象、触发动作或分析目的，研发无法据此设计事件。
  - 列出了要分析的数据指标，却没有说明这些指标对应哪些用户行为埋点来回收。

## 豁免与边界
- 本检查只针对「PRD 自身已表达埋点需求」的情况。以下两类都直接判通过（severity=none），不要因为「没写埋点」就扣分：
  - PRD 完全不涉及埋点、也无数据回收诉求；
  - PRD **明确声明本次需求无需埋点**（如埋点/数据章节注明「本需求无需埋点」「无埋点诉求」）。即使含「埋点」字样、甚至写有成功指标，也不报缺失、不要求补埋点。
- 不要求 PRD 写出具体事件名、属性名或埋点表（那是 tracking-gen / 埋点表的职责）；只判断诉求颗粒度是否足以指导后续埋点设计。
- 运维监控类「埋点」（如服务端日志埋点、性能监控打点）不属于用户行为埋点，不在本检查范围内。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
