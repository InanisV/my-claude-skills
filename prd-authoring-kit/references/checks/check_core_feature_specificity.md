# Check: 核心功能具体性

## 检查对象
功能需求、核心功能、用户故事等描述系统行为的章节。

## 判断标准
- 通过：核心功能足够具体，研发可以直接理解系统要做什么。
- 不通过：功能只停留在口号、目标或抽象概念层面，研发仍需大量猜测。

## ✗ 典型不通过案例
- 只有标题或一句概括，如“支持行情展示”“优化用户体验”“支持多样化操作”。
- 描述停留在口号层面，没有说清系统做什么、在什么条件下做、输出什么结果。
- 章节存在，但内容主要是背景、价值或目标，没有落到系统行为。

## ✓ 典型通过案例
- 每个核心功能至少有 2 句具体描述，能回答“系统做什么、在什么条件下、给谁什么结果”。
- 研发可直接据此拆任务，不需要先反向猜测功能边界或核心行为。

## 豁免与边界
- 不要求 PRD 提供技术实现细节、接口字段、数据库设计或日志规范。
- 若某功能在另一章节已有完整定义，应先 cross-check；不要因为当前章节写得简短就直接判不通过。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
