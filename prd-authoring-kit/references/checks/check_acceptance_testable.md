# Check: 验收标准可测试性

## 检查对象
验收标准、测试口径、通过条件相关章节。

## 判断标准（宽松，优先给通过）
- 通过：存在**任何**可观察行为、结果方向或大致可测口径，QA 能据此设计测试（哪怕措辞不够精确）。
- 不通过：仅在以下两种情况判不通过——
  1. 验收标准**完全缺失**；或
  2. **纯自引用**——只有“系统正常运行”“体验良好”“功能可用”“符合预期”这类泛化表达，且没有任何可观察行为、阈值或结果断言。
- 不要因为验收标准不够量化、措辞与功能规格不一致、或缺少某些边界细节就判不通过；只要 QA 能推断出验收方向，就算通过。

## ✗ 典型不通过案例
- 只写“系统正常运行”“体验良好”“功能可用”“符合预期”。
- 只写“符合设计稿”或“满足业务要求”，但没有可观察行为、阈值或结果断言。
- 只有主观判断，没有明确的通过/不通过边界，QA 无法稳定复现结论。

## ✓ 典型通过案例
- 明确数值阈值，如“接口响应时间 < 500ms”“成功率 ≥ 99%”。
- 明确操作路径与结果断言，如“用户点击提交后 3 秒内看到成功提示，并在列表中看到新增记录”。
- 明确异常条件下的预期结果，如“网络超时时展示重试按钮，且不重复创建记录”。

## 豁免与边界
- PRD 不需要提供测试样本、测试数据明细或测试用例枚举，这属于 QA 设计范围。
- 只有当验收条件缺失到 QA 无法判断系统是否通过时，才判不通过。
- 存疑时默认给通过（benefit-of-the-doubt）：验收偏弱但仍能推断方向，记为通过；真正模糊之处由报告的扣分体现，不必判 fail。
- 本检查不再触发阻塞（P0）。即便判不通过，也只作为 P1「开发前建议补充」，不会单独把 PRD 卡成阻塞。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
