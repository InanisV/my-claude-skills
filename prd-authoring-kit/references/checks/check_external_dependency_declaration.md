# Check: 外部依赖声明

## 检查对象
第三方系统、内部服务、接口、配置中心、竞品 API 等依赖描述。

## 判断标准
- 通过：关键依赖已被点出，研发可据此评估风险。
- 不通过：明显依赖外部系统，但 PRD 未显式说明。

## ✗ 典型不通过案例
- 功能依赖第三方 API、内部服务、其他团队接口、配置中心或竞品数据，但没有说明依赖关系或对接方式。
- 研发只有在开始实现后才会发现该功能需要外部能力配合。

## ✓ 典型通过案例
- 明确列出关键依赖来源、上下游关系或需协作对象，足以让研发评估实现风险。
- 对外部系统的限制、前置条件或待确认事项有基本说明。
- **接口用占位说明或只标明「依赖某方 / 某系统提供的某类接口」即视为通过**（如「依赖行情团队提供的实时价格接口，接口待联调阶段确认」）。产品层能识别到有此依赖、由谁提供、大致提供什么，风险即可评估。

## 加分项（非达标基线）
- 若 PM 额外给出了接口名、调用方式、request/response 字段等契约细节，属于**加分项**，应在 issue 结果里作为通过依据/亮点体现，而不是把「未给这些细节」当作缺陷。

## 豁免与边界
- 内部独立实现、无明显外部依赖的功能，不需要因为未列依赖而判不通过。
- 不要求 PRD 细化到接口字段、鉴权方式或环境配置，只需达到产品层风险可识别。
- **不得**因缺少接口名、调用方式、request body、response 结构等技术契约细节而判为 issue——这些属于技术方案 / 联调阶段职责，不是 PM 在 PRD 里必须交付的内容。

## 输出格式
返回 JSON：`{"pass": bool, "severity": "P0|P1|P2|none", "location": "...", "description": "...", "why": "...", "fix": "..."}`。
