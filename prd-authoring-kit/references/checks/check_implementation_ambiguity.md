# Check: 实现歧义

## 检查对象
功能规格中可能被研发理解为多种实现的描述。

## 判断标准
- 通过：关键行为有明确约束，不会导致多种互斥实现都“像是对的”。
- 不通过：同一描述可被理解为不同实现，研发必须猜测或反复确认。

## 禁止误判规则
- 若文档已分别定义 `0`、`null`、空值、非法值、未返回` 的处理方式，**不得**把这些不同输入条件混为同一触发条件后再判歧义。
- 若文档已分别定义“正常链路参数透传”和“上游提取失败后的继续调用/降级链路”，**不得**把这两条不同触发条件的链路判为互斥实现。
- 若同一接口被主功能与依赖展示型从属功能复用，而差异仅体现在是否 toast、是否静默降级、是否沿用原逻辑展示，**不得**直接判为 P0 实现歧义。

## ⚠ conflict_type 典型误判
- "`=0` 时改为1继续" vs "返回为空/非法时降级" → 触发条件不同，应为 `boundary_ambiguity`。
- "接口失败返回 `500`" vs "业务层降级并返回内置限制" → 同一路径的两层描述，应为 `boundary_ambiguity`。
- "正常路径下参数必须传入" vs "参数缺失时继续调用/兜底" → 不同触发条件，应为 `boundary_ambiguity`。

## ✗ 典型不通过案例
- 同一描述可被理解为“前端控制”或“后端控制”，且文档没有进一步约束。
- 使用“自动处理”“智能推荐”“合理提示”“按需展示”等未定义行为，却没有说明触发条件或选择规则。
- 判断问题时，若两种互斥实现都能满足这段文字，应判为不通过。

## ✓ 典型通过案例
- 对关键行为给出明确触发条件、处理规则和输出结果，使不同研发实现会收敛到同一行为。
- 即使措辞不是技术化表达，产品规格也能唯一约束系统行为。
- 文档区分了 `0`、`null`、空值、非法值等不同输入，并分别给出处理链路，例如 `0` 走受限兼容逻辑、`null/非法` 走降级逻辑，这属于可实现的明确分支，不算歧义。
- 文档区分了主功能链路与依赖该接口的从属展示链路，虽然两者前端提示策略不同，但后端限制来源和分支触发条件仍唯一，也不算歧义。
- 文档若写明“依赖接口失败时内部捕获并降级到内置口径继续返回”，同时又在接口说明里列出上游可能返回 `500`，这表示分层描述，不应误判为同一层面的两套实现。

## 豁免与边界
- 不要把纯技术方案分歧当成 PRD 缺陷，例如数据库索引、环境变量命名、日志格式。
- 接口名、调用方式、request body、response 结构缺失属于技术方案 / 联调阶段职责，**不算实现歧义**；PM 用占位或「依赖某方提供的某类接口」标注即可，不得因此判不通过。
- §2.x 范围概述与 §5.x 功能规格详细度不同不构成歧义；若 §5.x 已完整定义，应以其为准。
- 文档若明确区分 `0`、`null`、空值、缺失等不同输入的处理规则，不算歧义；不要把“0 和空是两种不同语义”误判为同一值的冲突定义。
- 主流程参数在正常路径下必须透传，但文档同时为“上游提取失败/依赖异常”定义了异常兜底流程时，不自动构成歧义；只有在相同触发条件下存在两套互斥实现，才判不通过。
- 同一接口被主功能场景和从属展示场景复用时，可允许两者有不同的前端提示策略或静默降级策略；只要核心限制来源、后端兜底规则和分支触发条件仍可唯一推导，就不算实现歧义。
- 不要自行推断 `0` 属于“空值/非法值/未返回”；只有文档明确把它们归为同一类时，才可按同一分支判断。
- “接口契约要求参数正常透传” 与 “上游提取失败时继续调用或降级处理” 是两种不同触发条件下的链路，不能因为都提到同一参数，就推导成两套互斥实现。
- “上游依赖可能返回 500” 与 “业务系统捕获后降级继续返回结果” 也是两层定义；除非文档同时要求业务对用户既报错又成功返回，否则不构成实现歧义。

## 输出格式
返回 JSON：
`{"pass": bool, "severity": "P0|P1|P2|none", "issues": [{"location": "...", "description": "...", "severity": "P0|P1|P2|none", "why": "...", "fix": "...", "conflict_type": "hard_mutual_exclusion|boundary_ambiguity|single_unclear|none"}]}`

`conflict_type` 判断规则：
- `hard_mutual_exclusion`：相同触发条件要求产生互斥行为，例如 `POST` vs `GET`、`min` vs `max`、同一输入既“改为 1 继续”又“完全禁止”。
- `boundary_ambiguity`：不同触发条件下的链路差异被描述得不够紧，但本质不是互斥实现，例如正常链路 vs 异常兜底链路、`0` vs `null` 的不同分支。
- `single_unclear`：单处描述不够具体，研发需要补充确认，但没有出现两套互斥实现。
- `none`：仅在通过时使用。

`conflict_type` 判断程序（必须按此顺序）：
1. 分别写出两处描述各自的触发条件（"触发 A：..."，"触发 B：..."）。
2. 如果触发 A ≠ 触发 B（例如：一处为"返回值=0"，另一处为"返回值为空/null/非法"；或一处为"正常参数透传"，另一处为"参数提取失败后的兜底"；或一处为系统层错误码，另一处为业务层降级处理结果），则必须判为 `boundary_ambiguity`，不得判为 `hard_mutual_exclusion`。
3. 只有触发 A = 触发 B 且行为互斥时，才可判为 `hard_mutual_exclusion`。
