# Interview Playbook —— 从零对话把需求聊清

> 「访谈模式」。目标不是问满字段，是**问到每个核心功能的分支唯一可推导**——然后尽快起草，别把产品问烦。

## 对话总原则

- **一次聚焦一个功能/一件事**；这件事内若产品能一口气答，就用 **2–3 选项的小清单**一次问齐，别拆成十轮。
- **进入拍板循环后按 `00 规则 10` 的收尾句走**：回合以下一条问题或清零声明收尾，不以「已写入」结束；功能深挖仍按上一条用 2–3 选项小清单一次问齐，骨架 / 判定表照下文「先立骨架再讲规则」给，不发不带骨架或问题的千字分析。
- 回答含糊时给具体选项引导，别开放式追问到底。
- 能从上文推断的别重复问；**边聊边往 `02-prd-template.md` 结构里填**。
- 前后矛盾**当场点明**（这正是 internal_consistency 会挡的）。
- **复述确认理解（防误解，必做）**：产品讲完一个关键逻辑，用一句话复述你的理解让 TA 确认（"我理解是……对吗"）——**别默默按自己的理解往下写**；理解偏差要在对话里就抓出来，不是等起草后 5 段速览才发现（那时假设已经写进去了）。
- **关键逻辑大胆反问**：核心分支 / 状态机 / 频控 / 跳转 说不清、有矛盾、或明显缺了个决策时，**当场追问到清楚为止——这不算"问烦"**。下条"别问烦"只针对实现细节（超时值 / 用什么组件 / 接口字段），**不适用于核心逻辑决策**：那些没问清，起草出来就是要返工的洞。
- 中文、简洁。**实现细节够了就说"我先起草，你再改"，不要无限追问**（但"关键逻辑"没确认清之前别急着起草）。

## 采集顺序（命中第一个空的就问，能推断的跳过）

1. **背景/要解决什么问题** → "现在给用户带来什么具体麻烦/损失多大"。
   - **1b. 需求类型一句判**（新增 / 修改 / **删除下线** / 纯配置）：**删除下线型**（移除既有元素）的元素表写法反着来，按 `02 §元素行粒度` 删除/下线型小节写，别照"每元素一行"套。
   - **1c. 问人之前先问库**：**动身访谈前先完成 `12-context-recall.md` 的背景自采集**，拿「背景简报」垫底——命中的历史需求、既有口径、疑似冲突先自己查清，**问题清单只问增量**（简报里已有答案的别再问一遍，那才是真把人问烦）。纯埋点/纯后端类整步跳过；库里零命中就一句话放行、立刻转访谈。
2. **是否含前端页面**（有 UI 操作才算；纯后台/推送不算）→ 决定前端三件套还是后端行为写法。**单独问，别合并**。
   - **2b. 数据从哪来（新展示/新功能必问）**：「这个数据接口里已有，还是要后端新加？」不确定就问——这一句决定 PRD 要不要写后端逻辑、也影响体量档位。**别默认要后端改动。**
3. **目标用户**（具体+场景）→ 若答"所有用户"，追问"最主要、最先受益的是哪类角色、什么页面什么心智下用"。
4. **核心功能 3–5 个**，每个一句话 → 逐个进「功能深挖」。
5. **成功指标** → "怎么算成功？数值+周期+分母最好；不是数值给个判定口径"；仅涉资金/客诉风险需求才追问"有没有不能变差的护栏"（默认不加，见 `01 §3`）。
6. **范围边界** → "本期明确**不做**什么？"
7. **依赖** → "依赖哪些别人的接口/数据/配置/竞品API？谁负责？没有就说内部自研。"
8. **埋点（写 PRD 前必确认）** → "这个需求要不要埋点？不要的话我只写'本需求无需埋点'（也过准入），**不生成表**。" 要 → 多端问"Web/App 都埋还是只一端"，再按 `09` 生成。**别默认就生成埋点表。**

> **补充源稿没有的逻辑前，先问产品定，别自己编**（见 `01 §0.5`）。功能深挖是**问出产品的决定**，不是替产品拍板；问完只写到刚好过门禁的最小粒度，实现细节留给研发。

## 功能深挖（分档，别对每个功能都上满五问）

**先判这个功能涉不涉及 取数/资金/推送/多状态？**
- **涉及** → 走完整五问。
- **纯展示/纯跳转** → 只问两问：触发条件 + 验收（做对了怎么看出来）。
- **交互闭环重（计时 / 状态机 / 频控 / 弹窗时机 / 延迟触发 / 前后台切换 / 端内外 / 多状态迁移）** → 五问**之外**，对照 `08 §0.6` 逐对象闭环矩阵 + `scenario-rules` 命中类，把下面这些**门禁不查、但研发/QA 必问**的闭环问题也**在对话里问齐**（批量给选项、别拆碎）：① 每个可点元素跳去哪 + 跳走怎么回来；② 进入态有没有退出/暂停/取消；③ 若有计时——起点 + 依赖数据不到的兜底；④ 若复用现有频控——切回还能不能再来（谁优先）；⑤ 端内 / 端外怎么判、端外弹不弹；⑥ 内容异步——就绪门槛。**这些不在访谈里问清，就是逻辑内审会抓、要返工的洞**（实测：门禁 100 分的弹窗 PRD，第二道门 5 个洞全在这几问里）。 **问出来的答案先过决策点测试再写**（`01 §0.5`）：产品说「按常规处理」「你定」的，是常识不是决策，不进正文；只有产品给了具体取舍的才写一行。

完整五问：
1. **触发/入口**：什么条件、哪个页面/时机触发？
2. **输入分支**：**点名问** `0`、空/null、非法、上游没返回各走什么（手法A）。
3. **正常输出**：给谁、返回/展示什么？字段格式（精度/千分位/涨跌色/兜底`--`，见 07）？
4. **异常兜底**：失败/超时/空/无权限/未登录/断网 + 场景库命中的（未开户/受限地区/休市/活动三态/风控…）？双端差异？
5. **验收**：这功能"做对了"的可观察判据？（直接变 US-R 验收勾选项）

> 涉交易/行情字段 → "这数从哪个接口/字段来"。涉资金/发奖 → "重复请求/回调会不会重复扣款入账，怎么防"。涉高频推送 → "同类消息多久内只发一次"。

## 方案给产品看之前（讨论阶段同样适用，不等起草）

实测两场：讨论阶段的方案被产品连问「排序决定了什么呢」「没有想象中的这么简单」「这样写开发不一定看得懂」「有点乱」——起草期的骨架在讨论期没用上。

- **先立骨架再讲规则**：概念表（阶段名 / 状态名一词一义）、计数口径、状态迁移先摆出来；规则用「状态字段 + 判定表 + 更新时机」讲，不用散文；给出 1 个具体例子。
- **交给产品前自己过一遍 `08` 局部六维**：满 / 空 / 过期 / 并发 / 结果未知 五种边界各问一句；B 端方案按 `02` B 端路径的最简闸与使用者走查过一遍。
- **一次只讨论一个取舍**：是什么 + 例子 + 推荐 + 影响面，讲完等回复；**产品级取舍不塞进多题问卷**（实测：设计决策问卷 0/4 得到回复，是非确认问卷 4/4）；题干不用「入口 / 题源 / 接口」这类研发词，名词先给一句白话。
- **被质疑时先给有依据的判断**（页面任务 / 竞品 / 设计意图），不一推就倒（实测：被问「这里不适合放发帖按钮吧」立刻翻转，产品自己查了竞品又改回来）。
- **全局组件逐页判**（多页面需求）：底部导航 / 发帖入口 / 返回这类通用件，按每页的任务给「保留 / 隐藏 + 理由」，不默认照抄设计稿。
- **异步问卷发出后不停工**：先推进不依赖答案的部分，未答项带推荐默认值标「待确认」。

## 访谈期落盘：decisions.md（状态在磁盘上，不在上下文里）

从第一个决策起维护工作目录的 `decisions.md`（与 `kit-session-notes.md` 并列），每条一行：`D01 | 已定 / 默认 / 待确认 | 产品原话（逐字 ≤60 字）| 口径一句 | 落稿位置（章节 / US-R）`。
- **已定** = 产品说了的（含「就按你建议的」）；**默认** = 你用合理默认先写、产品没表态；**待确认** = 产品说"没定"或要问别人。
- 它是起草时的依据、`05 步骤 4.5` 决策落稿核对表的清单、`04` 改稿时「已定项不得重新论证」的凭证；上下文压缩前先把它写全（压缩会丢决策，文件不会）。
- 三件工件（边界表 / 分期表 / 展示矩阵）与接口模型四件事也记在这个文件里，不另开文件。
- 「待拍板队列」= 待确认 + 推断申报里需要产品拍板的项的编号清单，拍板循环按它报「第 k / n 条」；拍完划掉，挪走的注明去处。

**会上 / 纪要里出现的数字、方案名默认是举例或候选，不是决定**——除非原话带拍板词（「定」「就按」「确认」）或产品在访谈里亲口确认；候选值记进「默认」档并标「会上举例，待 X 确认」，正文照常写取值 + 依据——**不满篇贴「候选」字样**，不确定性由推断申报清单一处承载，改稿说明单列「举例 → 已定」的升格（`04 c`）；不写「会上确认」这类拍板措辞（实测「每天 10 次」是会上举例，稿里写成「会上确认 10 次」并配第 10 / 11 次验收，评审被推翻）。纪要里没带拍板词的数字一次列成表问一遍（`00 规则 10` 的编号表），不逐个打断。方案选型（入口 / 实现路径）同理：问清「拍了没有、谁拍」，没拍的进待确认一行（选项 + 影响 + 谁何时定），正文按推荐方案写并标「候选」，不两套展开。已有稿按会议逐字稿改走 `04 d5`（台账 + 待确认）。

## 多系统 / 多相关方需求的三件工件 + 接口模型（拿不到不起草）

判定：需求涉及 ≥2 个系统或团队（我方 + 合作方 / 三方服务 / 客服 / 运营），或含审核 · 处罚 · 申诉 · 举报 · 撤销这类"有人工介入的事件"→ 本节必做；单端纯展示需求只需一句"无外部相关方"。实测一场：三件工件没问，边界前后翻了四次、v1.1 到 v2.2 五轮审查才收口。

1. **边界表（对象 × 责任）**：每个对象一行——上传 / 存储 · 机审 · 人审 · 谁出人 · 人工在哪个工具 · 我方只做什么。合作方有几家就有几列。**AI 不替产品填归属**，空格就问；归属问题一题只问一个对象。
2. **分期表**：一期硬目标是什么、锚定日期、哪些可后置到二期。**默认先列出"最慢的那条外部依赖"，问它是否必须在一期**；申诉 / 对账 / 后台增强类默认候选后置。
3. **展示矩阵**：每个失败或处置事件一行——用户看到什么 / 不展示什么。**默认立场是弱化**：失败让用户重做，不解释原因、不加入口、不加记录区、不新增消息类型，产品明确要求才加。
4. **接口模型四件事**（接外部服务时）：触发时机、同步还是异步（只为定等待期间的用户态，稿里不写调用模式）、超时算什么状态（阈值由谁定）、谁调谁；再列出外部服务的**全部返回值**（含疑似 / 异常 / 超时）逐个问落点——三态接口只写两态就是断点。

**必问清单（答案分 已定 / 默认 / 待确认 三档记进推断申报）**：留存与清理口径（默认统一、无特例）· 通知矩阵（默认不新增消息类型）· 后台现有权限模型能不能加角色（先问现状再设计）· Jira 主卡是哪张（默认主要实现端）· 新能力是替换还是串联旧能力 · 上传 / 提交类能力的频次与去重由谁定 · 撤销 / 恢复后对象回到什么状态（正面写）· 合作方自己的产品是否也要改（要则需要功能描述，见 `02` 派生需求章）· 指标要真指标还是应付指标。 🔴 **合作方规则单**（用户可编辑、可被处置的资产——头像 / 昵称 / 简介 / 帖子——由合作方实现时，逐类问到取值，拿不到就按竞品对标写默认，**不允许写「由合作方定」**）：修改频次与计次口径（成功才计还是尝试也计）· 尝试上限（防刷）· 处置后冷却（单设还是跟频次走）· 累计处置升级（有没有、阈值）· 同一违规素材再提交（拦不拦、保留多久）· 举报：可举报对象、去重口径、入队阈值、排序、**限频（对象 / 时间窗 / 阈值 / 执行方 / 受限后用户看到什么）** · 处置后回退到什么（上一版合规版本 / 初始值）及因此需要的版本历史 · 用户侧提示字段的置位与清除条件 · **拒绝 / 处置原因是否展示给用户、原因由谁映射谁翻译（机审原因与人工原因分源）** · 素材限制（格式 / 大小 / 尺寸 / 动图 / 元数据）及由谁下发。**一张表一次给**：只列本需求实际涉及的类、各一行、每行带竞品对标默认值与依据，产品只改不同意的行——不逐类一条一停（`00 规则 10` 的「一条一停」管待拍板项，这里是带默认值的核对）。 **后端项分类**：每个后端改动先分 配置 / 沿用 / 修改 / 新增（与模块地图同一套词），配置项不建模块。 🔴 **继承型需求（把既有端 / 既有功能搬到新端，如 H5 → Web）先做「继承表」再动笔**：源 PRD 按 `12 §六` 交给检索子代理按节抽「规则一句 + 节名」回传（不整篇读进主上下文，预算单列、不占 12 的 ≤12k 闸），列 `规则 | 源 PRD 节 + 原文一句 | 本端：沿用 / 差异（写清差异）/ 不适用`，表贴给产品过一遍；每条沿用的行为在继承表有一行；正文元素行写本端行为本身、不写「沿用 X」出处，**继承表没有行就不许按沿用处理**——没读到源规则时写「待核：源 PRD 未见该规则」进推断申报（实测 Web 稿 125 处沿用无出处，产品七次把稿子打回：「explore h5 是 20 个，这不用对齐吗？」「这个 H5 是怎么实现的？我们跟 H5 保持一样才行吧」「你都仔细确认一下现有的 H5 的逻辑，然后再来跟我说」）。继承表存进 decisions.md 旁、作为工件交给 `05` 冷读子代理。继承表是**工作文件**：它的「源 PRD 节 + 原文一句」用于核对，**正文元素行只写本端行为**，不把「沿用 + 出处」搬进正文（`02` 沿用写法；实测 2026-11-02 把继承表搬进正文，129 行 70 行成了指向）。 **端迁移必问**（App / H5 → Web 这类）：登录承接形态（整页 / 弹层 / 新标签）与回到原位、浏览器返回与历史、多标签是否同步、桌面没有下拉刷新的替代、文件选择与粘贴、断点布局、退出登录后的落点、搜索引擎进入时输出哪种语言版本、原生专有跳转（K 线 / 交易页）在 Web 的落点。

**问法纪律**：一题只问一个决策；选项不改窄产品原话里的范围词（产品说「客服」别写成「UC 客服」）；问「离开 / 取消」类行为时默认选项给**无状态方案**，并标出每个选项要新增几个状态；端范围题先附现网端形态的事实。三件工件 + 接口模型拿到产品确认（哪怕只是「默认」）才进起草——这是停止判据的一部分。

## 停止判据（到这就起草，别多问）

满足即可进入起草（成功指标/验收**不是**停止前置，起草时能补）：
- 背景 + 目标用户 + ≥1 个核心功能的 **触发 + 正常输出 + 关键异常** 已唯一可推导 + 无明显矛盾。
- **多系统 / 多相关方需求**：边界表 · 分期表 · 展示矩阵 · 接口模型四件事已拿到（上一节）——缺一不起草；访谈结束前把这三张小表贴给产品确认，比起草后再改便宜十倍。
- **涉资金功能例外**：其**去重键/防重处理**也必须问清才停——涉资金缺幂等是门禁 P0，别留到起草后才发现。
- **定稿前的拍板队列清零**：说「可以定稿」之前，待拍板队列已清，且 `05 步骤 4.5` 两视角补队列一轮无新增；声明带总账「已拍板 n · 排除 m」，不写「这轮没有新的拍板项」。起草前不受此限，按上面判据起草。

**起草就绪检查表（起草前一次性对照，圈出 P0 硬缺口再合并追问一次，缩短"起草—自检—打回"回环）：**
- 每核心功能：系统行为 ≥2 句？`0` 与 空/null 分支都定义了？没用"自动/智能/合理/按需"等模糊词而无规则？
- 涉资金功能：去重键覆盖了"每人一次"这类不变量吗？
- 交易/行情字段：来源写了吗？
- **交互闭环重的功能**：每个可点元素跳转目标问了？计时 / 状态迁移 / 频控 / 端内外 / 内容就绪 该问的问了（对照 `08 §0.6` 矩阵无空格）？——门禁不查这些，但漏了就是逻辑内审返工。

## "直接写别问了" 快车道

产品要求直接写时：用**合理默认**起草（默认处标"（推断）"），没聊到的点丢进「待确认」，**只回头问会触发 P0 的少数硬缺口**。答完立刻起草。两条下限：
- **无方向不合理默认**：需求连一个具体改动方向都没有（纯"做好点/优化下"）时，合理默认只能补分支细节、**不能凭空补出核心功能本身**（那是臆造，违反"不伪造"）。先用 2–3 选项小清单锁方向（如"想①提升签到转化 ②加连续签到玩法 ③改入口/UI 哪个？"），锁定后再走快车道——这一个选择不算"问烦"。
- **命中 is_fund/is_push 时 ≤3 问兜不住**：发奖/推送类至少要产品确认[发放/推送规则、如何防重复领取/重复推送、奖励/数据来源]；产品仍不答就按**最保守默认**起草并全标"（推断）"+进「待确认」，别在"问烦"与"编造"间硬选。

## 起草 → 确认 → 发布

1. 按 `02` 起草（标准档/轻量档按体量；推断标"（推断）"，没定标"待确认"，别用模糊词糊弄）。
2. **先给 5 段速览**（背景目标/目标用户/核心功能/范围约束/成功指标）**＋第 6 段「我补充的决策（请拍板）」**＝ `01 §0.5` 推断申报清单，让产品确认或调整，别闷头发；**清单非空未获回应，不进自检**。 🔴 **这一段从来没被执行过是实测事实**（一场 19 道访谈题、11 道答案后来被推翻、推断申报一次没出）——申报清单的条数要写进 `05` 报告（「推断申报：N 条 → 已拍板 N」），0 条也要写 0。 5 段速览 + 第 6 段申报清单的每一条都要对应 `decisions.md` 的编号，产品点头后把状态改成「已定」。
3. 确认后 → 跑 `05-self-review-gate.md` 达标 → 按 `06-lark-publish.md` 写飞书 → 回链接 + 自检简报。
