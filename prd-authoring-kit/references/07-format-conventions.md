# 数字·文案·UI 格式规范（house canon）

> 交易所 PRD 每次都要写、也最容易被 QA 追问的"字段怎么显示"。这一份是可直接套用的口径。`02-prd-template.md` 的元素表「展示规则」指向本文件；写到价格/涨跌/收益/百分比字段时照此写清，能同时满足 house 风格与 `implementation_ambiguity` / `developer_confusion`（消除"显示成什么样"的歧义）。

## 一、数字格式

| 字段类型 | 规则 | 示例 |
|---------|------|------|
| **价格 / 金额** | 千分位；跟随该币种价格精度（无则默认 2 位小数）；**不带正负号**；无数据兜底 `--` | `43,201.50`、`1,234.00` |
| **涨跌 / 盈亏 / 收益率** | **必带 +/- 号**；带 `%`（比率类）；**跟随 App 涨跌色**（涨绿跌红或站点配置，中性场景除外）；精度按 PRD（一般 2 位）；无数据兜底 `--` | `+12.34%`（绿）、`-5.00%`（红） |
| **中性百分比**（胜率/匹配度/占比等，不表示盈亏） | 带 `%`；**不带正负号、不跟涨跌色**（中性色）；精度按 PRD；`--` 兜底 | `68.30%`、`匹配度 92%` |
| **大数缩写 KMBT** | 启用条件由 PRD 指定（一般卡片位、空间受限处）；K=千 M=百万 B=十亿 T=万亿，保留 2 位小数；**缩写后仍保留正负号与涨跌色** | `+1.20M`、`323.45K`、`-2.10B` |
| **时间** | 相对时间（`{N}min`/`{N}h`），超阈值转日期 `MM-DD`；或绝对 `yyyy-MM-dd HH:mm:ss`（标时区）；**分段口径必须完整**（见下方默认口径库，可直接引用） | `3min`、`12h`、`07-05` |
| **杠杆/倍数** | `{N}x`，兜底不展示 | `20x` |

写字段时，一句话把"精度 + 千分位 + 正负号 + 涨跌色 + 兜底值"讲全，例如：
> 30D 收益率：`+/-` 号必带，2 位小数带 `%`，跟随涨跌色，兜底 `--`。

### 分段格式必须给完整口径（研发实测必问，缺了就是返工）

**凡是"展示形态随取值切换"的格式模式**——相对时间（`{N}min`/`{N}h`/`MM-DD`）、KMBT 缩写、百分比精度、滚动窗口（7D/24h/72h）——它的**分段边界、边界归属、取整方向、时区、窗口起点不是实现细节，是产品口径**，研发无法替你决定（实测：只写"相对时间展示，超过 24h 展示 MM-DD"会被研发追问"具体计算规则是怎样的"）。两种合规写法任选：

1. **引用默认口径**（最省）：元素行先写本模块结果，括注来源（如「…（同 MVP）」「…（house 默认精度）」），或把下表抄进「通用显示口径」块，行内只写差异；
2. **自定义**：给全 区间划分 + 边界归属（`=24h` 落哪边）+ 取整方向 + 时区 + 异常值。

**House 默认口径库**（PRD 直接引用即视为写清）：

| 模式 | 默认口径 |
|------|---------|
| 相对时间 | 基准=设备当前时间，差值**向下取整**：不足 1min 按 `1min`；1–59min 展示 `{N}min`；满 60min 起展示 `{N}h`（1–23h）；**满 24h 起**展示 `MM-DD`（设备本地时区）；未来时间戳（时钟偏差）按 `1min` 兜底 |
| KMBT | **≥1,000 起启用**：K=10^3、M=10^6、B=10^9、T=10^12，除后保留 2 位小数**四舍五入**；<1,000 按原数值精度展示 |
| 百分比取整 | 2 位小数**四舍五入**；说明"无需补 0"时 `+5%` 不写成 `+5.00%` |
| 滚动窗口（7D/24h/72h） | 自请求时刻起往前滚动 N 自然小时/日（**非自然日切**）；口径不同须显式写"自然日，以 UTC+X 零点切" |

**长度/数量上限必须写计量单位**并全文统一——字符（UTF-16 码元）/ 码点 / 字形簇（用户感知的"字"，emoji 算 1）；正文写「字符」而配置表写「字」= 前后端按不同算法计数，边界必不一致。（**§二之二 管「上限要不要写」，本条管「上限按什么单位算」**，两条不重叠。）**时间窗类规则**（N 天可见 / N 秒轮询 / N 小时抑制）成套给：**起算字段 + 时区 + 到期瞬间的表现 + 是否需重新请求才生效**。

## 二、UI 词条约定（减少词条歧义）

- **UI 上真实出现的固定文案 / 按钮名 / Tab 名 / 字段名，一律用中文引号「」框出**（如点击「立即跟单」、切到「精选带单员」）。这样研发/QA 一眼分清哪些是界面真字、哪些是描述性语言。
- 🔴 **引号本身就是标记，不再套代码样式**：**禁止**把 UI 文案写成反引号 / `code` 形态（`` `"立即跟单"` ``、`` `立即跟单` ``），也**禁止**用英文引号 `"…"` 包裹——代码样式在 PRD 里的语义是「技术标识」，它们**各有其家**（埋点事件名与属性键在埋点表、错误码在错误码表、i18n key 在 Localisation 表、数据来源指针在元素表「后端说明」列，总纲见 §二之三 节末），把界面真字也染成 code 会让这条区分失效。**权威形态照 `examples/example-copytrading-PASS.md`**（全篇 146 处 UI 词条，零反引号）。机械检查见 `05 步骤0 ⑥`。
- **设计稿是英文时，先译成中文再写进需求逻辑**（Trending→热门、Long/Short→看多/看跌）；正文出现的中文词条 = `Localisation` 表「原文（中文）」列，**英文只出现在本地化表**，不散落正文。
- 动态数值、带单员昵称、后端返回的业务串不算 UI 词条，不用「」框、不进本地化。

## 二之二、产品口径 vs UED 职责（边界条：什么该写、什么一个字都别写）

**「字段怎么显示」是产品口径，「组件长什么样」是 UED 职责。**

- **必写（产品口径，研发/QA 问你你必须能答）**：数据显示口径——千分位、涨跌色、精度、缺失兜底、时间分段（相对时间/KMBT/滚动窗口，见 §一）、UI 词条中文原文（§二）、展示条件与交互闭环。**元素的信息结构与形态也是必写**（「半圆仪表盘 + 中间数值，底色按数值区间取涨跌色」「固定 3 格均分、不可横滑」「卡片可见 2.5 张、可横滑、自动轮播 5 秒」）——研发据此选组件、QA 据此验；像素级样式（色值 / 尺寸 / 圆角 / 间距）才是下面说的 UED 职责（实测 2026-09：kit 稿把形态也省了，产品原话"细节不清晰"）。
- **不写（UED 职责）**：① **组件视觉样式**——颜色值、尺寸、圆角、间距、阴影、字重；② **布局适配**——占宽、横滚、字号、元素排列顺序、响应式断点、**组件自身随内容变宽变高的承接方式**（🔴 点名一条实测二连出的：❌「tab / 按钮 / 组件宽度随文案自适应」——B 端后台 PRD 一次、删徽标的 C 端 PRD 一次，两次都被写进元素表说明格，一律删）。**前提=有 UED 设计稿托底**（C 端常态，设计稿是视觉与布局的权威）。
- 🔴 **别把「内容展示规则」误当布局适配删掉（实测：黄金样例里正是这类 bullet 撑起颗粒度）**：**内容的行数/字数上限与超出处理**（「事件描述最多 3 行，超出截断、末尾省略号」「昵称超 12 字省略」）、**数量上限与超出策略**（「最多展示 5 条，多余不展示/折叠」）、**缺失与异常兜底**——这些**都是产品口径、必写**：研发不知道超长怎么办就搭不对，产品也要为「截到几行」负责。与上条的分界：**内容怎么被裁剪 = 产品口径（写）；组件被内容撑开后页面怎么承接 = UED（不写）**。
- **B 端后台例外（实测误伤）**：管理后台常无 UED 稿（原型=HTML/截图，且非权威）——此时**页面区域划分、每区元素清单与顺序、列表列的截断/兜底格式**是研发搭页面的**产品口径，必写**（按 `02` B 端路径四件套）；仍不写的只剩组件视觉样式（颜色/圆角/间距——house 后台组件库默认）。判别式：**「研发没有这条就搭不出/搭不对页面」=产品口径；「换个颜色圆角不影响验收」=视觉样式**。
- **连「以 UED 设计稿为准」都不必写**——那是默认分工，写了 = 凑行数（实测被产品点名删除）。要指设计稿就放线框/UED 小节的链接，不在需求逻辑里补免责句。
- 判别式：**这条规则变了要不要改需求评审结论？** 要 → 产品口径，写；只影响好不好看、研发照设计稿实现即可 → UED，不写。
- ⚠️ 边界提醒：**免责句不豁免产品决策**——「以 UED 为准」盖不住"这个态到底展不展示"这类口径（见 `01 §0.5` 推断申报闸①）。省的是样式，不是决策。
- 另一条正交的边界见 **§二之三**（产品行为 vs 实现机制）——本节切"谁的职责"，那节切"写到哪一层"。

## 二之三、产品行为 vs 实现机制（🔴 边界条：PRD 写行为，技术方案写机制）

🔴 **核心判据：产品文档写「用户与运营可感知的行为、结果、顺序、上限、兜底表现」；实现机制一律不写。** 研发原话锚（实测：一份 1119 行的后台 PRD，里面有整章 74 行的接口字段契约表）——**"你这个写的是产品需求文档还是技术方案啊"**。写多了不是更严谨，是串岗：技术方案会重写一遍，PRD 里那份注定过期。

> **三条分界不同轴，各管各的（互指一次，别混用）**：`§二之二` 切**产品口径 vs UED 职责**（字段怎么显示 vs 组件长什么样）；`§二之二` 里那条 🔴 再切**内容怎么被裁剪（写）vs 组件被内容撑开后页面怎么承接（不写）**；**本节切产品行为 vs 实现机制（行为写、机制不写）**。三条不冲突也不互相豁免——**本节判"不写"的，动不了前两条判"必写"的内容**。

- ❌ **机制（技术方案职责，不进 PRD）**：
  - **技术形态的接口字段契约表**——一行一字段写 `content_id：ID，必传` 这种**字段名 / 类型 / 必传约束**的表（实测 74 行整章）；🔴 **禁的是技术形态,不是"列信息"本身**——「前端要哪些信息」用业务中文列成表**是产品职责、推荐写**,见下方 ✅「接口信息需求清单」；
  - **错误码枚举散落正文/验收当叙述主语**（「返回 `CURSOR_EXPIRED` 时…」「返回 40301 时…」——正文该写用户看到什么）。🔴 **正文与验收的正确写法 = 「触发情形 → 用户/运营看到的文案与动作」**：「内容已不可见时，提示「内容暂不可用」并回列表」。**正文不写枚举 token 名**——`CURSOR_EXPIRED` / `IDEMPOTENCY_CONFLICT` 这类**大写下划线标识符散在叙述里**，就是替技术方案定契约（实测：24 种 token、31 处，全藏在两章"研发当主角"的 US 里）。🔴 **禁的是散落，不是错误码本身**——**码 → 文案的映射是产品交付物，集中列进「错误码表」**，见下方 ✅「错误码表」条（2026-08 产品明确纠正：错误码、场景与文案属产品范围，要列）。**字段名同理**——`content_id` / `symbol_id` 这类 snake_case（实测 `content_id` ×13），**正文与验收一律用业务中文**（「内容 ID」），要列信息去下方 ✅「接口信息需求清单」。四类豁免：**Data Requirements 埋点表**（`standard_*` 事件名与全部属性键，以 `09 §2 埋点规范`＋`§5 输出埋点表` 为准——house 规范就要求英文）、**错误码表**（表内一码一行，下方 ✅ 条）、**`04 步骤 6` 技术方案对齐后回填的真实 key**（Localisation 的 i18n key `mc_xxx`、配置项总表的 config key——研发已定的终口径）、**下方保护清单第 6 条那 1–3 条数据来源指针**（「字段 `title`，可能为空串」是指针，不是契约）——豁免的是这四处（都是"技术标识在自己的专表里"，总纲见节末**技术标识各有其家**），**不是"只要写在后端说明列就随便写字段名"**；判据看**聚集与叙述主语**（同段/同表冒出一串 token、或拿 token 当句子主语）；
  - **游标 / 快照的内部结构**、翻页 token 怎么生成；
  - **幂等键与 `request_id` 的机制设计**、重试次数与退避参数；
  - **他方服务的消费关系当章节内容**（「XX 服务消费 YY」「由 XX 服务下发」，实测 ×6 个服务）——**系统/管道类需求写「本系统消费什么：格式 / 字段 / 时机」不在此列**，那是业务口径（`02` 管道骨架第 3 条），禁的是替别人写服务架构。
- ✅ **行为（产品口径，必写）**：
  - **行为级幂等**——「重复提交只生效一次，后台提示「已处理」」：**门禁 `crypto_fund_idempotency` 要的就是这句，不是键设计**（口径见 `01 §2`、`02` 幂等表）；
  - **顺序与上限**——「列表按提交时间倒序」「最多展示 50 条，超出不再加载」；
  - **结果与不可逆性**——「删除后列表立即消失且不可恢复」；
  - **错误码表——是产品交付物、要列**（产品 2026-08 明确纠正；交易所惯例：**码 → 用户文案的映射由产品定**，QA 照它验、i18n 照它翻，研发只负责在接口里返回对应的码）。形态：**专表**列 `错误码 | 触发场景 | 用户文案 | 前端动作`（**前端动作可选**；动作简短时并进文案列写成「用户文案与动作」亦可，见范例），**一码一行**（同 `09` 埋点表「一属性一行」）；位置放在「异常与兜底」相关处——**集中一张**（错误码全局统一时）或**按模块各挂一张**（各 US-R 自己的失败情形），按体量选；表里的用户文案**同步进 `Localisation` 表**。🔴 **正文与验收引「场景/文案」、不引码**——码只活在错误码表里（越出这张表就落回 ❌ 那条"散落"）。🔴 **按需列，别硬造**：业务失败情形多、需要研发/QA/i18n 三方对齐文案时才建表；**只有一两种失败就写进「异常与兜底」表**，不为形式凑一张（同 `05 步骤 0 ⑦` 形式主义反查）。🔴 **码名产品定、你别现编**——「该列」不等于「你可以自造 token」：源材料/产品没给码名时，先列 `触发场景 | 用户文案` 两列、**码列留空待回填**（同 `04 步骤 6` 回填真实 i18n key 的路子），凭空编出一串大写 token 照样触 `01 §0.5` 臆造申报闸第 ④ 条。**产品交付的是「有哪些失败情形、各自给用户看什么」，码名是与研发一起敲定的业务契约。****与「异常与兜底」表分工**：异常表管**行为分支**（触发条件 → 系统行为 → 用户提示），错误码表管**码 ↔ 文案的映射**；两者同一条失败**只写一处**（量少并进异常表、量多抽成错误码表后异常表那行只留行为、文案指向错误码表），别两处各定义一遍（同名规则只定义一次，见 `02` 复述上限）；
  - **依赖接口:两档都合规,推荐第二档**——
    1. **占位（达标底线）**：「依赖后端的内容列表接口（待联调确认）」（`01 §0.5` 依赖接口条；coast 门禁 2026-07/08 官方口径：**接口契约细节 = 技术方案职责，占位即通过、缺了不得判 issue**，见 `05 §审查器新版行为` 第 7 条）；
    2. **接口信息需求清单（推荐）——产品给研发提要求：前端要哪些信息，列一列**。放该 US-R 的「后端逻辑」小节（跨方需求按 `02` 后端逻辑「按侧分表」形态：每个数据方一张「模块｜说明」表，其「输出信息」行就是这份清单，另有 筛选与排序 / 数量 / 时效 / 多语言 / 兜底 各一行——那些同样是产品要求，不是机制；单一后端且信息少时两列清单即可）（或量少时并进元素表「后端说明」列），小表两列 `信息 | 说明`，**用业务中文**。例（假设快讯接口）：快讯正文｜来源｜发布时间｜原文链接。🔴 **只列"要什么信息"，不写字段名（`content_id`）、类型（字符串/ID）、必传/可空约束、分页机制**——那些是研发拿着这张清单去设计的东西，写了就越界回 ❌ 首条。
    🔴 **一条信息占一行**（产品 2026-08 点名："信息清单挤在一起一点也不清晰，应该每个字段一行"）——**信息格出现顿号串列** = 拆行：实测负例「内容 ID、状态、类型、作者、正文、图片、提交时间、Cashtag、评论数、点赞数、当前关系态和分页结果」十几项挤一格，读的人根本对不出哪条要哪条。判别式与 `02 §元素行粒度` 的顿号列举机械判别式**同一把尺**（那条切元素行、这条切信息行，两处互指）。列式：基础两列 `信息 | 说明`，**按需**加「来源」「缺失/异常时表现」列；仍业务中文、仍不写类型与必传约束。**反向护栏**：同源同规则、拆开只会把同一句说明抄两遍的一对（「昵称与头像」）可并作一行——拆行是为了看清，不是凑行数（同 `05 步骤 0 ⑤` 反向护栏）。
- 🔴 **保护清单（别矫枉过正——以下六项一条都不许因本节删）**：
  1. **失败态的 UI 行为**（输入保留 / 回滚 / 提示文案）：可感知行为，**必写**（`02` 异常与兜底表）；
  2. **涉资金幂等的行为级要求**（`scenario-rules.md` 那套）：不动；
  3. **B 端管理后台四件套**（`02` B 端路径）：不动——运营可感知的界面口径；
  4. **配置项总表**：不动——运营照它调参，是可感知面；
  5. **埋点表的「是否必传」列**：`09` house 骨架的固有列，**不属于本节说的"字段契约表"**，别误杀；
  6. **元素表「后端说明」列的 1–3 条数据来源指针与职责归属句**（「字段 `title`，可能为空串」「列表接口 `/xxx/list`」「排序与过滤由后端负责」「分页游标由后端下发」）：**那是指针不是机制设计**，`02 §列职责别串台` 明确要求它们写在这一列，保留；本节禁的是**再往下写游标怎么算、字段契约表长什么样**。
- 判别式：**这条信息变了，产品要不要重新拍板 / 运营要不要改操作？** 要 → 行为，写；只影响研发内部怎么实现、**换个实现方式验收一字不改** → 机制，交技术方案。
- 🔴 **技术标识各有其家（本节总纲，四条既有规则的共性收拢——不是第五条特例）**：**字段 / 信息 → 接口信息需求清单**（✅ 上条第二档）；**错误码 → 错误码表**（✅ 上条）；**埋点事件名 / 属性键 → Data Requirements 埋点表**（`09 §2`＋`§5`）；**文案 key → Localisation 表**（`10`，真实 key 在 `04 步骤 6` 回填）。**在自己的专表里 = 合法且应该；散落正文当叙述主语 = 非法。** 判断任何技术标识该不该出现，先问一句「**它在不在自己的家里**」——在，留；不在，要么搬回它的表，要么在正文改写成业务中文 / 用户可感知的说法。🔴 **推论：别再把"某类 token 被写坏"整类禁掉**——三次矫枉过正是同一个形状（内容被截断→禁裁剪→回收内容裁剪；接口被写成契约表→禁列信息→回收信息需求清单；错误码被当叙述主语→禁错误码→回收错误码表）：**X 被写坏 ≠ 禁掉 X**，是把 X 请回它的家。
- ⚠️ **范例与本节冲突时以本节为准**（通用原则，不因某份范例当前合规而失效）。`examples/` 四份**已按本节对齐**（新增 `example-house-insight-tab.md`：后端说明按侧分表，行内只写要求不写实现）：`example-copytrading-PASS.md` 的每个「后端逻辑」都是 ✅ 第二档「接口信息需求清单」（两列 `信息 | 说明` 业务中文小表、一条信息一行），US2-R2 的失败分支是一张标准**错误码表**（`错误码 | 触发场景 | 用户文案与动作`，一码一行；正文与验收只引场景与文案、不引码），幂等写成行为级——**形态可直接照抄**；再撞见字段契约表、或枚举 token **散在正文/验收里**，一律按本节改写（**表内的那几个码是合法示范，别顺手清掉**）。

## 三、措辞与排版禁忌（读起来不像 AI、也更好过审查器）

- **禁用 AI 味词**：值得注意的是、需要指出、综上所述、旨在、赋能、助力、一站式、无缝、确保（改成"要求/必须"）。
- **排版**：正文避免用 `→` 箭头串逻辑、避免 `——` 长破折号、列表项结尾不加分号；用短句和明确主语。
- **只对"真实多取值且处理不同"的字段做分输入域**（0/null/空/非法分开写）；不可能出现的取值一句话收口，别为分域而分域凑篇幅。
- **自造的压缩说法当场展开**：规则里自己造的缩略语（「保留日号」「同距优先未来」「坏卡保序」这类）要么写成完整句，要么紧跟 1 个具体例子——实测一个词扛过 11 轮自检，评审时研发问「这是怎么理解呢」。**压缩句同罪**：删掉主语 / 宾语 / 连接词的四字短句（「保输入」「禁跳」「续办原关注」「写时登录」「直关」「保正文」）读者要二次翻译——写成「失败时保留已输入内容」「点击不跳转」这样主谓宾完整的句子；判据是朗读：评审会上念不顺的句子就是压缩句（实测 2026-11-03 Web 稿「游客举报先登录，成功只回本帖阅读，再点才打开原因」→ 拆成三条 bullet：「游客点「举报」先进入登录」「登录成功后回到本帖阅读位置，不自动打开举报原因」「用户再点一次「举报」才打开原因列表」）。
- **表外不写大段散文**：段落超过 3 行、或一段里含 ≥2 个「；」，拆成列表或小表（`05 步骤 0 ⑫` 机械项）。
- **机器坐标禁裸写**：Figma file key / node-id / 屏号（「屏 334:174081」）是机器坐标，禁止出现在正文任何位置（原型格 / UED 节 / 说明列）。引用设计稿仅两种合法形态：**截图**（优先，`06` 贴图流程）或**可点链接**（锚文本＝「UED 设计稿」或屏名/区块名，坐标只在 URL 里）。

## 四、标准兜底措辞（统一，避免同义不同写触发 internal_consistency 误判）

| 场景 | 统一写法 |
|------|---------|
| 数值缺失 | 展示 `--` |
| 头像/图缺失 | 展示默认图 |
| 某模块整体无数据 | 后端未返回则**不展示该模块**（不占位） |
| 列表为空 | 展示空态，不渲染卡片 |
| 配置为空 / 单条数据缺失 | **隐藏该条**；板块内全部缺失 → 连标题一起隐藏整个板块（不置灰、不占位、不做「可见但不可点」）；要与此不同才问产品 |
| 单字段加载失败 | 该字段 `--`，不阻塞同卡其余字段 |

**用词表（用户侧与后台术语不同的需求必备）**：`概念 | 用户侧用词 | 后台用词`，各列只填一个词，全文照表用——「未通过审核 / 未通过」「处置原因 / 处理原因」「撤销处罚 / 处罚已撤销」这类混用算缺陷；计量单位全文只能一种（字符按码点还是码元、时长按秒还是毫秒，定一个）。

## 五、可读性与 AI 友好排版（强制）

服务两类读者：人要能扫读到单条规则；LLM 审查器不能把同句里的两条规则读成矛盾（internal_consistency / implementation_ambiguity 误判源）。

1. **一格一列表（按需，不是形式指标）**：单元格内 >1 条规则必须用真列表，禁止分号/顿号/破折号串行；**只有一条规则就直接写，别套单条列表壳**。🔴 **组名 / 嵌套 / 有序列表都按需**——≥2 组才加组名、真有主从才嵌套、有先后才用 `<ol>`；**为凑形式硬造的空层次与伪组名，和分号串行同样不合格**（实测：后端说明列被强加「产品规则」组名 174 处）。元素表等需要格内列表的表用**内嵌 HTML 表格**写法——`<table>` 单元格内的 `<ul><li>`/`<ol><li>`（含嵌套）经 `docs +create --doc-format markdown` 导入会 round-trip 成**真正的飞书列表块**（实测，见 `06`）；管道表格里 `<br>`+连字符只是假列表。
   🔴 **覆盖所有列**（说明列、后端说明列、异常列一视同仁）——实测漏症：后端说明列被写成分号串行的一句话。**有层次就嵌套**：主规则一条 `<li>`，它的下属细则在该 `<li>` 内再开一层 `<ul>`（飞书导入后是真缩进列表）；**有先后/优先级用 `<ol>`**。判据：**格内 ≥2 条规则就用列表，每条内不再用「；」拼第二条**。🔴 **一条 bullet 一条规则**：一条规则 = 一个字段 / 控件在一个触发条件下的一个行为；它自己的边界与兜底（缺失显示 --、超长截断）可以用「，」写在同一条；**字段不同或触发不同就拆成两条**，不用「；」或第二句拼接。**条数由规则数决定，不设目标**——拆开后条数变多不是注水，字数变长不回炉（`05` 审计轮次不扩写）。格式 / 阈值类 bullet 带 1 个示例值（「整数，如 "72"」）。机械影子 `prd_lint L48`（复合 bullet 比例）。实测 2026-11-03 Web 稿 43% 的 bullet 是「；」拼接的复合句，研发 / 测试反馈「太长不易读」（样例见 evals E27）。
2. **格内分组：按该元素「实际存在的规则类型」分组，组名自拟、有几组写几组**——不是固定三类。常见组名（按需取用，别硬凑也别只写三个）：展示条件 / 展示规则 / 默认值与选项 / 数量与排序 / 刷新机制 / 交互（点击·滑动·长按）/ 状态与切换 / 计时与轮播 / 字段规则 / 跳转与回流 / 权限与登录态。每组下逐条 bullet（字段类写成 `字段名：格式/兜底`），**每条是一条可实现的具体规则**（❌「支持轮播」→ ✅ 拆成两条 bullet「多于 1 条时自动轮播，间隔 config 可配、默认 5 秒，无限循环」「手动滑动后暂停且不自动恢复，离开 tab 再回来从暂停位置继续」）。🔴 **一个元素只写一句散文 = 颗粒度不合格**（实测：同一份需求，合格样例每元素 2–4 组、每组 2–5 条）。示例见 `02` 元素表；机械自检见 `05 步骤 0`。
3. **散文上限**：正文任何连续散文 ≤3 行，超过转 bullet/编号/小表。
4. **分档必表格化**：数值分档（阈值区间×系数类）必须用小表逐档一行，禁一句话串档（❌ `≤100→×10–20；≤500→×2–5；>500→×1–2` 连写一句）。
5. **流程用编号**：多步流程写 `1) 2) 3)` 编号列表——这是 §三「禁 `→` 箭头串逻辑」的正向替代写法。
6. **通用显示口径块**：US-R 顶部可设 3–5 行「通用显示口径」（数字格式/涨跌色/缺失兜底），**只放跨板块共享的规则**；元素表字段行仍要写自己的形态一句（格式 + 示例值 + 兜底）再引「其余按通用口径」——通用块是防漂移的，不是把字段行抽空的理由（实测 2026-09）。
7. **AI 友好度 = 分层标题 + 具名章节 + 列表化**：审查器先做 SOURCE_FORMAT 判定，不友好会被转写评审并在报告公开标注——直接写成友好格式、跳过转写才稳。
8. **比率/指标公式一律 LaTeX 分式**：`$$率=\frac{分子}{分母}$$` 且分子分母写明统计口径（哪个集合、什么窗口）；禁止"A 占 B 的比例"式文字串（实测用户点名要求公式化+层级化后可读性显著改善）。
9. **跨系统流程步骤句以执行主体开头**：「agent 侧：…」「后台：…」「运营：…」——主语缺失是"这事谁做"误读的直接来源（实测"打标"归属被读反）。
10. **流程配画板导览**：≥4 步的流程/状态流转/多分支判定，配一张原生画板，**由 `scripts/prd_diagram.py` 按 `14-diagram-style.md` 生成**（样式写死：三色、编号、图例、实虚线；AI 只写 spec）；图管全貌、文字管判定规则（唯一权威）。**mermaid 源码与「供 XX 读取」说明句禁止出现在正文**。 **泳道图画法**：系统泳道按系统分道，相关方泳道按相关方分道——**同一相关方只出现一条泳道，系统名写进方框**（按系统分会出现两条 H5、两条 UC，最后一步看似回到起点其实是另一个人）；一页一图、左到右，每条泳道 ≤7 个方框、方框 ≤14 字，步骤编号、分支用 5a / 5b，实线=请求或操作、虚线=结论或事件，人工介入方框与用户可见结果方框在 spec 里标 `kind`，语义色与图例由脚本自动加；跨团队需求再加一张「相关方合作总览」（每条业务线一行、标出人工介入点）——给合作方讲需求只用这一张。 **业务线 = 流程里有动作的参与方**（含人工介入的运营 / 客服 / 审核）；数分 / 测试 / UED 这类交付型支持不是业务线，指标与埋点不是步骤。产品要导出 PDF 外发时，导出后逐图核对，出现加载占位算图没画。 🔴 **图型由 kit 自动选、画完自己先看**（产品 2026-10：「泳道图和流程图等具体图表的选择由 kit 自由决定…主打一个自动化，而不是每次都需要我提醒」）：选型按 §五之二 工具箱表——≥2 系统 → 系统泳道；有人工介入 → 再加相关方泳道；对象多状态 → 状态表（图只做导览）；多条件组合 → 判定表不画图；单系统线性 → 流程图。画完机械自查：一图节点 ≤12、每泳道 ≤7 个方框、交叉边 ≤3、一页一图——超了就拆图或换图型，**不等产品说「画得乌七八糟」再改**。 **≥3 态的状态机画状态图、不写编号列表**（产品原话：「明明可以画一个图」；2 态开关一句话写完，不画）：节点 = 状态，边标「触发与条件」，人工动作在 spec 里标 `by: human`（脚本给条件标签框上人工介入底色）、机器动作默认白底，自环表示状态不变的处理；多条边指向同一终态可合并为一条「任意状态」汇总边（图上合并，决策表与验收仍逐状态列）；画前扫一遍全部写操作入口（前台按钮、后台按钮、定时任务、合作方回调），每个入口对应一条边或自环；图旁保留决策表（输入组合 → 结果），**不再写平行的文字列表**；图下注释只放图里画不了的四类：不变量、窗口规则、图外对象、特殊路径。
11. **元素表列职责别串台**：「说明」列写前端怎么渲染与交互，「后端说明」列写数据来源与后端职责——**排序/筛选/去重/分页游标写进后端列，别写进前端说明**（细则与实测反例见 `02` 元素表指引）。**后端说明格 = 对后端的要求句**（给什么 / 多少 / 何时 / 缺了怎么办）或 `/`；名词短语（「现有评论列表」「既有媒体资源」「帖子关联币种、可用性及行情」）不是要求，删或改成句（实测 2026-11-02 Web 稿 129 格里 80 格名词、29 格只有链接名）。
12. **读者负荷是症状，不是靶子**：研发读不动，先回 `01 §0.5` 决策点测试逐条删常识、再回 `02` 把段落改成规则表——不删字数、不删编写记录（一轮加一行必须保留）。
13. 🔴 **列宽固定（产品 2026-11-03：「表格间距有的宽有的窄」）**：XML 发布路径每张表都写 `<colgroup>`，**同类表同一方案**——元素四列表 `80/140/328/325`；编写记录七列 `54/72/230/84/84/84/90`；二列「项 | 规则」`150/545`；埋点十列 `210/170/145/230/140/130/74/235/210/185`；其它矩阵同用途同方案，短值列（编号 / 枚举 / 是否）≤120、规则 / 说明列最宽。来源：产品本人 H5 PRD 17 张元素表全部同一方案。实测 2026-11-02 Web 稿 30 张元素表 22 种方案、3 种总宽，「元素」列 326 宽装 10 字、「说明」列 213 宽装 148 字。发布后 `lark-cli docs +fetch --doc "<url>" --detail full --doc-format xml > /tmp/doc.xml && python3 <KIT_ROOT>/scripts/table_widths.py /tmp/doc.xml`，报不一致的表回修。标准档（含元素四列表）默认走 XML 路径（列宽 / rowspan / @ 卡片都只有 XML 能写）；markdown 直发只给无元素表的轻量档。

## 五之二、排版工具箱选型表（何时用什么·怎么不滥用）

§五管结构（列表化/表格化/编号/画板），本表管**选型与视觉强调**。总则：**视觉标记是稀缺资源，密度越高信号越弱**——结构承担九成可读性，视觉强调只给「读错会出事故」的词。实测负例：结构齐全但全文加粗 0 处的 PRD，阈值与主体淹没在素文里，扫读无抓手；反过来满篇加粗等于没有加粗。

| 工具 | 该用在 | 禁用负例 | lark 落地 |
|------|--------|---------|----------|
| 管道表格 | ≥2 实体×≥2 属性的对齐信息：概念表/配置项表/口径表/分档表/对接表/「条件-口径-不满足动作」判定表（**"判定+例外动作"混在一句的编号长句，拆成这种三列小表**） | 单列表格（该用列表）；格内长散文 | md 管道表 |
| 内嵌 HTML 表 | 格内需要真列表的元素表 | 无 CLI 降级时禁用（`07 §六`） | `<table>`+`<ul><li>`（§五.1） |
| 画板 | ≥4 步流程/多分支/状态流转的全貌导览 | 承载唯一逻辑；画板旁贴 mermaid 源码 | `prd_diagram.py` 生成（`14`）；mermaid fence 仅无 node 时兜底 |
| 系统泳道图 | ≥2 个系统 / 团队之间的请求与结论流转 | 单系统线性流程硬画泳道 | 画板（`prd_diagram.py` 生成，`14`），按系统分道，密度上限见 §五 第 10 条 |
| 相关方泳道图 | 有人工介入点的流程（审核 / 处罚 / 申诉 / 客服 / 运营介入） | 按系统分道、同一相关方出现两条；把数分 / UED 画成泳道 | 画板（`prd_diagram.py` 生成，`14`），按相关方分道（只画流程里有动作的方），系统名写进方框 |
| 状态表（+ 状态图） | 对象有 ≥3 个状态或有撤销 / 恢复 | 用「通用口径」清单代替 | 表是唯一权威（`02` 状态表指引），图只做导览（`prd_diagram.py` 生成，`14`） |
| 判定表 | 多条件组合（合流 / 优先级 / 分档） | 画成一串菱形的流程图 | 管道表格，输入组合逐行 |
| 编号列表 | 有先后/优先级的步骤与判定 | 无序并列硬编号 | md `1.` |
| 项目符号 | 无序并列（功能点/排除项/依赖） | 有序流程用符号 | md `-` |
| 加粗 | 判定关键词逐点强调：**阈值数值带单位**（30 分钟/3 条/48 小时）、状态名、执行主体（agent 侧/后台/运营）、否定与限定词（不/仅/禁止/至多）、首次定义的实体名 | 整句整段加粗；一个条目/单元格 >2 处、一段 >3 处（全粗=没粗） | md `**`（导入与 `block_replace` 均生效） |
| 导读表 | ≥5 节的长文档开头放「你要做什么｜看哪里」两列表（实测好评） | 短文档硬加 | md 表 |
| 文字颜色 | **仅语义色：红 = 评审之后（或产品点名开始标红后）的改动，产品明说才转黑**（团队评审惯例）；首发稿全黑；已发布未评审稿第一轮问一次「标红还是全黑」、答案逐轮延续、默认全黑（`06` 迭代改稿标红惯例） | 装饰性用色；用颜色编码分类（色盲/打印/AI 都读不到——分类用表格列） | markdown 表达不了；XML text style（block 级，语法读 `lark-doc-xml.md`） |
| 单元格底色/高亮块 | 词级/格级强警示（资金红线、不可回退操作） | 大面积铺底、装饰 | XML 路径；markdown 路径退化为 `>` 引用块+加粗 |

- **视觉标记不进审查可见面**：审查器与下游 AI 读不到粗体/颜色的语义——任何约束**必须在文字本身成立**（"仅 P0"的「仅」要在句子里；"这是新增"不能只靠标红表达）。
- 加粗密度自查：交付前扫一遍，通篇 0 加粗与满篇加粗都打回；每段 ≤3 处、每格 ≤2 处。
- 颜色只承载评审语义一种含义，不做第二用途。

## 六、无 lark-cli 纯文本交付格式（降级专用；与 §五/§五之二 冲突时**本节优先**）

> §五第 1 条的内嵌 HTML `<table>`/`<ul><li>` 是 **lark-cli markdown 导入专用**——无 CLI 时产品是**人肉复制粘贴**进飞书，HTML 标签会原样显示成代码文本、直接翻车。降级交付一律改用：

1. **标准 markdown 表格**（`|` 管道语法）；单元格内多条规则用 `①②③` 编号衔接在同格内（禁 `<br>`、禁内嵌 HTML）；格内仍按规则类型分组（组名自拟，同 §五.2），组间用 `；` 衔接编号重排。
2. 复杂大表（元素表/埋点十列表）保持标准 md 表格整表交付；**经飞书「上传 → 导入为在线文档」(.md) 转为原生表格**（飞书官方不支持 markdown 表格语法，直接粘贴时 `|` 表格可能保持原文本——给用户的操作话术以 `00 §降级` 第3条为准：导入为主、粘贴为兜底）。
3. **流程图照样用 ```mermaid fence 写在 md 里**（无 lark-cli 时的唯一兜底：拿不到画板 token，`prd_diagram.py` 用不上；导入后是飞书默认样式，交付简报里写一句「画板样式待按 `14` 重绘」）——产品经「导入为在线文档」后 fence 自动转为原生画板，代码不残留；粘贴路径下 fence 可能保持文本，**导入路径优先**。
4. **内容标准一个不降**：章节/验收/兜底/幂等照旧齐全——降级改变的只是**载体格式**，不是内容标准；§五的散文≤3行/分档表格化/编号流程等仍适用。
5. 交付前照跑 `06` 步骤 0 的净化口径（去 [必填]/占位符/写作指引），产物是本地 `PRD-<需求名>.md` 文件而非飞书文档；文件开头**不要**写任何"本文件由降级模式生成"之类的元说明（产品要直接导入/粘贴成正式 PRD）。**升级模式例外**：全文 md 仅作对照，用户操作指引以 `04 步骤5` 降级行的「按清单手动改原稿」为准，**勿引导整篇导入/粘贴**（会丢原稿截图/@）。
