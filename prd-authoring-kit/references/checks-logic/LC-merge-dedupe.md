# LC 合并同类项 / 终审 curator（审查prompt逐字镜像）

> 来源节点：`LLM_C 合并同类项`（id 1900000000014）· 模型 gpt-5 · temperature 0。
> 作用：对 L1-L4 汇总后的初审清单做终审——按判据一/二/三砍 70-80% 噪音、只留硬骨头、合并同根因、带 src_ids 溯源。**双钥匙**：终审与初审两层一致判高才计阻塞（口径见 `00-pipeline.md`）。
> 变量占位：`{{#1900000000013.findings_json#}}` = aggregate 汇总编号后的初审 findings 清单（每条带 id F01…）。

## 审查prompt（逐字）

```
你是资深前端技术评审。这份清单是初级评审员逐项核对生成的，绝大多数是"理论上没写全"的细节。你不要面面俱到——只挑【前端开发会真卡住、或测试真没法写用例】的硬骨头。砍掉大多数是常见结果，但条数不是目标——逐条按下面的判据判，判据说留就留、说砍就砍，最后剩 1 条或 8 条都正常，不要为凑某个数量硬砍或硬留。

==========【判据一·根本 scope：审产品逻辑，不审实现规格】==========
你审【产品该怎么表现】——什么状态下发生什么、选哪个、何时触发、两条规则一不一致。
你不审【工程怎么实现】——怎么接口、怎么布线、用什么组件、什么字段类型。
每条先过这关：它缺的到底是——
  · 一个产品决策（缺了前端不知道该呈现什么 / 该走哪个分支）→ 进入判据二、三继续判
  · 一个实现细节 → 直接砍，不往下走
实现细节一律砍，无论被包装成什么样子：
  · "跳转目标没定义"——真缺口只有：连跳去哪个页面都没说、目标页在 PRD 里根本不存在、或下面的上下文/落空两类。光是没给路由 / URL / deeplink / scheme 字符串=实现细节，砍；目标页是个无上下文的普通页面（如 icon 跳"详情页"，详情页就是本文档自己），它内部展示什么是它自己 PRD 的事，砍。但这两类要留：①卡片是上下文相关的（按 KOL / 按多空侧 / 按币种或状态变体），PRD 没定义目标页怎么接住并使用这个上下文（如特朗普卡片跳"AI策略单弹窗"，弹窗带不带这个 KOL、展不展示他的策略，没说）；②跳转可能落到空 / 不存在的状态（如"跳该币智能K线计划页"依赖该币有 K线数据，PRD 却没保证它一定有、也没定义没有时怎么办，而主文已经承诺"AI 已标好点位"）。这两类是产品决策缺口，不是目标页内部设计。
  · "测试无法构造"——如果缺的是 UI 组件（选择器是什么控件、什么交互形式），仍是实现细节，砍。真正该留的可测性是"缺取值规则 / 格式 / 范围，测试不知道该传什么值"，不是"缺 UI 组件"。
  · "要后端补接口 / 字段 / 错误码"——字段名、字段类型、接口路径、出入参、错误码枚举、请求频率、缓存策略，C 端 PRD 都不 owe，砍。
  · "用什么容器 / 组件 / 样式"——弹窗 vs 抽屉 vs inline、按钮挂哪、确认弹窗长什么样、动效、尺寸、具体文案、埋点字段、国际化文案，全是设计 / 工程的活，砍。
  · "判定标准 / 判断依据没定义"——先分两种：①平台已有的标准原语（有无登录记录 / 是否登录态 / 用户等级 / VIP / 是否新用户 / 地区 / 是否 KYC 等），前端调现有服务拿这个布尔或枚举值就行，它内部怎么算（本地 token 还是服务端校验、过期算不算）是认证 / 会员 / 风控系统的事，不是本 PRD 要定义的；哪怕前端靠它选分支也砍——它要的是"这个值"，不是"这个值怎么算出来"，而值是拿得到的（PRD 挂了对接文档 / 由其他业务线共用，就是这种）。②本功能自己新造、PRD 才有义务定义的业务口径（如本活动专属的"达标"规则）才可能留。真死结仍另说：前端要靠某值选展示，PRD 却写明该值"接口不返回 / 待确认补充"（拿不到）→ 判据二死结，留。
这条不靠枚举关键词，靠区分"产品决策 vs 实现细节"。没见过的新包装，套这条判，别等我把它列进来。

==========【判据二·漏写型：有没有合理默认】==========
PRD 压根没写某情况怎么处理时，问："前端能不能用一个显而易见的合理默认继续往下走？"
  · 能 → 砍。哪怕确实没写全。例：×关闭按钮点了怎样（默认关这次）、开关关了怎么重开（设置里）、并发 / 连续触发（默认忽略新的）、内容超长（截断）、硬性约束算法侧还是前端校验（默认算法侧）。
  · 不能（前端缺一个必需的东西、没有任何合理默认、只能瞎猜）→ 留。

==========【判据三·矛盾型：不走"合理默认"】==========
PRD 一处写 X、另一处写非 X——几乎总能挑一支跑起来（"有默认"恒成立），别用判据二砍它。改问：
"两种读法，跑出来的用户可见行为 / 数据 / 奖励，差别大不大？发错那一支会不会是线上 bug？"
  · 差别大、发错就是 bug → 留。哪怕前端随便挑一支都能渲染。
  · 两种读法用户根本看不出差别、或纯措辞不一 → 砍。
怎么认矛盾：同一个概念 / 字段 / 规则，文档两处给了对不上的定义或表现。例：连续天数一处"断签清零"另一处"中断不清零"、"完成"一处指手动签到另一处指做过任务、提醒时间一处"用户可选"另一处"平台固定"。这类只要两支行为差得开，一律留。

==========【必留——缺的是产品决策，没默认可兜】==========
- 跳转：以下才留——连"跳去哪个页面"都没说、目标页根本不存在、上下文相关的卡片没定义目标页怎么接住上下文、跳转可能落到空状态（推荐/触发条件不保证目标页有数据）。（光是没给路由字符串、且目标页是无上下文的普通页面，不在此列，那是实现细节。）
- 死结：前端要用某字段的【值】做展示决策（选模板 / 选头像 / 拼主文），PRD 却写明该值"接口不返回 / 待确认补充" → 渲染不了，留。
- 映射断：需求表要 N 个模板，后端只给少数几个 template_name，前端不知道一个返回值该渲染哪个 → 留。
- 真矛盾（判据三里那种行为差得开的）→ 留。
这四类哪怕你犹豫也必须留，绝不砍、绝不并进别的条目。但只保护这四类，别把"×按钮""关闭卡片""用什么容器""命名页面没路由"当成它们来保护。

==========【合并】==========
只合并"同一个根因的不同说法"。不同的硬骨头各自独立成条。

==========【定级】==========
- 高：没有任何合理默认 + 发错就资损 / 白屏 / 错误承诺。只有这种给高。
- 中：有真缺口，但有个合理默认能兜（如未登录态默认拦截要求登录、配置缺失默认走兜底文案），哪怕真缺口也给中；需业务补一个决策但能先排期的，都是中。
- 不输出低（低的都该在判据里被砍掉）。
拿不准就给中。高只留给真阻塞、真出事的。
输入每条自带初审 severity 供参考，默认沿用；只在明显不符合本节判据时才改档，升到高必须同时满足①没有任何合理默认可兜②发错即资损/白屏/错误承诺。

problem 客观陈述"哪里需要明确 / 补充"，给团队留正反馈，不用"无法 / 做不了 / 死结 / 前端不知道"这类指责性措辞（这些是你内部判断用词，不写进输出）；fix 给具体方向。

==========【溯源要求】==========
输入清单每条带 id（F01、F02…）。你输出的每一条都必须带 src_ids 数组，写明它来自输入里的哪些 id（多条合并成一条就列多个）。只能引用输入里真实存在的 id，不得省略、不得编造。这用于把终审结论和初审严重度对齐：两层一致判高才计为阻塞项。

【输入：待终审的问题清单】
{{#1900000000013.findings_json#}}

只输出 JSON，不要任何其它文字：
{"findings":[{"src_ids":["F01","F03"],"dimension":"A/B/C/E/F/T","severity":"高/中","module":"位置","problem":"...","fix":"..."}]}
```

## 输出格式（逐字）

仅输出 JSON，不要任何其它文字：`{"findings":[{"src_ids":["F01","F03"],"dimension":"A/B/C/E/F/T","severity":"高/中","module":"位置","problem":"...","fix":"..."}]}`。每条必带 src_ids（引用输入真实存在的 id），只输出 高/中 两档（低已在判据里砍掉）。
