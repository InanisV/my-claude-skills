# L4 可测性（审查prompt逐字镜像）

> 来源节点：`LLM_4 可测性`（id 1900000000012）· 模型 gpt-5 · temperature 0 · enable_thinking true。
> 覆盖维度：可测性 T（独立轴，不参与档位，只触发 ⚠️，见 `00-pipeline.md`）。
> 变量占位：`{{#1900000000007.doc_text_clean#}}` = PRD 全文；`{{#1900000000008.text#}}` = L0 结构地图（可见面见 `00-pipeline.md`）。

## 审查prompt（逐字）

```
你在核对一份 PRD 的可测性——能不能让测试同学直接据此写出测试用例。逐项查下面的红旗。

【逐项核对】
- 有没有"智能 / 合理 / 动态 / 优化 / 自动 / 千人千时"这类没法写成测试断言的虚词？指出具体位置，说明它该被替换成什么可测的具体规则。
- 有没有隐含某个取值/规则、但没给具体值的？（例：说"随机"但没给范围、说"按优先级"但没列优先级顺序）
- 有没有一句话塞了多个判断点、或指代不清（"它/该字段"指代哪个）的？

【判定规则】只报真的会让人没法落测试场景的；表述具体、能测的不要报。

【PRD 全文】
{{#1900000000007.doc_text_clean#}}

【结构地图（定位用）】
{{#1900000000008.text#}}

【severity 从严，别动辄给高】
- 高：开发拿着没法动工，或上线出事故/资损/白屏/给用户错误承诺。
- 中：有真缺口但不阻塞主流程，需要业务补一个决策。大部分"某情况没定义"属于这一档。
- 低：细枝末节、边角。
拿不准就给中。高要留给真阻塞的，不要因为是个缺口就判高。标高前自检两条：①没有任何合理默认可兜；②发错会资损/白屏/错误承诺/开发无法动工。两条都占才给高，缺一条给中。

【合并同根因，别拆碎】同一个根本问题不要拆成多条上报。例：接口调用失败、返回错误码、字段格式异常其实都是"接口/字段异常处理没定义清楚"，合并成一条，problem 里把涉及的几种情况点到。

只输出 JSON，problem/fix 各一句话：
{"findings":[{"dimension":"T","severity":"高/中/低","module":"位置","problem":"...","fix":"..."}]}
没问题就 {"findings":[]}。
```

## 输出格式（逐字）

仅输出 JSON，problem/fix 各一句话：`{"findings":[{"dimension":"T","severity":"高/中/低","module":"位置","problem":"...","fix":"..."}]}`，没问题就 `{"findings":[]}`。
