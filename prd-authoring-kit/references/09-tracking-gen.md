# 埋点生成 —— 从 PRD 自动产出埋点表（读线上公参）

> 填 PRD 的 **Data Requirements / 埋点** 章节。源自成熟的「PM 自动埋点填写机 V2.0」，并改成**读线上公参表**（不再硬编码）。产出：**PRD 内一份完整埋点表**（满足 nocode 准入，且是唯一真源）。🔴 **默认不另建子 Sheet**（2026-08 产品定，以 PRD 为准），仅当产品明确要求单独表时才建，见 §6。

## 第 0 步：先确认要不要埋点
**写 PRD 前先问产品**："这个需求要不要埋点？" 不要 → PRD 只写「本需求无需埋点」（过 tracking 豁免、也过准入），**不生成表、不建子表**，本文件后续都跳过。要 → 才走下面流程。别默认就生成。

## 流程
PRD → 抽独立 UI 对象 → 派生曝光/点击 → 匹配标准事件类型（Element/Resource/PageView）→ 挑公参（查线上公参表校验）→ 生成埋点表 → 写进 PRD（默认不建子表）。

## 1. 抽独立 UI 对象（不是每个字段都埋）
**判断法**："如果这个对象消失，从用户视角是少了一个**独立可识别对象**，还是只少了一个**数据/字段**？" 只是少字段 → 不抽。
- ✅ 抽：模块本身、模块下的独立卡片/弹窗/抽屉、有独立点击行为的子区域。
- ❌ 不抽：模块内的标签/文案/数值/图标/走势线/进度条、子展示区、"纯展示不可点"的并列指标、卡片内字段（icon/涨跌幅）。
- **曝光**信号词：展示/显示/出现/默认展示/停留/弹出/浮出/固定在某处/插入某区域/返回时继续显示。
- **点击**信号词：点击/跳转/打开/关闭/进入/查看/领取/报名/参与/确认/提交/切换/展开/收起/拉起。

**强制中间产物（生成表前必做，防成批漏抽）**：先输出「独立 UI 对象清单」中间表——`对象 | 归属模块 | 可点? | 需曝光? | 是否复用现有埋点`，逐对象过上面判断法（清单可不写进 PRD，但生成过程必须先产出，禁止凭印象直接写表）。**这份清单同时是 `08 §0.6` 逻辑闭环矩阵的枚举行——一次枚举、两个镜头（本文件问"埋不埋点"、`08` 问"逻辑闭不闭环"），别枚举两遍。** 随后三条自检，任一不过=漏抽，回去补：
1. 每个可点对象都能映射到**某点击事件的一个 `button_name` 取值**（事件默认合并，见 §5——"有点击"≠"独立事件"）；
2. 每个非过场展示对象都有曝光归属（模块级曝光事件 or 列表项以 `rank`+主体 ID 并入，见 §5）；
3. PRD 需求逻辑里每个交互动词（点击/进入/打开/展开/切换…）都能映射到某点击事件的 button_name 取值，或标「复用现有埋点」。
4. 🔴 **曝光↔点击 维度对称（属性级成对派生，实测漏过）**：对每一对"同对象的曝光 + 点击"事件，把属性分两类——**维度属性**（你会想"按它切分/筛选转化率"的：`rank`/`card_type`/`trade_type`/位置/tab/币种…）**必须两侧都有**；**事件专属属性**（只在一侧有意义：点击的 `button_name`、曝光的 `show_type`/失败原因…）允许单侧。列出「曝光独有」「点击独有」的属性逐个判：曝光有而点击无的**维度**属性 = 按该维度筛的**曝光点击率算不出来**（分母有分子无）= 缺陷，必须**补到另一侧 或 从两侧都删**（产品决定要不要这个切分维度）。**成功指标若要"按 X 筛的转化率"，X 必须同时在曝光和点击。**
5. 🔴 **分析问题清单（与对象清单同时产出，2026-09 实战补）**：每个事件组先写一行 `分析问题 | 口径（分子 / 分母 / 统计单位）| 用到的事件与属性`——答不出「这条埋点回答哪个问题」的事件不建；答得出但**分母事件不存在**的（条件渲染的按钮、入口、提示胶囊），先补分母曝光再建点击。这张清单是 §5.5 三视角复核的输入，也直接进 PRD 埋点章末尾的「指标与数据来源」小表（`分析问题 | 口径 | 事件与边界`）。

**对象清单收尾做「归属审计」（2026-08 实战补）**：每个对象终态五选一——新增埋点 / 已被 PageView 覆盖 / 后端事实数据（查表得到）/ 复用既有埋点 / 不采集（写理由）。没有归属的对象就是漏抽；"页面上有控件"本身不构成埋点理由，每个事件都要对得上 §1 的一个分析问题。

## 2. 埋点规范（公司口径）
- **状态参数化**：点赞/已点赞、关注/已关注、登录/未登录、有持仓/无持仓 → **抽一个对象**，用状态公参区分（如 `is_in_login_status`/`is_havefutureposition`），**不要为状态变化抽多个事件**。
- **公共组件统一上报**：弹窗、确认/取消按钮等公共组件由公共组件层统一上报，不在每页再抽一遍；疑似公共组件 → 标"建议复用现有埋点"。
- **不必要曝光不埋**：纯过场动画、loading、转场页、系统 toast、模块内微小展示元素 默认不抽。
- **单报不多报**：同一行为不因模块层级被多次上报；父子都抽时用 `module_name = "父-子"` 区分（element_name 不写进 module_name）。注意 `module_name` 是概念名，落表用真实键（本环境=`module`，见 §4）。
- **可区分维度必带**：每个 Element 事件必须带 module 级区分维度（模块名属性），保证全表内任意两个同名标准事件都能靠属性组合唯一区分；点击对象再带 `button_name` 等元素标识（无任何区分属性的事件落地后数据无法按对象回收）。
- **CTA 不能漏、但不单独建事件**：模块内可见 CTA（"立即…/去…/领取…"）必须成为该模块点击事件里一个独立的 `button_name` 取值（即便整卡已可点，整卡与 CTA 是两个取值）；事件层面并入同模块点击事件（见 §5 合并规则）。
- 🔴 **事件级维度单值（埋点产品 2026-09 明确要求，实测被打回两次）**：一个事件里 `module`、`page_description`（页面描述属性；原 `page_name`，平台 2026-09-17 改名）只能各有**一个固定值**，不许在属性值格写 `A / B` 让研发按情况选——跨模块、跨页面就拆成独立事件（Feed 页 / 我的主页各一条发帖入口曝光；For You / Following 各一条帖子曝光）。**曝光按「页面 + 独立对象」拆**，不同对象的曝光不写进同一条。`button_name` / `rank` / `message_type` 这类**元素级枚举**仍可多取值。
- 🔴 **页面归属按研发的页面清单，一条事件只属一个页面（平台 2026-09-17 起事件卡有「页面名称」单选下拉）**：页面 = 路由级，取值只从研发提供的页面 / 路由清单里选；页内 tab、弹窗、抽屉、编辑器**不是页面**，归到宿主路由，用 `module` / tab 类属性区分（实测：For You 与 Following 同属 Feed 页；评论编辑器归帖子详情页，仍用 `module` 区分编辑器曝光）。同一个点击对象出现在多个页面（「关注」按钮在详情页 / 主页 / 关系列表都有）→ **按页面拆成多条**，各条保留同一套 `button_name` / `source` 口径，拆出的每条都要配图。清单里没有精确项（如 APP 原生入口，而清单只列了 H5 页）→ **问产品选最接近的一项**，不自创、不留空。这个页面值同时写进 PRD 表事件组首行的「备注」列（`§5`），两端才对得上数。
- **结果查表，过程埋点**：后端能查到「结果」（帖子已发布、关注已建立、举报已提交）不等于可以省掉「过程」（入口曝光 / 入口点击 / 提交意图 / 主动放弃 / 前置拦截）——过程只有前端看得见；反过来，**能通过主键查表得到的属性不上报**（被关注人查关注记录、作者类型由 `content_id` 关联），只上报对象主键。
- **隐私默认**：不上报正文、答案原文、目标用户 ID；只报 option_key / 主键 / 类型。
- **技术字段不进产品埋点**：`fail_reason` / `is_success` / `result` 这类失败原因、成功与否进日志监控；业务结果以后端事实数据为准，不在产品埋点里重复回收。
- 🔴 **H5 需求的 APP 宿主入口也要埋**（tab 曝光 / 点击、下拉二楼、推送落地等）——标端 APP、写进同一张表；否则漏斗没有顶部（实测 2026-09 被埋点产品补回）。手势触发、SDK 采不到自动曝光的对象（下拉二楼等）由研发按点击事件类型手动上报，备注列写明；借点击类型报曝光时，「曝光」与「真实进入」用两个固定 `button_name` 取值分开（如 `xxx_exposure` / `xxx_enter`），说明里写清「算曝光时纳入、算真实点击时排除」，别让兼容事件混进点击量。
- **页面停留时长不自建事件，复用 SDK 预置事件**：采集 SDK（神策）自带 `$WebPageLeave` + `$event_duration`。只是顺带一提 → 说明列注一句即可；**要单独回收某一页的时长**（发帖编辑器这类看「投入 / 流失」的页）→ 表里和平台上各占一条：事件类型选 `$WebPageLeave`，属性只配 `$event_duration`（NUMBER，秒）+ `url_path`（SDK 页面路径，按路径识别是哪一页）；**SDK 预置事件不带 `jira_id` / `module` / `page_description`**——那是 `standard_` 事件的东西（实测配了 `page_name` 被埋点产品改回 `url_path`）。口径写在触发时机里：前台可见开始计时，隐藏 / 离开 / 切后台 / 锁屏时上报本段新增秒数，恢复后另起一段，同一结束信号去重，只报 >0 的分段；「指标与数据来源」小表按用户累计看均值与分位数，**不拿分段均值冒充一次访问时长**。
- **标识取值用固定值**：`button_name` 等区分维度的取值用代码枚举 / 固定中文短语，**不取界面上的动态文案**（会随语言、状态变，研发实测点名）。对象的类型 / 种类用独立枚举属性区分（通知类型走 `message_type`，不是把通知正文塞进 `button_name`）——研发对某条字段提疑问时，通常只需改固定值和说明，不需要加事件或加字段。
- 🔴 **生成前先做既有埋点复用对照**（实测两场：重复建了 4 条帖卡事件 / 底部 tab 入口已有埋点又建）：拉前序 / 兄弟需求的埋点（PRD 埋点章或平台历史页），列表与卡片沿用旧事件用 `source` / `tab` 区分；必现元素（每个专区都有的胶囊）随页面曝光不单建；公共入口（底栏 / 发帖按钮）沿用旧事件；跨需求同一事件统一枚举值。
- **运营可配置对象（热点 / 活动 / 话题）同报「稳定 ID + 中文名」**（后端下发、前端上报）——是「查表得到不上报」的例外：只报编号，数分取数还要映射。**漏斗默认按分步 UV 转化率看**，不为"同一次流程"新增流程标识字段，要加先问产品。

## 3. 标准事件类型（6 种）与 Element vs Resource
| 事件 | 英文 | 用于 |
|---|---|---|
| 页面浏览 | `standard_PageView` | 新页面/新路由/整页改造/tab 型升级（**只加模块/弹窗/按钮不需要**） |
| 元素曝光/点击 | `standard_ElementExposure` / `standard_ElementClick` | 前端硬编码 UI、业务接口数据驱动的模块/按钮/卡片 |
| 资源位曝光/点击 | `standard_ResourceExposure` / `standard_ResourceClick` | **运营后台物料**（banner/活动/push/站内信/CMS 配置） |
| 资源位曝光失败 | `standard_ResourceFailResult` | Resource 且 PRD 写了"未展示/被过滤/兜底/接口异常不展示"场景 |

**Element vs Resource 关键判断**：内容来自**运营物料系统**（活动/Banner/CMS 管理）→ Resource；来自**业务数据接口**（行情/合约/订单/AI）→ Element。**即便后端能控位置/数量/上下架，只要内容本身是业务数据 → 仍是 Element**。产品功能弹窗(确认/引导)=Element；运营活动弹窗(后台下发)=Resource。

## 4. 公参：查**线上**公参表校验（不硬编码、不编造）
线上公参字典（一次配置，随线上变化）：
- 坐标在公司配置 `tracking.base_token` / `tracking.table_id`（`python3 scripts/company_config.py get tracking`；由 `npx pm-ai-kit config <链接>` 导入）。坐标是资源定位符而非凭据——调 API 另需本人 lark 授权、表仅公司租户可访问；2.1 起不随公开包分发。
- **没有公司配置或访问不了才降级**（无权限/非公司环境）：改用 ①环境变量 `LARK_TRACKING_BASE_URL` ②用户在对话里给过的公参表链接；都没有 → **跳过线上校验、不阻塞交付**——属性名按本节命名规范自查，交付简报注一句"公参未线上校验，请埋点同学过一眼属性名"。**绝不编造属性名。**
- 表结构：事件属性表
- 字段：`name`(公参英文键) / `cname`(中文名/说明) / `data_type`(STRING|NUMBER|BOOL|DATETIME|LIST)。共约 1574 条，是**全局公参词典**（校验 + 中文 + 类型来源），**不含"是否必传"、不含事件↔参数映射**。

**用法**（先读 `lark-cli skills read lark-base` 拿准命令；查询而非全量拉，全量 ~2.6s/页很慢）：
- 每个事件挑 **0–5 个真正相关**的公参（>5 只取最相关 5 个）；依据事件的 `module_name/element_name` 语义。
- 每个要用的公参，**必须在公参表 `name` 里逐字存在**（区分大小写）→ 查表校验；用 `cname` 作中文列、`data_type` 作类型。**查不到就不用、不编造**。
- **本文凡写 `module_name` 均为概念名**：落表前必须查公参表用逐字命中的真实键——本环境线上公参表**没有 `module_name`，真实键是 `module`（模块名称）**；常用真实键还有 `element_name`、`button_name`、`page_description`（页面描述；**原 `page_name`，平台 2026-09-17 改名，旧键已不在字典里**）、`trade_type`（交易类型，可作开仓/平仓等状态参数化）、`rank`（排序，列表项序号从 1 起）、`jira_id`；`url_path`（SDK 页面路径）只给 `$WebPageLeave` 这类 SDK 预置事件用。**字典键会改名**：录入前在平台字典里再核一次，键名以字典当前为准，别照抄本文。
- **SDK 自动带的通用环境字段不要列**（`is_in_login_status`/`platform_type`/`user_id`/device/session/version/timestamp 之类）。
- 看不到明确语义信号就不推；**宁可少，不可多**。标注（过审样例惯例）：**「是否必传」列只写 是/否**；不确定的取值在「属性值」或「备注」列标 `【待确认】`、公参推荐标 `【公参推荐】`——标注不进必传列。
- 🔴 **录入平台时以平台属性字典为准**（`§8`）：键在字典里不存在 → **先找同义键**（实测 `symbol_id` 不在，字典里是 `token`(币种标识)），别在平台里写「待补属性」占位；同义键也没有 → 先问「能不能查表得到」，能 → 不上报；确实要新增 → 找埋点产品在字典登记后再录，PRD 表里标 `【待字典登记】`。

示例查询（以 lark-base skill 实际命令为准）：按 `name` 精确/模糊查这批候选公参，返回 `cname`/`data_type`，只保留命中的。

## 5. 输出埋点表（10 列，过审样例校准口径）
```
| 触发时机 | 事件名称英文 | 事件名称 | 事件说明 | 事件属性英文 | 事件属性说明 | 是否必传 | 属性值 | 页面截图 | 备注 |
```
- 同一事件多属性 → 多行；事件级列（触发时机/事件名/说明/截图/备注）只在该事件组**首行**填，后续行留空（Lark 友好）。
- 🔴 **每个属性独立一行/独立 `<tr>`（铁律，markdown 与 XML 两条路径都适用）**：无论 markdown 表还是 XML block 手写表，一个属性一行；**严禁把多个属性用 `；`/`/`/换行 挤进同一个「事件属性英文」或「属性值」单元格**（`/` 只允许用于**同一属性**的多取值枚举，见下方「格内写法」）。自查：`<tr>` 数 = 1 表头 + 属性总数（6 事件 25 属性 = 26 个 `<tr>`，不是 7 行）。**XML block 手写路径最易塌成「一事件一行」**（markdown 导入天然多行不会塌），block_replace/insert 埋点表前务必按此数核对。
- **点击合并（默认动作，过审样例惯例）**：同一卡片/同一模块上的**所有可点区域合并为一个点击事件**，用 `button_name` 取值区分（整卡、子区域、CTA、icon 各是一个取值）；🔴 **只在同一 `module` 内合并**——跨模块不合并（`module` 单值铁律，见 §2）；语义差异大的对象即使同模块也分组。**禁止**为同卡的每个按钮各建一个事件。
- **曝光合并**：模块级曝光一个事件；**列表项/卡片项不单独建曝光事件**——并入该曝光事件，用 `rank`（序号，从 1 起，**分页列表跨页连续编号**——第 2 页首项=第 1 页末项+1，说明列写明）+ 主体 ID（strategy_id/trader_id 等）逐项上报。**同一对象出现在新页面 = 升级老事件，不新建**（产品 2026-10 点名「对老的埋点做了一个升级，而不是新增埋点」）：事件名、字段、必传与原版逐项一致，只扩 `page_description` 的取值 / 加一个 `source` 类来源字段；平台要求一事件一页面时，同一事件按页面各登记一条，但**不起同名新事件、不顺手改老字段**——各页，共享同一套 `rank` / 主体 ID 口径；同一页面上不同对象的曝光也各一条（页面 + 独立对象）。
- **每个 `standard_` 事件必带 `jira_id` 属性**（是否必传=是，属性值=**主卡卡号**——主卡 = 主要实现端的故事：App 内 H5 的需求是 WEB/H5 卡、APP 需求是【Flutter】卡（原生双端包时取 iOS 卡）；全端只用这一个号，如 APP-34744）——埋点与需求单挂钩追溯，过审硬惯例；**公共属性（jira_id / module / 平台）可在表前一行声明一次、表内不逐事件重复**（`§5` 格内写法；录平台时按声明补到每张卡）；`$WebPageLeave` 这类 SDK 预置事件例外（`§2` 时长条），不带。
- **PageView 一页一条**：`standard_PageView` 带 `jira_id` + `page_description`（**单值**；页面其它维度由采集 SDK 自动上报），有对象主键的详情页再带主键（帖子详情带 `content_id`）；**不做多页面共用一条 PV**（实测被埋点产品打回：页面不可多选一）。
- **格内写法**：「事件属性英文」列一格永远只有一个键（❌ 禁：`card_type / strategy_id`）；`/` 拼只用于**同一属性的多取值枚举**（如 button_name 的取值列）；属性值列用"代码枚举（中文注释）"或中文短语可读值，以与研发实现一致为准。 **公共属性表前一行声明、表内不逐事件重复**：`公共属性：jira_id=<主卡>（全部事件必传）；module 由数分定值；平台 WEB`——录平台时按声明补到每张事件卡（`§8`）；表里只列事件特有属性，行数减半。
- 🔴 **属性说明四要素**（产品实测「挺好的」并要求推广到全表）：每个属性写清 **何时上报 / 取值从哪来 / 何时必传 / 不传 = 不携带**（不填空串、不沿用上一页的值）——只罗列字段名研发看不懂「什么时候用、上报什么」。
- **触发时机写清开始 / 结束 / 去重**：PV 首次展示算不算、切 Tab 是否重报、同一流程只报一次还是每步各报。**端只分 WEB / APP**（不按 iOS / Android 拆事件）；**`jira_id` 同一需求全端只用一个号**（优先 Flutter 主卡 → iOS → Android），不按端分写。
- **是否必传只写 是/否**；【待确认】/【公参推荐】标注放「属性值」或「备注」列。
- 🔴 **`module` 属性保留、取值留空，由数据产品定值**（产品 2026-09/10 两场明确：「按照最新的要求就应该要置空」「module 这个字段应该都要空着，是数据产品来写，不是我们直接写的。所有的埋点都是这样」——它推翻了此前「module 用中文」的口径）：十列表里 `module` 行照列、是否必传照填，「属性值」格写「由数分定值」，录平台时留空；`page_description` 照旧单值。其余照旧：事件名与属性键是英文（`standard_ElementClick` / `element_name` / `button_name`），`button_name` 等取值用代码枚举（中文注释）或中文短语。🔴 **英文键只活在这张埋点表里**——正文与验收不散落事件名 / 属性键。
- **截图列**：具备截图能力时（来源与编排见 `06` 元素表「原型」格贴图），埋点对象的截图**与该 US-R 原型图同源复用**——同一张 PNG **重新 `media-insert` 一次**拿新 token 插进 PRD 内埋点表截图列（🔴 禁止 `<img src="<旧token>">` 复用——垃圾图红线，见 `06`）；产品要求另建子表时，子表截图列写「见 PRD 埋点表」即可（sheet 单元格插图不在本流程）。不具备截图能力则该列留空或写「/」。 🔴 **每条事件都要有图，且要清晰**——用 `06` ⓪ 的 Figma 原生导出或原型图裁剪，别用模糊截屏（实测 17 条配图被产品整批打回重传）。
- **数量 sanity 看链路不看条数**：核心链路每个节点各一条、每个点击率有匹配分母 → 条数随页面数与对象数走（实测：一个多页面 H5 一期 29 条合理，压到 11 条就把发帖链路打断了）；明显多出来的通常是没有分析问题的辅助页 PV 和纯操作按钮，用 §5.5 三视角判，别以「减条数」为目标先删再说。
- **复用的公共组件**（弹窗/现有流程/一键下单等）：不重复抽，在表下补一行「复用现有埋点」说明，并与对应负责人确认入口来源参数（如 `source=xxx`）可透传。
- **备注列固定写「端 + 页面名称」**（事件组首行）：`平台：WEB；页面名称：<研发页面清单里的名字>`；多端需求逐条标 Web/App/H5，或统一注"双端均实现"（对齐 tracking_platform_clarity）。十列不加列——页面名称是平台事件卡的单选字段（`§2` 页面归属），住备注列即可，PRD 与平台按它逐条对数。
- **口径别自相矛盾**：某状态（如"兜底/失败曝光"）若只是主曝光事件的一个 `show_type` 值，指标**整体口径**要以主事件的**维度**为准回收；"专项监控"事件在说明里写清"是 X 事件 show_type=Y 的子集，不代表整体口径"（实测被扣完整性分）。

## 5.5 三视角复核（删前、录前必做——防过抽，也防过删）

🔴 **调整既有埋点表 = 变更**：先出「补 / 删 / 改」三列清单等产品确认，再回写（`04 §需求变更` 同款，不批量改表）。

实测锚（2026-09 广场一期）：36 条按「后端能查到结果的都删」压到 11 条，发帖按钮点击率都拿不到；再按三视角逐条复查，恢复 11 条、补 7 条必要节点，定稿 29 条。**先定分析问题，再决定条数；不要以减少数量为目标。**

| 视角 | 问自己 | 典型结论 |
|---|---|---|
| **资深产品** | 阅读 / 创作 / 讨论 / 关系 这几条关键路径，每一步都有节点吗？（入口曝光 → 入口点击 → 编辑器访问 → 按钮可用 → 点击提交 → 后端接收 → 审核发布） | 提交意图、主动放弃、前置拦截只有前端能看见，必须留；资料维护类辅助页不进本期 |
| **业务运营** | 供给 / 消费 / 互动 / 关系 / 回访 / 反馈 六类都能观察吗？能区分「没人尝试」「尝试了没成」「成了没过审」吗？ | 发帖尝试、作者探索、新内容提示响应要留；举报量、粉丝数这类结果查业务表 |
| **数据分析** | 每个点击率有匹配分母吗（曝光与点击按 module / page / tab 对齐，条件渲染的按钮要有自己的曝光，不能用整页 PV 代替）？UV / 次数 / 业务记录数有没有混除？结果与过程分开了吗？ | 为关键点击补配对曝光；接收成功与审核发布分开；能查表的属性不上报 |
| **冗余探针（与防过删同等力度）** | 答不出 §1 分析问题的过程事件、同一步骤被两条事件记录、可随页面曝光的必现元素单建的曝光、公共入口的重复事件 → 删。产品要求「精简」时也**先出三视角表再删**，删曝光要证明对应的点击率不再需要；条数来回（20→8→15）就是没先定分析问题 | 一场实测 36→11→29，另一场 20→8→15——先定问题再定条数 |

三视角各出一张 `事件 | 保留 / 删除 / 新增 | 理由` 表再合并；结论**写进交付简报**，PRD 只留最终表与「指标与数据来源」小表。

## 6. 写回 PRD（默认不建子表，满足 nocode 准入 + 单一真源）
1. **PRD 内（唯一必做）**：把埋点表写进 `Data Requirements` 章节（结构扫描器 + tracking_* 四项要看到具名章节和逐条诉求）。**PRD 内表 = §5 十列格式一字不改**（列名、列序、逐属性多行、组首行规则全部适用）：禁自造列、禁把多个属性用 `/` 拼进一格；「页面截图」列 md 阶段可写「见设计稿」占位。**本表不是摘要，是完整表、以 PRD 为准**。 🔴 **埋点章表外文字 ≤400 字**：平台链接一句 + 「指标与数据来源」小表 + 公共属性声明一行，到此为止；**搜索流程定义、转化计算方法、统计单位、页面识别核验这类分析方法不进 PRD**（进平台需求页说明或数分文档）——被投诉稿埋点章 6.9k 字里有 1.5k 是这类散文，研发看不懂也不需要。
2. 🔴 **默认不建子 Sheet**（2026-08 产品定）：埋点表直接写在 PRD 里，研发/数据同学看 PRD 即可，**不再默认另建表、也不留「见 Lark Sheet」占位行**。别顺手建了再问。
3. **仅当产品明确要求单独表时才建**（可选路径）：用 `lark-sheets`（`lark-cli skills read lark-sheets`）新建电子表格（标题如 `<PRD名>-埋点表`）写入同一张十列表 → 可选挂成 PRD 子页 `lark-cli drive +move --file-token <sheet_token> --type sheet --folder-token <PRD docx token>`（需 `space:document:move` scope）→ 链接贴回 `Data Requirements` 章节，并保证两处逐行一致。**实测两个坑**：① 该 scope 可能被租户管理员禁用（授权页会提示、增量授权返回"新授予 scopes：空"，别反复重试）；② `sheets +workbook-create --folder-token <docx token>` 不行——create API 只认真文件夹（报 1310204 folder token not exist）。API 路被禁时**降级为指导产品手动挂**：飞书云文档里对该 Sheet 点 ⋯ →「移动到」→ 选中 PRD 文档（用户 UI 操作不受 app scope 限制）。
4. **无 lark-cli（降级）**：第 3 步本就不做——埋点表**只进 PRD 正文**（十列格式不变，用 `07 §六` 标准 md 表格），**不因降级砍列砍行**。**§4 的查表校验同步降级**：只使用 §4 已列出的本环境验证过的真实键（`module`/`element_name`/`button_name`/`page_description`/`trade_type`/`rank`/`jira_id`）；其余候选公参照写进表格、但在属性说明列标注「待确认·装 lark-cli 后校验」——**不因查不了表就编造键名，也不砍 jira_id/module 等必带项**。「装 lark-cli 后可校验公参」这类话**只说在对话交付简报里，不写进 md 正文**（产品要直接导入成正式 PRD）。

## 7. 反编造（贯穿）
- 事件：不把纯文案/字段误判成按钮；不把动画/进度条/倒计时当埋点对象；不输出重复对象。
- 公参：只用公参表里真实存在的键；有语义信号才推；不复述 SDK 自动字段；不编造属性名/取值。
- 声明豁免：确实无埋点诉求 → PRD 写"本需求无需埋点"（`05` tracking_* 直接通过），不硬凑。

## 8. 录入公司埋点平台（产品要求时；实测 2026-09 广场一期，五轮返工的教训）

平台：`{{company.tracking.platform_url}}/ai-tracking/<需求 id>`（`python3 <KIT_ROOT>/scripts/company_config.py get tracking.platform_url` 取前缀；埋点产品建好需求页后给链接）。**录入是 PRD 之外的独立交付环节**，用平台自带浏览器工具操作（产品要求即可做；**不用桌面级 computer use / 截屏自动化**，公司 2026-09-08 安全通告禁用）。

1. **先做 §5.5 三视角复核、再录**——先录后拆 / 后删返工最贵（实测 14 → 17 → 22 → 36 → 11 → 29 五轮）。
2. **字段映射（PRD 十列 → 平台事件卡）**：`事件名称` → 中文名称*；`事件名称英文` → 事件类型下拉（曝光 / 点击 / 页面浏览，SDK 预置事件如 `$WebPageLeave` 也在里面）；端 → 下拉只有 **WEB / APP**（H5 归 WEB，并在说明里写「由 H5 实现」）；备注列的页面名称 → **「页面名称」单选下拉**（2026-09-17 起；候选来自研发页面清单，没有精确项就问产品选最接近的一项，每条都必须选、不留空）；`事件说明` → 「这个埋点是做什么的」（写分析用途，不写触发）；`触发时机` → 「描述：侧重上报逻辑，点击 X 后 / 接口 Y 成功返回后」；每个属性 → 「新增属性」从**平台字典**选键（`§4` 同义键规则）+ 描述（中文名）+ 说明（取值枚举 / 何时必传）+ 必传开关；`页面截图` → 图片附件，**每条事件至少一张高清图**（浏览器扩展上传本地文件要先由用户开「允许访问文件网址」，AI 只给步骤）。
3. **`module` 留空、`page_description` 单值、「页面名称」单选**在平台里是硬约束——录入前按 `§2` 拆好，别录成 `A / B`；同一对象跨页面的按页面各登记一条但沿用老事件名（`§2` 复用优先）；页面名称从研发页面清单里选**最接近的已有项**，清单没有的在备注写真实页面。
4. **只保存草稿，不代产品点「提交审核」**。
5. **回读校验**：刷新后按卡片数出 `事件数 / 属性数 / 空字段数 / 图片数 / 端全为 WEB(或 APP)? / 页面名称为空的条数（应为 0）`，与 PRD 表逐项对数，差异逐条修；字段改过名就再 grep 一次旧键（平台与 PRD 各一次，应为 0）；拆分出来的新条目逐条看有没有图。
6. **双向对齐**：平台改了什么，PRD 埋点表同步改（编写记录加一行版本）；PRD 改了什么，平台同步——两边都以 `§5` 十列为唯一口径，不允许「平台拆开了、PRD 还是合并的」。 **平台已录入的条目就是基线**：录入之后 PRD 再改，先拉平台现状对齐，条数以平台为准同步回 PRD，不在 PRD 里另起一版。 **录入后把平台需求页链接贴进 PRD 埋点章**（一句「平台登记：<链接>」）。**平台 AI 自动生成的草稿不算人工改动、不当基线**（实测照搬了平台自动拆的 iOS / Android 两条）。
   - **两端条数对不上先问、不自动补**：平台比 PRD 少的条目，先问产品「是主动删的吗」——是 → PRD 同步删；**删一条事件要连带清理依赖它的口径**：用它作分母的点击率改口径（没有入口曝光就不算按钮 CTR，改看点击量与到达量）、说明里「研发需补报 X」的旧话删掉、「指标与数据来源」小表同步改——不能只删表行。
   - **平台上的人工改动优先**：埋点产品 / 研发直接在平台上改过的条目（换事件类型、换属性键、改固定值）是最新真相，同步前先 diff 平台现状与本地上一版，**保留人工改动、PRD 向平台对齐**，不用本地旧版 plan 覆盖回去。
   - **平台字段改名**（属性键或字段标签变了，如 `page_name` → `page_description`）：两端全量替换——属性键、属性说明、事件说明里的引用一起换，回读 grep 旧键 = 0 才算完；PRD 编写记录加一行版本说明改名。
