# 项目群同步消息 Skill

## 这是什么，先分清和 ego-messenger 的边界

同步消息不是"写给谁看"，是**给一整个团队立一份共识记录**。它会被跨职能同事、可能还有 leader 一起看到，事后还会被翻出来当依据。所以它的基调和 ego-messenger 完全相反：

- **ego-messenger**：1v1 经营关系，暖、带飞书表情、有敬称、目的是让 E 哥心情好 + 觉得你靠谱。
- **group-sync（本 skill）**：面向全群，**中性、克制、像会议纪要**，目的是把"定了什么 + 接下来谁做什么"钉清楚，顺带把该拍的板抬上去。

判断用哪个：这条消息是**给团队留记录 / 立共识**（用本 skill），还是**在向老板汇报或说服他拍某个方案**（用 ego-messenger）。如果一条消息两个目的都有，主受众是全群就用本 skill，主受众是 E 哥就用 ego-messenger。

**本 skill 覆盖四类场景，骨架不同、方法论共用**：
- **会后同步**：一次会的结论 + 待办。骨架是「已确认 + 待办」，见下面「消息结构」。
- **项目周报**：一个项目的周期性状态快照。骨架是「负责人 + 本周进展 + 推进中 + 风险 + 关键节点」，见「场景二：项目周报」。
- **回应业务方案**：业务侧发了方案要产品支持，产品在群里给时间线、对账诉求、设议程、约会。骨架是「规划和时间线 + 方案里的产品支持 + 会上需要讨论的内容 + 邀约」，见「场景三」。这一类对方可能借你的话挖坑，规则最多。
- **阶段状态同步**：leader 让把当前数据表现和接下来的产品规划一起发群里。骨架是「数据对基线 + 产品侧动作 + 规划逐项按阶段口径」，见「场景四」。

四类共用同一套政治分寸、语言格式、组装流程。下面先讲会后同步（标配），再讲周报，再讲回应业务方案，最后讲阶段状态同步。

## 核心原则

1. **结论先行，两块为主：已确认 + 待办**。别人扫一眼就知道定了啥、自己要做啥。中间视情况加一块"待对齐 / 待拍板"。
2. **群里有 leader 和跨团队，政治分寸是第一位的**。不评价人、不甩内情、把分歧中性化、把该拍的板抬给该拍的人。这一条最容易翻车，单开一节讲。
3. **忠于会上和事实**。会上没定的别写成已定，自己额外加的项要么标出来、要么先问 Noah。
4. **可扫读，不写墙**。编号分节，一条一句，别堆长段。

## 消息结构

### 标配骨架（大多数同步就这三段）

```
[抬头一句：今天和谁对齐了什么，同步结论和待办。]

一、已确认
1. ……
2. ……

二、待办
1. ……
2. ……

cc @相关人 @leader
```

### 可选中段：待对齐 / 待拍板

有**分歧**或**需要别人拍板**的事，才加这一块，放在"已确认"和"待办"之间。没有就不加，别硬凑。

```
二、待对齐 / 待拍板
1. [分歧点]：[A 方观点]，[B 方观点]，[下一步怎么收敛]。
2. [需拍板项]：[要定什么]，[谁来定]。
```

### 各块怎么写

- **已确认**：编号。每条是一件**已经定了的事**，一句话说清，别展开论证（论证是会上的事，纪要只记结论）。
- **待办**：编号，**动词开头**（确定 / 梳理 / 罗列 / 输出 / 评估），简洁。要不要写负责人看场合：需要问责、认领的写`（负责人）`；纯轻量同步可以不写，让它简洁。
- **待对齐 / 待拍板**：**中性陈述双方**，不站队、不开撕。把"需要谁拍板"点出来。

## 场景二：项目周报

周报和会后同步是两回事。会后同步是**一次会的结论**，周报是**一个项目一周的状态快照**，每周固定发。骨架不同，但政治分寸、格式、组装流程完全共用。

### 周报骨架（固定五块，每周照填）

```
[抬头一句：X 项目第 N 期周报，同步本周进展、推进、风险、节点。]

一、负责人（仅首期，或有变动时才列）
1. [模块]：@人
……

二、本周进展
1. [已经做完、有产出的事]
……

三、推进中
1. [在做、还没完的事]，@负责人
……

四、风险项
1. [客观风险 + 影响]
……

五、关键节点
1. [日期] [事项]
……

[可选结尾：一句心气 / 团队感的话]

cc @相关人 @leader
```

### 五块各怎么写

**负责人：只首期列，之后不列**。首期周报兼当「分工确认」，把「遇到问题该找谁」钉清楚，之后每周不再重复，除非分工有变动。列的时候按模块分（产品 / 设计 / 技术方案 / 项管 / 研发），一模块一人或一组。

**本周进展 vs 推进中：必须分开，这是周报最容易失真的地方。**

| | 放哪块 | 判断标准 |
|---|---|---|
| 拉会评审、定了选型、功能定稿、发了文档 | **本周进展** | 已经**做完、有产出**的事 |
| 需求还在写、UI 还在设计、方案还在做 | **推进中** | 还**没完、在做**的事 |

- 把「在做还没完的」写进「本周进展」，是虚报，回头交付不出来打脸。
- 一件事这周做完了就进进展，没做完就进推进中，别含糊。
- 进展条目动词用完成式（完成了、确定了、定了）；推进中条目挂负责人 @，让人知道谁在跟。
- 进展宁可写实不写满：某件事其实只是「初步讨论」没定死，就写「初步讨论了 X，需要 Y」，别写成「定了 X」。忠于事实比好看重要。

**风险项：分清是「同步周知」还是「要人解决」，写法不同。**

- **同步周知型**（只想让大家知道有这么个风险，不逼谁解决）：客观陈述风险 + 影响，不带「需要谁协调」的指向，不点人。
- **要人解决型**（想让 leader 出手）：按政治分寸那节的「成本显性化」，把影响和需要的动作摆出来，@ 到能拍板的人。

**同步周知型风险有个反直觉的坑：删掉归因会让风险「悬空」，反而害了自己。** 只报「前端资源紧、影响 Q3」不说为什么紧，leader 扫到会猜「是不是你们自己没规划好人力」。给一句**客观原因**（不点人、不带情绪）其实是**保护自己**，说明这是客观调配不是项目自己的锅。

| 写法 | 问题 / 效果 |
|---|---|
| ❌ "前端一半人被抽去做 Flutter 了" | 归因太具体、带情绪，像甩锅某个决策 |
| ❌ "前端资源紧缺，影响 Q3"（完全不给原因） | 风险悬空，leader 可能误以为是项目自己没规划好 |
| ✅ "前端资源紧缺，受 App 整体人力规划影响，可能成为最长路径，影响 Q3" | 说明是客观规划所致，不点人、不甩锅，保护自己 |

**关键节点：只列日期 + 事项**，一行一个，不展开。让群里对时间线有共识。

### 周报的结尾抒情句（可选，但很容易翻车）

第一期或阶段性周报，Noah 有时想在结尾放一句话表达团队心气（比如引曾国藩「扎硬寨打呆仗」）。这句话用好了提气，用不好就说教 + 官腔。三条经验：

**1. 讲「自己的感受」，不要「教大家怎么做」。** 结尾是发个人感慨、带个头，不是布置团队该怎么干。「广场这个项目不追风口、要慢慢把内容做扎实」——这是在教大家做事，说教。改成「最近看到 X，挺有感触」——一人称的感受，不说教。

**2. 别用泄气或端着的词。** 引了个硬气的典（扎硬寨打呆仗），后半句用「绵力推进」自我消解，气就泄了（「绵力」是自谦力量微薄，显得没底气）。反过来「一仗一仗往下打」又太军事化、端着。落点要在**踏实、有韧劲、有温度**，不悲情也不逞强。

**3. Ealy 会扫的群里，基调要「稳」不要「悲」。** 风险项里已经客观报过困难了，结尾别再哭一遍「困难重重」，要落在「我们有心气、沉得住」。

- ✅ 参考："最近看到曾国藩说的扎硬寨打呆仗，挺有感触。资源紧、难处多，那我们就沉下心把每件事做扎实，不着急、不取巧，和大家一起往前走。"

**表情符号**：纯会后同步纪要建议零表情（见格式节）。但**周报**这种带阶段总结、想给团队一点温度的场景，结尾配一个暖表情（如 SendingLove）是可以的，Noah 自己的风格说了算。功能性说明句（如「遇到问题找谁」）后面别硬配表情，会出戏。

## 场景三：回应业务方案，给时间线、设议程

**什么时候是这个场景**：业务侧（运营 / SEO / 商务）在协作群里发了一份方案，里面点名"产品需要支持 A、B"，群里 cc 了老板。senior 产品让你"整理一下当前功能规划的上线时间线，然后约个会"。这条消息是产品第一次公开接这份方案，会被当依据翻出来，所以它和纪要一样是记录，但多一层：对方可能借你写的每一句话挖坑。

**先分清两件事**：对方的方案要不要做、优先级怎么调，不在这条消息里定，也不在业务会上定，那是有老板在的场合（周会之类）的事。这条消息只做三件事：把当前有日期的东西摆出来，把对方的诉求逐项对账，把会上要讨论的问题列全。leader 说"不着急、按自己节奏来、别为他们改"，指的是不为对方改优先级，不是不回复。对方的诉求（时间线、订会）要当天正面回，读过头就变成不接话。

**三关逐句过**（每写一句都问）：
1. 这句是不是在回对方要的东西（时间线、会议）。
2. 这句是不是产品在陈述自己的判断，而不是在解释困难。
3. 对方读到，会觉得产品在接他的方案，还是在设防。

### 骨架

```
@提要求的人 @发方案的人 [抬头一句用对方的原话：X 当前的功能规划和时间线整理如下，方案里提到的 N 项产品支持也一起说一下，方便会上大家对复杂度和周期有个预估。]

一、规划和时间线
1. [版本 / 需求]，[状态口径]。[一句说清用户拿到什么]
2. ……
N. 再往后的版本产品这边也有规划，会在 [有老板在的场合] 详细同步。

二、方案里的 N 项产品支持
1. [诉求 A]：已有 / 在某个需求里一起做 / 还没进评估，加上进评估的前提。
2. ……

三、会上需要讨论的内容
1. ……（一条一件事，不贴责任标签）

[邀约 + 时间 + 一句客气话]
cc @参会人 @leader
```

### 十条写法规则（每条都是踩过的坑）

1. **时间线只写有评审或上线时间的东西**。没日期的不进时间线。
2. **再往后的版本只写一句"产品这边也有规划，X 场合详细同步"**。指向场合，不列功能。列了功能会被追三句：那规划给我看看、产品有规划运营不参与决策吗、那我提的能不能排进去。也不能写"等数据出来再排"，那等于告诉对方产品没规划，拱手让人。
3. **每项只写它当前阶段对应的那一个口径**：已上线写日期，开发中写目标日期，评审前写"需求 X 评审，评审完出排期"，评审完写"排期中"。不写还没有的上线日期、不写"待排期"（被动）、不写实现方式（前端写死还是动后端，说了都是诉苦）。
4. **上线日期有滑动风险**：写"目标 X，具体日期本周和研发确认后再同步"。新日期不在业务群首发，先项目群和 leader。
5. **只写已评审、在评审的需求本身**。不编"我们的规划正好能接住对方目标"这种连线（比如"项目方内容会聚合在币种页"），规划里没有的不能写成有。
6. **对方诉求逐项对账，只有三种状态**：已有、在某个需求里一起做、还没进评估加上进评估的前提（认证给谁、怎么审先定，定了产品再评估排期）。不写"分两步""二期做"，那是替没立项的事排版本，谁也没授权。
7. **对方目标当前版本承接不了的**（如项目方入驻，一期账号能力和普通用户一致），不写"一期怎么进来"，写成"需要的能力会上明确，作为后续版本规划的输入"。认账要规划，不承诺当前能进。
8. **议程段一条一件事，书面口径，不贴"运营侧定 / 会上共同定"标签，不写"由谁输出"这种模棱两可的话**。责任靠内容分，谁有信息谁自然接。对方诉求里属于规则、资质、责任方、法务的问题要列全（如认证体系就是认证对象、资质审核标准与流程、审核责任方、法务意见），对方自己会看到这是他们要补的。
9. **不在业务群里提内部物料**（规划表、研发工作量、实现方式），除非是指向场合。评审遗留事项（如头像人审归属）可以在评审完之后单独补一条，不混进时间线。
10. **结尾两种收法**：邀约 + 时间 + 一句客气话（"欢迎各位大佬参会"），或"结论我会后发群里"（谁写纪要谁定口径）。不写"看是否符合预期，有调整我会后更新"，对方会读成"不合我们预期就改"，带着清单来。

### 发前反读：坐到对方椅子上

把自己换成发方案的人，逐句问"这句我能接什么话"。能接出下面任何一句的，删或改：
- 那规划给我看看。
- 产品有规划，我们不参与决策吗。
- 那我提的能不能排进去。
- 既然 X 能做，Y 为什么不能（拿你写的某个能力反推他的诉求）。
- 你说以后做，以后是什么时候。

### 示例：回业务方案，给时间线、约会（最终发出去的版本）

```
@Vivien L @Bob Ban 广场当前的功能规划和时间线整理如下，方案里提到的两项产品支持也一起说一下，方便会上大家对复杂度和周期有个预估。
一、规划和时间线

1. 广场1.0，目标 9/23 上线，具体日期本周和研发确认后再同步。App 内 H5，推荐和关注两个流，发帖（文字、图片、cashtag 点了直接进 K 线页）、评论、点赞、关注、个人主页、消息通知、翻译，冷启动内容由 AI 账号提供，审核后台一起上。
2. 币种页圈子，需求今天评审，评审完出排期。用户搜一个币或者点热门币种，就能看到这个币的全部帖子，页面顶部有行情和交易入口。
3. MEXC 官方账号，需求明天评审，评审完出排期。一个官方主账号，有认证标识和专属头像，上线后负责运营的团队可以直接登录账号发帖，也可以在运营后台发。
4. 再往后的版本产品这边也有规划，会在本周五的周会上和大家详细同步

二、方案里的两项产品支持

1. 用户页面：1.0 已经有了，头像、昵称、注册年限、关注和粉丝数、帖子列表都有。

## 场景四：leader 让在群里同步阶段状态，数据加接下来的规划

**什么时候是这个场景**：leader 让把"当前的数据表现"和"接下来大的产品规划"一起发到业务协作群或项目群，群里有 E 哥、业务 leader 和运营。典型触发点：放量后、上线后、一个里程碑之后，或者老板问了"现在什么情况、接下来做什么"。和场景三的区别：不是回对方的方案，是产品主动立一份"现状 + 规划"的记录。leader 点名要列方向，所以方向可以列，但每一项只写它当前阶段的口径（口径规则沿用场景三第 3 条）。

### 骨架

```
[抬头一句：接着上次 X 的同步，把 Y 之后的数据和接下来的产品规划一起同步一下。]

一、数据（写清截至哪天、哪个阶段）
1. 量级对基线：核心量级，和上次同步里写的预计值或目标对照。
2. 最该看的一个转化数（如入口点击率），加一句现状（如发帖、互动）。
3. 产品侧动作：只列产品自己的行动项。数据有口径或埋点上的 caveat，一句带过。
4. 下次评估或节点的日期，和谁一起定。

二、接下来的产品规划
1. 开发中：……（有排期的写目标日期）
2. 评审中 / 设计中：……
3. 大方向逐项，一项一行，只写当前阶段口径。

cc @leader @业务侧
```

### 六条规则

1. **每次阶段同步里埋一个下次能核对的数**（预计值、目标值或评估日）。下一次就能写"和上次预计一致"或"差多少"，比干报数有说服力，老板也看到产品在用自己的预期管进度。没有上次的基线，就把这次的数写明作为基线。
2. **数据标截至日期和口径**（哪个看板、哪段时间）。数字从对话、看板分析或周会材料里取，标好日期让 Noah 刷新，不留空（Noah 原话：不要空在那里）。
3. **一块数据放三个左右**：量级、一个转化数、一句现状。老板扫的是量级和对不对得上预期，更多的数字放周会文档，不放群。
4. **弱数据如实写，后面紧跟产品侧动作**，读起来是"看到了，在做"。只列产品自己的动作，不写"要靠产品"或"要靠谁"，运营的空间留给运营，他们也可以做活动。
5. **规划每项只写当前阶段的口径**，和场景三第 3 条一致：开发中写"目标 M/D"，评审中写目标版本或时间窗，需求梳理中、设计中、方案设计中不带日期。新方向一句大白话加一个例子，收在"方案出来后在 X 场合同步"。
6. **方向的"为什么"只写一句能力关系**（这个能力是哪件事的前置），不列还没方案的子项，不写实现方式。

### 示例：放量后的数据加季度规划（发业务协作群，E 哥在群里）

```
接着 10/12 的放量同步，把 50% 放量后的数据和接下来的产品规划一起同步一下。

一、放量后的数据（截至 10/15 的看板，50% 放量后一周）
1. 广场页面日均访问约 2.4k 人，和放量前预计的 2,000 人左右一致，线上稳定。
2. 入口：首页广场 tab 每天约 14 万到 15 万人看到，点击率 1.1%。进来之后看帖和互动的比例还低，发帖以 Persona 账号为主，真人发帖和互动量还小。
3. 产品侧动作：先做更细节的新功能引导，需求已列入待办，广场分享接着排。发帖和互动相关的埋点上周修复，这周数据补齐后一起看。
4. 下次评估 10/26，和内容运营侧一起按 50% 这两周的数据定全量时间。

二、接下来的产品规划
1. 开发中：币种搜索与币种帖子页。股票 Meme 专区，目标 11/11 上线。
2. 评审中：自定义头像与图片审核，目标 11 月中旬随全量上线。
3. 话题：需求梳理中。用户可以按话题看帖和讨论，也是预测市场投票和活动话题投放的前置能力。
4. 广场 Web 端：设计稿 10/22 出，评审后出排期。
5. 交易即内容：把用户的交易动作变成广场内容，比如订单分享带交易卡片，产品方案设计中，方案出来后在周会同步。

cc @Yoki Xu @Bob Ban @Kay T @Vivien L
```

几个点：第一块第 1 条能写"一致"，是因为上一次放量同步里先写了"预计日均曝光 2,000 人左右"，这就是规则 1。规划里只有股票 Meme 专区有上线日期，其他各写各的阶段，币种搜索开发中不带日期，Web 端只有设计稿日期。交易即内容只有一句大白话和一个例子，没展开成清单。

## 场景五：配图发群（业务协作群的日更，字只讲图上没有的）

**什么时候是这个场景**：Noah 把业务协作群当成自己的运营渠道在跑，每天给老板们发一条，一条一个重点（10/26 全量，10/27 数据加规划，再往后上线日历），每条都配一张 mexc-infographic 出的图。群里有 E 哥、Jackie、Bob、Kay、Yoki。和场景四的区别：图已经把数字、问题、解法、日期都讲了，文字只负责图讲不到的四件事。这个场景的口吻比纪要轻，是 Noah 自己在群里说话的样子。

### 骨架

```
[开头一句：同步一下 X 的数据～ / 昨天大家都挺关注 X 的，这块我们是……]

1. 一句成绩（带那个最好的数），顺手夸一下
2. 一句口径（这个指标怎么看，接下来看什么，下一个节点什么时候）
3. 一句指向图（问题和动作都在图里👇），最后半句放唯一需要别人出手的事

（第二条，配规划图）
1. 产品这边，……
2. 运营这边，@运营负责人 他们会……
3. 另外 X 我们也一直在调，……[FistBump]

cc @leader @业务侧
```

### 八条规则

1. **文字只讲图上没有的**：结论、往哪看、下一个节点、唯一的请求。数字、三行问题解法、日期全在图里，文字里不重复（Noah："很多细节就不用在文字里面讲，让他们看图就可以了"）。
2. **好消息开头，顺手自夸一句**："看得出大家对广场还是挺有兴趣的"，不写"用户是愿意来的"这种像判词的总结句。
3. **参考指标先定口径再给数**：点击率这种不代表产品表现的数，文字里写"我们只当参考，广场主要是刷着看的"，再说真正要看的指标和它什么时候能看到。不然掉一点老板就慌。
4. **唯一的请求放最后一点的最后半句**：读到底正好看到，不会被前面的数淹掉。写法是"需求已经评审过了，但后端现在只有一个同学在做别的高优需求，暂时排不上，这块可能需要协调一下人力"：已就绪、卡在哪、要什么，三件事一句话，留一点余地。要软一点就不点人数："排在后端现有高优需求之后，人力到位就能开工"。
5. **请求要不要 @ 到人，Noah 定**：@ 研发负责人能落到人，但当着老板的面有可能让他下不来台；不 @ 就交给 cc 里的 leader 去接。
6. **两条连发**：数据图那条先发，规划图那条一分钟内跟上，坏数字不在群里单独挂着。cc 只放在后一条，把团队拉去看解法，不是拉去看问题。
7. **运营要写进正文**：规划图那条把运营负责人 @ 在正文里（"是跟 @Kay T 一起对过的"），只放 cc 是知会，放正文是公开说这条线是她的。KOL 来源这类替运营写的细节，发前让她先看一眼。
8. **分点但不像 AI**：开头一句，空一行，1、2、3 各一件事，每点是完整的口语句子，用"产品这边，……"开头，不用"标题：内容"的冒号格式，不对仗，末尾再空一行放 cc。

### 这个场景的格式例外

下面"语言与格式"那节是纪要的规范。日更这条不是纪要，照 Noah 自己在这个群里的样子来：
- 开头可以用"同步一下～"，指图用 👇，结尾可以带一个飞书表情代码（[FistBump] [PartyPopper]），一条最多一个。
- 句末不用句号，一点之内用逗号把一整件事串下来。
- 分点用 1. 2. 3.，不用一、二、三。

### 示例：10/27 数据加规划两条（最终发出去的版本）

第一条，配数据图：
```
同步一下广场截至 10/25 的数据～

1. 同样是 50% 放量，第二周的访问人数比第一周涨了 34%，大家对广场还是挺有兴趣的
2. 点击率我们只当参考，广场主要是刷着看的，后面重点看发帖、讨论和停留时长，这几个指标今天跟数分对过了，预计周五上看板

## 政治分寸（重灾区，群里有 leader）

这是本 skill 最容易翻车、也最值钱的部分。同步消息是**公开记录**，一句话说重了，得罪的是整个协作方，还会被 leader 记在账上。

### 五条铁律

**1. 不评价人、不甩内情**

Noah 私下的判断（比如"开发信不过自己的 AI、不想担责"、"某团队在推诿"），**绝对不进消息**。群里一放，就成了当众杠人，对 Noah 只有坏处。

| 私下能说 | 群里怎么写 |
|---|---|
| ❌ "开发信不过自己的 AI，想甩锅才要人审" | ✅ "审核采用 AI 加人审兜底。当前 AI 审核准确率大概在 60% 到 70%，前期保留人审。" |
| ❌ "我们巡检 agent 人力不够只能求人" | ✅ "这块正好在找现成能力，不想重复造。" |
| ❌ "市场部根本没把广场当回事" | 不写。只记客观进展和待办。 |

**2. 分歧中性化，别在群里论输赢**

有分歧时，用一句话把双方立场摆平，写清"下一步怎么收敛"，不在消息里替谁定输赢。

- ✅ "巡检 agent 还有分歧。开发建议在审核环节一并处理、当前人力不足；产品认为有独立价值，先找其他团队看有没有现成能力可复用，再定。"
- 如果不想在群里显得和开发顶，甚至可以把分歧**压成一句话带过**："agent 团队新增一个审核 agent。巡检 agent 还有分歧，产品这边再评估。"

**3. 决策抬上去，靠"成本显性化"而不是靠吵**

想让 leader / 相关方拍板某件事，别在群里论证"这事该归谁"，而是把它**列成待拍板项 / 待办**，把资源和责任明明白白摆出来。成本一旦显性化，该掂量的人自然会掂量，不用 Noah 点破。需要谁拍就 **@ 谁**，姿态克制、留余地。

- ✅ "其中审核人力来源和业务后端归属这两块需要尽快定责任方，辛苦 @Ealy 帮忙拍一下。"

**4. 立场要不要亮：两种基调，让 Noah 选**

同一份纪要，两种写法，对应不同意图。写之前先判断 / 先问 Noah 想要哪种：

| 基调 | 什么时候用 | 怎么写 |
|---|---|---|
| **中性纪要** | 不想在群里和谁顶、或分歧还没到摊牌的时候 | 六点都落成结论 / 待对齐 / 待办，不替产品表态，把分歧放"待对齐"里让它自己说话 |
| **带产品立场** | 想把产品的判断和该拍的板钉进记录里 | 同样骨架，但在分歧点上把产品倾向讲出来（讲价值、讲成本，**不评价对方**），结尾点名 leader 拍板 |

亮立场时也要**克制**：只讲"为什么这样对两边都好 / 成本在哪"，绝不评价对方的动机或能力。

**5. 忠于事实**

会上没讨论的项，不要偷偷塞进"已确认"。如果 Noah 需要补一个会上没提但确实该做的待办（比如某个前置清单），**标出来是新增的、或者先问一句**，别让纪要失真。

## 语言与格式（Noah 硬规范）

同步消息的输出严格守这些，和 Noah 所有对外文字一致：

- **不用 emoji**。这是记录不是 1v1 寒暄，表情会显得不严肃。（这点和 ego-messenger 相反，别搞混。）
- **完整句子 + 完整标点**。不用空格切碎成短片段。
- **不用破折号「——」当分隔符**，不用正文分号「；」，该断就用逗号句号。
- **不用 filler**：赋能、综上所述、确保、旨在、值得注意。
- **AI 味词也不用**：承载、供给、接住、打通、先说结论、进一步。对方用什么词就用什么词（对方说 timeline 就写时间线，不写节奏）。群消息里的大白话是对的："审核后台一起上""点了直接进 K 线页""搜一个币或者点热门币种"。
- **极少加粗**，最多标数字或关键结论，不堆叠。
- **编号分节**（一、二、三 + 1. 2. 3.）。**群里用编号列表，不用表格**（飞书 / lark 聊天里表格渲染差，纪要用列表更稳）。
- **数字用 KMBT**，百分比直接写（如 60% 到 70%，不写 60–70% 那种容易和破折号混的）。
- **末尾 cc @相关人**，涉及要拍板的再 @ 上 leader。

## 去 AI 味（2026-10-27 加，所有场景出稿前都过一遍）

方法来自三处：GitHub 上的 humanizer（按维基百科"Signs of AI writing"整理，支持拿本人文字做口吻校准）、它的中文版 humanizer-cn（避免二元对比和戏剧性分段、长短句混用、两项比三项自然、金句重写）、以及中文工具 ra-人话 列的几种"壳"。落到群消息上就是下面这些。

### 一眼就是 AI 的东西，不出现

- **冒号讲义腔**："产品把交易变成内容：……""重点是：……"。改成普通句子，"产品这边，……"。
- **两行对仗、三项排比**："产品把交易变成内容 / 运营把内容做成生态"并排就是模板。要并列就两项，而且各说各的话。
- **金句收尾**："平时不太看得到，但一直在做""当作长期主线来做"。听着能被引用的句子就重写成事实。
- **数据后面跟一句判词**："用户是愿意来的""说明……"。要夸就口语化地夸："大家对广场还是挺有兴趣的"。
- **数字框架**："三个问题和对应的解法"。图里有数的，文字里说"问题和动作都在图里"。
- **壳**："不是 A，而是 B""其实""本质上""核心在于""更重要的是""归根结底"。
- **每行长度一样、每行都是完整的漂亮句**。

### 怎么写得像 Noah

拿他自己写的当样本。10/26 他回 Bob 的那条："嗯嗯bob哥产品基建这边，我和 Kay T 一直在保持同步，是在按照运营要求的优先级推进的，当前的开发重点在web端，但是话题的方案我们也会尽快推进起来，后续会先行推进设计[FistBump]"。特点：
- 一整件事用逗号串下来，不分点、不用冒号
- 常用"这边""目前""后续会""一直在""先……再……"
- 做完的事用完成时说："已经跟数分对过了""是跟 Kay 一起对过的"
- 结尾一个飞书表情代码
- 要人力这种话留余地："这块可能需要协调一下人力"

### 出稿前最后扫一遍

- [ ] 没有冒号起头的小标题，没有对仗的两行，没有三项排比
- [ ] 没有"不是…而是""其实""更重要的是""本质上"
- [ ] 结尾不是金句，是事实或请求
- [ ] 长短句混着，至少一句口语连接（"另外""其中""这块"）
- [ ] 该用"我们这边"的地方用了
- [ ] 分点的话，每点是完整的口语句子，不是"标题：说明"

## 组装流程

1. **先抓事实**：从会话 / 会议里提炼出——定了哪些事（→ 已确认）、有哪些分歧或待拍板（→ 待对齐，看情况加）、接下来谁做什么（→ 待办）。
2. **过一遍政治分寸**：把 Noah 的私下判断、内情、对人的评价**全部剔除**；分歧改成中性陈述；该抬给 leader 的做成待拍板项。
3. **定基调**：中性纪要还是带产品立场？不确定就给两版让 Noah 选。
4. **按骨架填**：抬头一句 → 已确认 → （待对齐 / 待拍板）→ 待办 → cc。场景三换成「规划和时间线 → 方案里的产品支持 → 会上需要讨论的内容 → 邀约 → cc」，并按场景三的十条规则和反读清单过一遍。场景四换成「数据对基线 → 产品侧动作 → 规划逐项 → cc」，按场景四的六条规则过一遍。场景五换成「开头一句 → 成绩 → 口径和节点 → 指向图加唯一请求」，字只讲图上没有的，按场景五的八条规则过。
5. **套格式规范**：无 emoji、无 ——、无 ；、无 filler、少加粗、编号分节。场景五按它自己的格式例外来。
6. **过一遍去 AI 味**：冒号讲义腔、对仗排比、金句、判词、壳词全扫掉，对着 Noah 自己的消息校口吻。
7. **自检**（见下），确认没内情外泄、没得罪人、忠于事实。
8. 用 message_compose 出稿（kind = other，飞书群消息）。@handle 用占位，提醒 Noah 换成真人。

| 踩雷 | 问题 | 修正 |

| 用表格排结论发飞书群 | 群里表格渲染差、读着乱 | 改编号列表 |

| 编"我们的规划正好能接住对方目标"的连线 | 和真实规划不一致，AI 味重 | 只写已评审 / 在评审的需求本身 |
| 议程段贴"运营侧定 / 会上共同定"标签、写"由谁输出" | 要么显得推责，要么模棱两可 | 一条一件事，责任靠内容分 |
| 结尾"看是否符合预期，有调整我会后更新" | 对方读成"不合预期就改"，带着清单来 | 邀约 + 客气话，或"结论我会后发群里" |
| 把 leader 的"不着急、别为他们改"读成"先不回" | 对方要的时间线和订会没回，显得不接话 | 不着急是不改优先级，诉求当天正面回 |

| 一大团不分点 | Noah："不太好读" | 开头一句，空行，1、2、3，每点一件事 |

## 跨团队议题消息（2026-11-03 加）

场景：工作坊、脑暴会、共创会要在群里发一个让大家讨论的议题（老板也在群里或会看到）。和会议结论、周报不同，它的目的是立题，不是同步进展。

格式（按主办方给的模板，通常是背景 / 目标 / 现状 / 其他）：
1. 第一行：议题一句，用老板当期的词，格式"从 A 到 B，XX 的下一步"。
2. 背景三条：行业趋势一句带两个竞品事实；一个判断句讲角色或竞争的变化；自家产品的位置句加势能数据（上线日期、增长率）。
3. 目标一句：用户视角，三个动词。
4. 现状两条：只写事实，已有规划只写名字加"已在推进，现场不展开"。
5. 带到现场讨论三题：开放问题，排成一条线（入口 → 链路 → 动机），题首可加老板的词当标签。
6. 收尾一句："大家有补充随时提，我汇总后提交。"

规矩：
- 不写绝对值小的数（日均个位数的评论），不写"空白""求助""资源""帮忙"。
- 不写"小组能带来什么"，也不写两个同事之间有分歧的题。
- 会前沟通里只有事实和输入进文档，别人的脑暴结论留在会上。
- 过人顺序：同组产品和运营先聊，leader 过目（通常改两轮：第一轮格局和词，第二轮姿态），再按业务方流程走（Kay 看，Kay 转 Bob，再提交）。

| 踩雷 | 为什么 | 修正 |
|---|---|---|
| 议题里写"真人帖第一条回应从哪来""各方有什么资源" | 主产品在公开场合求助，人设变了 | 换成"怎么在 MEXC 里传开""什么能让交易者长期经营自己" |
| 为避开别人项目的名字，把老板的词全换成同义词 | 老板找不到他的词 | 留词，用"关键载体"守归属 |
| 把还没设计的方案当议题 | 等于请别人帮你画 | 议题选规划没覆盖的层 |
