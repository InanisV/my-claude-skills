# 项目群同步消息 Skill

## 这是什么，先分清和 ego-messenger 的边界

同步消息不是"写给谁看"，是**给一整个团队立一份共识记录**。它会被跨职能同事、可能还有 leader 一起看到，事后还会被翻出来当依据。所以它的基调和 ego-messenger 完全相反：

- **ego-messenger**：1v1 经营关系，暖、带飞书表情、有敬称、目的是让 E 哥心情好 + 觉得你靠谱。
- **group-sync（本 skill）**：面向全群，**中性、克制、像会议纪要**，目的是把"定了什么 + 接下来谁做什么"钉清楚，顺带把该拍的板抬上去。

判断用哪个：这条消息是**给团队留记录 / 立共识**（用本 skill），还是**在向老板汇报或说服他拍某个方案**（用 ego-messenger）。如果一条消息两个目的都有，主受众是全群就用本 skill，主受众是 E 哥就用 ego-messenger。

---

## 核心原则

1. **结论先行，两块为主：已确认 + 待办**。别人扫一眼就知道定了啥、自己要做啥。中间视情况加一块"待对齐 / 待拍板"。
2. **群里有 leader 和跨团队，政治分寸是第一位的**。不评价人、不甩内情、把分歧中性化、把该拍的板抬给该拍的人。这一条最容易翻车，单开一节讲。
3. **忠于会上和事实**。会上没定的别写成已定，自己额外加的项要么标出来、要么先问 Noah。
4. **可扫读，不写墙**。编号分节，一条一句，别堆长段。

## 消息结构

### 标配骨架（大多数同步就这三段）

```
[抬头一句：今天和谁对齐了什么，同步结论和待办。]

一、已确认
1. ……
2. ……

二、待办
1. ……
2. ……

cc @相关人 @leader
```

### 可选中段：待对齐 / 待拍板

有**分歧**或**需要别人拍板**的事，才加这一块，放在"已确认"和"待办"之间。没有就不加，别硬凑。

```
二、待对齐 / 待拍板
1. [分歧点]：[A 方观点]，[B 方观点]，[下一步怎么收敛]。
2. [需拍板项]：[要定什么]，[谁来定]。
```

### 各块怎么写

- **已确认**：编号。每条是一件**已经定了的事**，一句话说清，别展开论证（论证是会上的事，纪要只记结论）。
- **待办**：编号，**动词开头**（确定 / 梳理 / 罗列 / 输出 / 评估），简洁。要不要写负责人看场合：需要问责、认领的写`（负责人）`；纯轻量同步可以不写，让它简洁。
- **待对齐 / 待拍板**：**中性陈述双方**，不站队、不开撕。把"需要谁拍板"点出来。

---

## 政治分寸（重灾区，群里有 leader）

这是本 skill 最容易翻车、也最值钱的部分。同步消息是**公开记录**，一句话说重了，得罪的是整个协作方，还会被 leader 记在账上。

### 五条铁律

**1. 不评价人、不甩内情**

Noah 私下的判断（比如"开发信不过自己的 AI、不想担责"、"某团队在推诿"），**绝对不进消息**。群里一放，就成了当众杠人，对 Noah 只有坏处。

| 私下能说 | 群里怎么写 |
|---|---|
| ❌ "开发信不过自己的 AI，想甩锅才要人审" | ✅ "审核采用 AI 加人审兜底。当前 AI 审核准确率大概在 60% 到 70%，前期保留人审。" |
| ❌ "我们巡检 agent 人力不够只能求人" | ✅ "这块正好在找现成能力，不想重复造。" |
| ❌ "市场部根本没把广场当回事" | 不写。只记客观进展和待办。 |

**2. 分歧中性化，别在群里论输赢**

有分歧时，用一句话把双方立场摆平，写清"下一步怎么收敛"，不在消息里替谁定输赢。

- ✅ "巡检 agent 还有分歧。开发建议在审核环节一并处理、当前人力不足；产品认为有独立价值，先找其他团队看有没有现成能力可复用，再定。"
- 如果不想在群里显得和开发顶，甚至可以把分歧**压成一句话带过**："agent 团队新增一个审核 agent。巡检 agent 还有分歧，产品这边再评估。"

**3. 决策抬上去，靠"成本显性化"而不是靠吵**

想让 leader / 相关方拍板某件事，别在群里论证"这事该归谁"，而是把它**列成待拍板项 / 待办**，把资源和责任明明白白摆出来。成本一旦显性化，该掂量的人自然会掂量，不用 Noah 点破。需要谁拍就 **@ 谁**，姿态克制、留余地。

- ✅ "其中审核人力来源和业务后端归属这两块需要尽快定责任方，辛苦 @Ealy 帮忙拍一下。"

**4. 立场要不要亮：两种基调，让 Noah 选**

同一份纪要，两种写法，对应不同意图。写之前先判断 / 先问 Noah 想要哪种：

| 基调 | 什么时候用 | 怎么写 |
|---|---|---|
| **中性纪要** | 不想在群里和谁顶、或分歧还没到摊牌的时候 | 六点都落成结论 / 待对齐 / 待办，不替产品表态，把分歧放"待对齐"里让它自己说话 |
| **带产品立场** | 想把产品的判断和该拍的板钉进记录里 | 同样骨架，但在分歧点上把产品倾向讲出来（讲价值、讲成本，**不评价对方**），结尾点名 leader 拍板 |

亮立场时也要**克制**：只讲"为什么这样对两边都好 / 成本在哪"，绝不评价对方的动机或能力。

**5. 忠于事实**

会上没讨论的项，不要偷偷塞进"已确认"。如果 Noah 需要补一个会上没提但确实该做的待办（比如某个前置清单），**标出来是新增的、或者先问一句**，别让纪要失真。

## 语言与格式（Noah 硬规范）

同步消息的输出严格守这些，和 Noah 所有对外文字一致：

- **不用 emoji**。这是记录不是 1v1 寒暄，表情会显得不严肃。（这点和 ego-messenger 相反，别搞混。）
- **完整句子 + 完整标点**。不用空格切碎成短片段。
- **不用破折号「——」当分隔符**，不用正文分号「；」，该断就用逗号句号。
- **不用 filler**：赋能、综上所述、确保、旨在、值得注意。
- **极少加粗**，最多标数字或关键结论，不堆叠。
- **编号分节**（一、二、三 + 1. 2. 3.）。**群里用编号列表，不用表格**（飞书 / lark 聊天里表格渲染差，纪要用列表更稳）。
- **数字用 KMBT**，百分比直接写（如 60% 到 70%，不写 60–70% 那种容易和破折号混的）。
- **末尾 cc @相关人**，涉及要拍板的再 @ 上 leader。

---

## 组装流程

1. **先抓事实**：从会话 / 会议里提炼出——定了哪些事（→ 已确认）、有哪些分歧或待拍板（→ 待对齐，看情况加）、接下来谁做什么（→ 待办）。
2. **过一遍政治分寸**：把 Noah 的私下判断、内情、对人的评价**全部剔除**；分歧改成中性陈述；该抬给 leader 的做成待拍板项。
3. **定基调**：中性纪要还是带产品立场？不确定就给两版让 Noah 选。
4. **按骨架填**：抬头一句 → 已确认 → （待对齐 / 待拍板）→ 待办 → cc。
5. **套格式规范**：无 emoji、无 ——、无 ；、无 filler、少加粗、编号分节。
6. **自检**（见下），确认没内情外泄、没得罪人、忠于事实。
7. 用 message_compose 出稿（kind = other，飞书群消息）。@handle 用占位，提醒 Noah 换成真人。

## 示例：广场 agent 方案对齐（会后同步到开发群，E 哥在群里）

**中性纪要版**

```
今天和 agent 开发团队又对了一遍实时交易广场的 agent 方案，同步结论和待办。

一、已确认
1. 审核采用 AI 审核加人审兜底。当前 AI 审核准确率大概在 60% 到 70%，前期保留人审。
2. 上线在小范围放量的基础上再限语言，前期只做中文和英文，跑稳之后再扩。
3. agent 范围复用现有的内容产生 agent 和用户行为 agent，agent 团队新增一个审核 agent。巡检 agent 还有分歧，产品这边再评估。
4. agent 团队只对外提供 agent 能力，不直接提供面向 C 端的接口，需要一个面向 C 端的业务后端来调用能力、对接前端。

二、待办
1. 确定人审兜底的团队和人审方案。
2. 罗列 C 端功能点。
3. 确定面向 C 端用户的业务后端。
4. 确定发帖的数据来源，现在是推文，扩展其他站内数据来源，确定内容及提供方。

cc @Ealy @相关同事
```

**带产品立场版**（把两个要拍板的事点名抬给 E 哥）

在"二、待办"之后加一句收尾：

```
其中审核人力来源和业务后端归属这两块需要尽快定责任方，辛苦 @Ealy 帮忙拍一下。
```

两版的差别只在**要不要把产品立场和该拍的板显性化**，骨架、事实、措辞的中性都一样。

## 写完后自检清单

**政治层（最重要）**
- [ ] 有没有 Noah 的私下判断 / 对人或团队的评价漏进去了？（如"信不过自己""推诿""缺人"）→ 删。
- [ ] 分歧是不是中性陈述、没在群里替谁定输赢？
- [ ] 该抬给 leader 拍板的，是不是做成了待拍板项 + @ 到人，而不是在群里论证？
- [ ] 如果别的同事 / leader 看到这条，会不会觉得 Noah 在杠某个团队？

**事实层**
- [ ] "已确认"里的每一条，会上是不是真的定了？
- [ ] 额外加的待办，标出来 / 问过 Noah 了吗？

**格式层**
- [ ] 结论先行，已确认 + 待办两块清楚？
- [ ] 无 emoji、无 ——、无 ；、无 filler、少加粗？
- [ ] 编号分节、没用表格、没堆长段？
- [ ] 末尾 cc 了相关人，要拍板的 @ 了 leader？
- [ ] 待办动词开头、够简洁？

## 常见踩雷 & 修正

| 踩雷 | 问题 | 修正 |
|---|---|---|
| 把"开发信不过 AI、想甩责"写进群 | 当众杠人，得罪协作方 + leader 记账 | 只记客观结论"AI 加人审兜底，准确率 60-70%"，动机烂在肚子里 |
| 在群里长篇论证"巡检该归谁做" | 像在公开吵架 | 压成一句中性分歧 + "产品再评估"，或做成待对齐项 |
| 想让 E 哥拍板却只在正文暗示 | 板悬着，最后压回 Noah 身上 | 列成待拍板项，点名 @Ealy，把成本摆出来 |
| "确保""赋能""综上所述" | AI 感 + Noah 明令禁用 | 删，用大白话 |
| 用 emoji / 飞书表情 | 这是纪要不是 1v1，显得不严肃 | 去掉，中性到底 |
| 用表格排结论发飞书群 | 群里表格渲染差、读着乱 | 改编号列表 |
