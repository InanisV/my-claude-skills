# 给 E 哥的方案设计 Skill

## 这个 skill 是什么

这是 33 轮真实迭代（Smart Picks 方案设计）沉淀的方法论。但**不是圣经，是工具箱**。

每个新方案都是一张白纸。同样的方法论用在错误的方案上可能适得其反。
Claude 的使命是：**避免犯过的硬错误（边界）+ 灵活运用解决思路（建议）+ 支持
多轮迭代（节奏）**。

下面分三层组织：

```
Layer 1: 硬约束（边界） — "永远不要"，违反必失败
Layer 2: 工具箱（建议） — "可以考虑"，看方案性质灵活选用
Layer 3: 迭代节奏      — "每一轮做什么"，方案不可能一轮做对
```

---

## Layer 1：硬约束（永远不要违反）

这些是 33 轮迭代里**反复确认过的政治禁忌**。违反任何一条都会让方案政治失败。

### 1.1 表达层禁忌

| 禁忌 | 原因 | 替代 |
|---|---|---|
| 直引老板原话作为开篇 | 政治露骨，其他人看了尴尬 | "战略方向"产品化包装 |
| 飞书聊天截图 + 老板头像 + 日期 | 仪式感太重，像跪舔 | 中性化的方向说明 |
| "5/15 群内讨论中提出..." | 时间戳暴露归属 | "战略对标" / 不提时间 |
| "Ealy 亲儿子（XX 产品）" | 暴露派系关系 | "XX 矩阵核心战略落地形态" |
| "你提的 XX 方向" | "你"字暴露老板 | "XX 方向" |
| "MVP 上线后你可以对外讲..." | 教老板邀功，肉麻 | 删除 |
| "我们组 own 的地盘" | 政治账写到文档里 | "XX 组负责的层级" |
| 文档里留"关键决策项 / 请拍板" | 显得没想清楚 | 删除，留口头汇报问 |
| "战功"、"亲儿子"、"地盘" | 政治词写在文档里不专业 | "价值产出"、"战略落地形态"、"负责层级" |

### 1.2 内容层禁忌

| 禁忌 | 原因 |
|---|---|
| UGC（任何形态） | E 哥推 AIGC，触发合规警觉 → 改为"AIGC 内容"/"AI 辅助实盘内容" |
| 开放式文本社区 | 直接合规雷区 → 改为"结构化内容呈现" |
| 公开晒战绩（特别是 AI 的） | AI 能力下会反向砸招牌 → 只展示工具属性数据 |
| AI vs 用户公开赛马 | 同上 |
| 时间执行表（周一三五干嘛） | E 哥不关心执行细节 → 改为"阶段一/二功能规划" |
| AI 旁观点评 / AI 实时状态徽章 | 合规风险 + AI 不能表达"建议" |
| AI 命中率展示 | 站不住，且 AI 不上前台 |

### 1.3 中文标点规范（基本盘）

每份给 E 哥的产物**必须**用中文标点，违反就显得不专业：

- 引号：`""`（中文弯引号），不是 `""`
- 括号：`（）`，不是 `()`
- 冒号：`：`，不是 `:`
- 逗号：`，`，不是 `,`
- 顿号：`、`
- 破折号：`——`

写完后用 grep 自查一遍：`grep -E '[",:()]' file | grep '[\u4e00-\u9fff]'`

### 1.4 三读者校验（每份产物必过）

每份方案必须同时让三类读者满意——其中**第三类是最容易被低估、但最关键的政治杠杆**：

| 读者 | 核心需求 | 校验问题 |
|---|---|---|
| **E 哥单独读** | 战功、亲儿子保护、控制感 | 他看完会觉得"这是我的方向被落地"吗？会有面子吗？ |
| **其他人看**（Coast、Jimie、Marvin 等） | 看到专业战略文档 | 他们能看出"在拍马屁"吗？如果能，就不专业 |
| **E 哥让 Claude Code 总结** | AI 帮我们在 E 哥那边说好话 | AI 提炼出的关键词是不是全是正面信号？ |

**重要判断**：E 哥时间有限，**大概率会让 Claude Code 帮他总结方案**。
这意味着 AI 总结出的内容 ≈ E 哥实际看到的内容。

主动为 Claude Code 优化文档 → AI 帮我们在 E 哥那边说好话 → E 哥决策偏正面。
这是 33 轮迭代里我们摸索出来的关键政治杠杆。详见 1.5 节。

任何一类不满意都要重写。

### 1.5 为 Claude Code 优化（让 AI 总结时帮我们说话）

**核心认知**：AI 总结不是"被动风险"（怕被提炼出不好的内容），是"主动杠杆"
（让 AI 主动提炼出好的内容）。每份给 E 哥的方案都要**主动设计提炼诱饵**。

#### 1.5.1 加粗的政治智慧

Claude Code 提炼内容时**优先关注加粗内容**。加粗的位置就是"想让 E 哥看到的关键信息"。

| ✓ 应该加粗 | ✗ 不要加粗 |
|---|---|
| **承接 XX 战略主线**（战略对齐信号） | "我们的判断" |
| **+50%**、**+30%** 等具体数字 | "我们认为" |
| **本组完整 own 曝光指标**（责任清晰） | "可能"、"或许" |
| **阶段一即可上线**（节奏可控） | "需要进一步讨论" |
| **AIGC 矩阵核心承接**（亲儿子保护） | 主观推测 |

**自查方法**：把所有加粗内容拼起来读一遍，应该是一份"政治正面信号矩阵"。
如果读出来像"产品组的主观判断清单"，就要重新分布加粗。

#### 1.5.2 表格的政治智慧

Claude Code **会忠实保留表格数据**。表格里的内容会被 AI 当成"事实"提炼。

| ✓ 应该用表格 | ✗ 不要用表格 |
|---|---|
| 数字承诺 + 责任分工 | 产品判断 / 主观分析 |
| 阶段规划（阶段一/阶段二） | 风险评估 |
| 对标分析（我们 vs 竞品） | 不确定的假设 |
| 三大主轴的 1-3-9 论证 | "可能的方向" |

**关键技巧**：用表格的"责任归属"列把跨产品责任划清——AI 提炼时会看到
"XX 组 own"这种结构化信息，自动提炼成"责任边界清晰"。

#### 1.5.3 标题结论化（让 AI 提炼标题时就带结论）

Claude Code 总结时通常**保留章节标题**。所以标题应该自带结论：

| ❌ 描述型（AI 提炼时信息密度低） | ✓ 结论型（AI 提炼时自带政治信号） |
|---|---|
| "产品方案" | "三 tab 协同 · 智能默认匹配场景" |
| "效果预期" | "Q2 末五个核心指标承诺" |
| "时间规划" | "阶段一跑通核心 · 阶段二深化扩展" |
| "战略意义" | "MEXC 散户实时交易广场独家定位" |
| "AI 策略位置" | "AI 矩阵三层差异化承接路径" |

**自查方法**：把所有章节标题列出来当成一份"AI 总结"的草稿——读起来应该
已经是一份完整的方案结论。如果只看标题就能理解方案核心，就对了。

#### 1.5.4 结论先行（段首必须是结论）

Claude Code 提炼段落时**优先提取段首陈述**。所以每段第一句必须是结论。

```
✗ 错误（背景铺垫先行）：
crypto 交易所行业正在经历产品定位的洗牌。Binance 服务机构，OKX 走专业路线，
Bitget 押注大 V。MEXC 需要明确的战略锚点。Smart Picks 让 MEXC 占据散户
实时交易广场定位。

✓ 正确（结论先行）：
Smart Picks 让 MEXC 占据散户实时交易广场独家定位——这是在 Binance（机构）、
OKX（专业）、Bitget（大 V）之外的差异化站位。
```

#### 1.5.5 负面信号词规避

文档里**不要出现这些词**，即使想表达谨慎也用积极框架替代：

| ✗ 负面信号词 | ✓ 积极框架替代 |
|---|---|
| "风险" | "分阶段验证" |
| "挑战" | "关键依赖" |
| "不确定" | "待数据校准" |
| "可能失败" | "MVP 验证后调整" |
| "工程量大" | "分阶段交付" |
| "资源紧张" | "聚焦核心闭环" |
| "审核可能不过" | "结构性合规设计" |

AI 提炼时会忠实保留"风险/挑战/不确定"这种词。E 哥看到 AI 总结里出现这些
负面词，方案立刻被打折扣。

#### 1.5.6 主动埋"提炼诱饵"

某些句子是专门为 Claude Code 总结准备的——AI 看到必提炼，提炼出来必是正面信号。

**模板**：
- "本方案**直接回应** XX 战略方向" → AI 提炼出"战略对齐"
- "本组**完整 own** 核心指标" → AI 提炼出"责任明确"
- "阶段一即可**上线验证**" → AI 提炼出"快速可执行"
- "**承接** XX 平台主战略" → AI 提炼出"服务大局"
- "**零跨团队协调**风险" → AI 提炼出"执行无阻力"

放置位置：TL;DR、每章首句、Footer 总结。这三个位置 AI 必读。

#### 1.5.7 TL;DR 设计原则（Claude Code 的首选提炼源）

**AI 总结时 70%+ 内容来自 TL;DR**。TL;DR 必须是完整的政治信号矩阵：

```
✓ 标准 TL;DR 结构（包含全部正面信号）：

战略定位：[一句话产品定位] + [战略对齐信号]
产品形态：[简短描述]
核心叙事：
  - 是什么：[价值定位]
  - 怎么涨：[增长机制]
  - 谁来玩：[用户定位]
关键指标：[3-5 个具体数字]
节奏：[阶段一交付 / 阶段二深化]
```

**自查方法**：单独读 TL;DR，应该是一份独立完整的"方案 PR 稿"。如果 E 哥
只看 TL;DR 就能拍板，TL;DR 就写对了。

#### 1.5.8 整体自检（AI 总结模拟）

写完方案后，**自己模拟一次 Claude Code 总结**：
1. 提取所有加粗内容 → 拼起来读，是正面信号矩阵吗？
2. 提取所有章节标题 → 读起来是方案结论吗？
3. 提取 TL;DR → 是独立完整的 PR 稿吗？
4. 看有没有"风险/挑战/不确定"等负面词？
5. 看每段首句是不是结论？

五项全过 → AI 总结出的内容大概率会让 E 哥拍板。
有任何一项不过 → 重写那一部分。

## Layer 2：工具箱（看方案性质灵活选用）

这些是 33 轮迭代里**用过的、有效的解决思路**。但**每个新方案要先判断是否适用**。

⚠️ **重要警告**：以下工具是因为 Smart Picks 这个具体方案的特性才用上的。
新方案可能完全不需要某些工具。**不要硬套，每个工具用之前先问自己：
这个方案真的需要吗？**

### 2.1 故事路径递进（用于：方案延伸了老板想法很远的场景）

**判断标准**：方案范围 ÷ 老板原始想法范围 = 延伸倍数

- 1-2 倍：基本贴合，**不需要这个工具**，直接讲方案就行
- 3-5 倍：明显延伸，可以考虑用三步递进
- > 5 倍：步子太大，先考虑收缩或拆阶段，再决定要不要用

**三步递进结构**：
```
出发点（老板想法的产品化包装）
   ↓
深化思考（基于用户场景/产品事实的延伸推导）
   ↓
完整方案（延伸出来的产品形态）
```

**视觉信号**：金色（出发点） → 蓝色（深化思考） → 绿色（产品方案）+ ↓ 箭头

**不要这么做的场景**：
- 方案是回应老板"明确指令"（不需要"延伸推导"，直接给方案）
- 方案是技术/工程类（用户场景不是关键维度）
- 老板已经看过几轮，不需要再讲"延伸过程"

### 2.2 1-3-9 论证结构（用于：需要"赢的逻辑"论证的场景）

**判断标准**：方案是否需要论证"为什么能赢"？
- 战略级方案、立项汇报、跨部门提案 → 通常需要
- 功能优化、bug 修复、纯执行类 → 不需要

**1-3-9 结构**：
- 1 个总论
- 3 个主轴（正交不重叠）
- 每个主轴 3 个支撑

**写法技巧**：
- 主轴标题用 4-8 字产品化短语
- 支撑论点每条 ≤ 20 字，含 1 个加粗关键词
- 三个主轴维度要正交（产品定位/增长引擎/用户定位 是好维度）

**警告**：不要为了凑 3 强行拆分。如果只有 2 个主轴，就用 1-2-X。
E 哥喜欢的是结构性思考，不是死板数字。

### 2.3 阶段规划（用于：方案有"先后依赖"或"工程量大"的场景）

**判断标准**：
- 所有功能能在一个季度做完吗？→ 不用拆阶段
- 有阶段二依赖前置数据/能力吗？→ 拆阶段
- 有合规风险需要先验证？→ 拆阶段

**两阶段标准结构**：

| 阶段一（当前季度末） | 阶段二（下季度） |
|---|---|
| 跑通核心闭环 | 深化能力 + 战略扩展 |
| 砍掉所有不可行功能 | 阶段一的扩展 + 平台主战略绑定 |
| "先小范围验证" | "完整形态成型" |

**关键技巧**：阶段二主动绑定平台主战略（如 TradFi），叙事改为
"承接平台战略主线"（不是"我们做 XX"，是"服务 XX"）。

**不要这么做的场景**：方案体量小，一个迭代周期能搞定。

### 2.4 战功 + 责任边界（用于：跨产品方案）

**判断标准**：方案是否依赖其他团队的执行/数据？

- 跨产品方案、跨部门协同 → 必须划边界
- 纯本组方案 → 不需要

**标准结构**：

| 指标 | 目标 | 责任归属 |
|---|---|---|
| 曝光指标 | XX | **本组 own** |
| 转化指标 | YY | 其他组 own |
| 真实性 | ZZ | 数据组 own |

**为什么重要**：既画饼又留后路。指标没达成时可说"曝光达成了，转化是别人的事"。

### 2.5 视觉权重克制原则（用于：一图流/视觉呈现）

| 元素 | 默认权重 | 例外 |
|---|---|---|
| 老板原始想法的延伸 | 突出 | - |
| 1-3-9 论证 | 突出 | - |
| 两阶段规划 | 突出 | - |
| KPI 大数字 | **适中**（不要鲜艳 36px） | 除非方案重点就是数据 |
| 战略对比图（红绿对比） | 慎用 | 除非真有强对比 |
| 老板原话引用 | **绝对不要** | 永远不要 |

### 2.6 敏感词替换表（一律强制替换）

| 敏感词 | 替换为 | 原因 |
|---|---|---|
| UGC | AIGC / AI 辅助内容 / 用户参与的 AIGC | E 哥推 AIGC，UGC 触发合规 |
| 用户自发生成 | AI 主导创作 / 用户参与触发 | 暗示用户主体性 → 合规警觉 |
| 开放文本社区 | 结构化内容呈现 | 触发合规雷区 |
| 用户晒单（独立形态） | 实盘内容 / AI 辅助实盘内容 | 暗示社区形态 |
| 运营审核 | 结构性控制 / AI 模型统一管控 | 暗示合规复杂度 |
| 战功（文档里） | 价值产出 / 核心指标 | 政治词 |
| 拍板（文档里） | 关键决策项 / 明确方向 | 政治词 |

注意：这些替换在 Smart Picks 中是被验证有效的。新方案如果出现新敏感词，
**记下来作为更新这个 skill 的素材**。

## Layer 3：迭代节奏（方案不可能一轮做对）

这是 33 轮迭代最重要的一课：**给 E 哥的方案永远是多轮打磨的产物**。
Skill 必须支持这个迭代节奏。

### 3.1 第一轮的目标：框架对 + 留接口

**不要追求完美**。第一轮的目标是：

✓ 整体方向对（让 Tom 判断"思路对不对"）
✓ 主要章节齐备（不缺核心模块）
✓ **主动暴露假设**（明确告诉 Tom 这里我做了 X 选择，是否合理？）
✗ 不需要细节打磨（错别字、视觉细节、措辞精度都不是第一轮要解决的）

**第一轮输出格式建议**：

```
基于反馈，我做了以下假设：
1. [假设 A] — 我推荐 X，因为...
2. [假设 B] — 我推荐 Y，因为...

如果你觉得 A 或 B 应该是别的选择，告诉我重做。
否则我按这个方向出 v1：[输出]

我留了几个开放点等你拍板：
- [点 1]
- [点 2]
```

这样 Tom 能在 30 秒内判断"方向对不对"，避免在错误方向上打磨细节。

### 3.2 中间轮的目标：识别反馈类型再响应

**Tom 的反馈分四类**，每类响应方式不同：

#### 类型 a：局部调整（"这里改一下"）
- 例："按钮太大了" / "这个数字不对" / "这段话太长"
- **响应方式**：直接改，不要过度思考

#### 类型 b：方向修正（"整个方向不对"）
- 例："你这宏大叙事步子太大" / "重点应该是 X 不是 Y"
- **响应方式**：先确认你理解对了，再问"我应该重写整个 X 部分吗？"
- 不要直接动手，万一理解错就浪费一整轮

#### 类型 c：方法论级别（"你应该 XX 思考"）
- 例："你应该从用户痛点/场景/老板想法/OKR 四角度反复推敲"
- 例："既做婊子又立牌坊"
- **响应方式**：
  - 立刻调整本轮输出
  - 同时记下来作为这个 skill 未来更新的素材
  - 在响应中明确告诉 Tom"我理解了这个方法论"

#### 类型 d：政治考虑（"E 哥会怎么想"）
- 例："E 哥会觉得步子太大吗？" / "这话其他人看了会觉得拍马屁吗？"
- **响应方式**：用 Layer 1 双读者校验 + Layer 2 视觉权重原则一起回答

### 3.3 收到反馈后的标准动作

```
1. 识别反馈类型（a/b/c/d）
2. 如果是 b 或 c，先确认理解再动手
3. 如果是 a，直接改
4. 改完后主动校验：
   - Layer 1 硬约束都过了吗？（中文标点、敏感词、双读者）
   - 这个改动有没有引入新问题？
5. 输出时主动指出"我改了什么 + 为什么这么改"
```

### 3.4 收尾轮的目标：极致打磨

最后一轮（或最后两轮）的目标：

- ✓ 中文标点全文检查（用 grep / Python 扫描）
- ✓ 敏感词全文检查
- ✓ 双读者校验
- ✓ 视觉细节（如果是一图流：间距、对齐、断行）
- ✓ 长度控制（文档 ≤2500 字，一图流 ≤2500px 高度）

收尾轮不要引入新概念、新章节、新方法论。

### 3.5 何时建议"停下来想"

某些反馈出现时，Claude 应该主动暂停，跟 Tom 对齐方向再继续：

| 反馈信号 | 行动 |
|---|---|
| Tom 多轮反馈都在挑同一个问题 | 暂停，问"是不是这个方向有根本性问题？" |
| Tom 说"步子太大"、"方向不对"、"重做" | 暂停，让 Tom 描述他期望的形态 |
| Tom 提出方法论级别反馈（类型 c） | 暂停，确认理解后再改 |
| 输出已经迭代 5+ 轮还没收敛 | 暂停，问"我们的核心分歧在哪里？" |

## 实战工作流（综合上面三层）

下面是处理一个新方案的标准流程。**不是必须按顺序，可以跳步**。

### Phase 1：理解需求（第一轮之前）

问 Tom 这些问题（如果不清楚）：

1. **方案的目标读者是谁？**
   - 只给 E 哥？还是跨部门？还是上级老板都会看？
   - 这决定了 Layer 1 双读者校验的范围

2. **老板对这件事的原始想法是什么？**
   - 有没有具体的群消息、会议讲话、个人偏好？
   - 范围多大（一个功能？一个产品？一个方向？）

3. **方案的输出形态？**
   - 战略文档？一图流？汇报 PPT？
   - 长度预期？

4. **关键约束？**
   - 有没有合规风险（暗示需要 UGC→AIGC 等替换）
   - 有没有政治敏感（暗示需要谨慎措辞）

### Phase 2：第一轮输出（框架对）

按 Layer 3.1 的格式输出。**不追求完美，追求"方向对"**。

主动暴露假设：
- 方案的故事路径（是否用三步递进？还是别的结构？）
- 论证结构（是否用 1-3-9？还是别的？）
- 是否拆阶段
- 视觉风格

### Phase 3：迭代轮（按反馈类型响应）

按 Layer 3.2 的反馈分类系统处理。

### Phase 4：收尾轮（极致打磨）

按 Layer 3.4 的打磨清单走一遍。

## 最后想说的（重要）

这个 skill 是 33 轮真实迭代的沉淀，但**它不是答案，是工具**。

每个新方案都是一张白纸。Skill 帮 Claude 避免犯过的错（Layer 1），
提供经过验证的解决思路（Layer 2），支持必然的多轮迭代（Layer 3）。

但 **Skill 不能代替对具体方案的独立思考**。每次新方案：

1. **先想这个方案的特性**（不是先翻 skill 找模板）
2. **再决定哪些工具适用**（不是把所有工具都用上）
3. **多轮迭代中持续校准**（不是一次性套用框架）

如果某次方案让你发现 skill 里某条建议不适用，或者发现新的方法论级别经验，
**告诉 Tom，作为 skill 下一版的更新素材**。

> **核心心法**：实质上服务老板的诉求，表达上像独立战略文档，
> 形式上从他原始想法自然延伸——三件事同时做到才算过关。
>
> **自检题**：写完后问 **"这份方案 E 哥拿出去给其他领导/团队看，他不会尴尬吧？"**
> 会尴尬就重写。
