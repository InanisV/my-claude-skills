# 字段模型与 payload 形状（2026-08 createmeta 实测）

> **实证基线**：本文件的默认值/恒定值都经 **2026-08-27 抽样 7 位产品近 180 天 97 张真卡**逐字段反查，
> 标 ✅ 的是全组通行、标「默认·须确认」的是抽样里各人不一致（原先是作者个人习惯，已降级）。
> 分布数据与抽样卡号见 [04-field-survey.md](04-field-survey.md)。

plan.json 里 `fields` 直接写 Jira REST 原生 payload。形状规则：

| 字段类型 | 形状 | 例 |
|---------|------|----|
| 单选/下拉 | `{"value": "选项文本"}` | `"customfield_16301": {"value": "是"}` |
| 人员 | `{"name": "username"}` | `"assignee": {"name": "noah.zhan"}`（username 用 `user-search` 查，不是显示名） |
| 组件/版本 | `[{"name": "..."}]` | `"components": [{"name": "iOS-公共模块-首页"}]` |
| 史诗链接 | 裸字符串 | `"customfield_10102": "XXX-12345"`（卡号每批问产品，**项目前缀不限于 APP**，见下方 Epic 硬闸）|
| 优先级 | `{"name": "P1+"}` | 允许值 P0/P1+/P1/P2/P3/P4 |
| description | 裸字符串（wiki 标记） | 见下方 description 规范 |

### 是否需要APP端产品介入（cf_17100）按**身份**取值，不是按需求取值

选项名自带答案：「（业务产品选填）」和「（APP产品选填）」说的是**谁在填这张卡**。
2026-08 抽样验证：7 位产品里只有 1 位（APP 产品线）12/12 填「已审核（APP产品选填）」，
其余 6 位业务产品 54/54 填「不需要（业务产品选填）」——**泾渭分明，和需求内容无关**。

- 使用者是 **APP 产品线**本人 → `已审核（APP产品选填）`
- 使用者是**业务产品**（合约/现货/理财/增长/中台…）→ `不需要（业务产品选填）`；
  确实要拉 APP 产品评审这个需求 → `需要（业务产品选填）`
- **首跑问一次**「你是 APP 产品线的，还是业务产品？」，答复用
  `python3 scripts/jira_cards.py config-set product_role app|business` 写入，之后
  `config-show` 读、不再问（工具只合并这一个键；🔴 **禁止 cat 或直接编辑 `~/.jira-card-kit/`
  下的文件**，见 SKILL.md 顶部「职责分离契约」）。
- 拿不到答复就问，别沿用本文档的举例——**这个字段没有全组默认值**。

> **Noah 2026-08-27 确认**："合理，APP 都默认已审核"——即 **APP 产品线默认「已审核（APP产品选填）」，
> 业务产品默认「不需要（业务产品选填）」**。角色化取值定稿，`product_role` 的实现保持不变。

### ⚠️ 选项值必须与 allowedValues **逐字一致**（含首尾空格）

Jira 按字面文本匹配选项，差一个空格就报 `HTTP 400 {"errors":{"<cf>":"Option id 'null' is not valid"}}`，**apply 停在第一张卡**（好在不会建出半张卡，修完重跑即可）。已实测确认的两个坑：

| 字段 | 看起来是 | 真身（逐字） | 备注 |
|------|---------|-------------|------|
| 是否需要国际化 cf_11531 | `不需要` | `不需要 ` | 尾部 1 个空格。2026-08-24 建 APP-39165/39166 时踩到 |
| 业务板块（受益方）cf_16706 | 某条选项中间只有 1 个空格 | 该条真身是 **2 个连续空格** | 所以受益方**一律从线上拉取结果整条复制**，一个字都别手打（见下方红线） |

其余 APP/WEB 必填项的选项值均已于 2026-08-24 用 editmeta 全量比对，无空格异常。**新增/拿不准的选项值一律先查真身**：

```bash
# 受益方（cf_16706）：直接用执行器实时拉线上选项，含空格异常会打标
python3 scripts/jira_cards.py beneficiary-options APP     # 或 WEB

# 其它字段：读一张同项目同类型的已有卡，拿 allowedValues 原文（repr 能看出空格）
python3 - <<'PY'
import json, sys
sys.path.insert(0, "scripts")
import jira_cards as jc
m = jc.api("GET", "/rest/api/2/issue/APP-38357/editmeta")["fields"]
for a in m["customfield_11531"]["allowedValues"]:
    print(repr(a["value"]))
PY
```

执行器已内置这道软校验：plan 里的值 strip 后能匹配、原样匹配不上时，`validate` 会直接指出「真身首尾有空格 / 你这边多打了」，不用等 apply 报 400。

### 🔴 红线：受益方（customfield_16706）不许想当然

组织纪律（团队 leader 2026-08 全员强调，此前已出现大面积错填）：**谁收益填谁**。这个字段决定人力成本记在哪个团队账上，是**定额消费**——季末会回溯审计"这些人力都花在哪了"，填错等于让别人替你的需求埋单。

**这是本 kit 最硬的一道闸（另一道是下面的 Epic 必问）：必须由使用 kit 的产品本人亲口确认，AI 才能代写。** 产品没明确回答就停下来问，不许自己推断着往下走；`plan.meta.beneficiary_confirmed_by` 和 `beneficiary_rationale` 缺任一项，validate 报 ERROR、apply 建不了卡。这两个字段只能在拿到用户明确答复后填，**不许 AI 自己编一个确认人绕过闸门**。

#### 取值流程（三步，一步都不能省）

**① 实时拉线上选项**——本 kit **不内置任何受益方枚举**（此 skill 全组产品共用，各人受益方不同；任何内置清单都会变成事实上的默认值，诱导错填）：

```bash
python3 scripts/jira_cards.py beneficiary-options APP     # WEB 项目换成 WEB
```

拉取失败（VPN 不通 / 无建单权限）→ **停下，不许猜、不许用记忆里的值**：让用户在 Jira 建单界面打开「业务板块（需求受益方）」下拉，把选项原文**逐字**抄过来（含其中的空格）。`validate` 在拉不到时同样直接报 ERROR，不放行近似值。

**② 结构化强提问，让产品从线上选项里亲选一条**：

- **有结构化提问工具的平台**（Claude Code 的 AskUserQuestion 等）→ 把线上选项列成选项让产品点选；选项多就**按前缀分组分批问**（先问大类：业务线 / 前台 / 中台 / 后台 / 其它，再在该组里列具体条目）。
- **没有该工具的平台** → 把候选清单原样列出来，**以问句收口等答复**，不许自己往下走。
- 问法："这个需求做成后收益归谁？如果是产品自提，有没有业务方愿意为它埋单（没有就只能挂产品线、消耗你自己的定额）？"

**③ 记账**：产品选定后，把选中项**逐字复制**进 `fields.customfield_16706.value`，把确认人写进 `plan.meta.beneficiary_confirmed_by`、把他给的依据（原话浓缩）写进 `beneficiary_rationale`。`validate` 会拿这个值去和**线上选项**逐字比对，并把整段展示在计划表里供复核。

判定顺序：

1. **这个需求做成后，业务价值归谁？** 归某条业务线（合约/现货/理财/钱包/预测市场…）就填那条线。
2. **产品自提的需求**：能说服业务方为它埋单（业务方认可这是他们要的、愿意计入其配额）→ 挂业务方；说服不了 → **只能挂产品线**（线上选项里对应的那条产品线），消耗产品自己的定额。
3. 拆分单/关联卡：**不许直接照抄主卡**。主卡的值只是线索，必须单独向用户确认——真实案例：广场主卡 WEB-18813 填的那条线是错的，正确答案是另一条，照抄就把同一个错误复制了 7 遍（2026-08-13，事后用 `set-beneficiary` 批量纠正）。

禁止事项：

- ❌ 不许用"历史上最常填的值"当默认值（本 kit 曾犯此错——这也是包内不再存任何受益方枚举的原因）
- ❌ 不许从需求名/所属项目/Epic 想当然推断（例：挂在 AI Epic 下 ≠ 受益方就是 AI 线）
- ❌ 不许照抄相似卡而不做判断
- ❌ 不许把线上拉不到当"那就先按这个填"的理由——拉不到就停，让人去界面抄原文
- ✅ 判不准就问用户，并把判定依据写进 `plan.meta.beneficiary_rationale`（validate 会检查；依据会随计划表展示给用户复核）

> 写示例、写文档、写模板时，受益方一律用占位符 `<受益方·从线上选项中经产品确认后逐字填入>`，**不写任何具名示例值**——写下去就会被复制。

### Priority 不是恒定值（2026-08 抽样降级）

原先本 kit 写"恒 P1+"，那是作者一个人的习惯。抽样 7 位产品：

- **APP 故事：P1+ 46 / P0 20** —— 有人整片 P1+，有人整片 P0，多数人两者混用；P0 卡就是普通业务需求，不是线上故障。
- **WEB 故事：P1+ 27/28**（另 1 张 P2）。
- **Jira 自己的默认优先级是 P2，而 97 张真卡里没有一张留在 P2** —— 说明这个字段人人手动设，不能靠系统默认。

处置：plan 里**默认写 P1+**，但计划表必须把它显示出来、**和其它待确认项一起问一句「优先级 P1+ 对吗？（APP 侧 P0 也很常见）」**——并入现有那一轮确认，不新增提问轮次。

### fixVersions：不主动问，默认分端占位

**Noah 2026-08-27 拍板**："不用，没主动说就空的；APP 应该是 iOS/Android 待排期"。落成两条被动规则：

1. **不主动问版本**——提问清单里**没有**"这批排期了吗"这道题（原第 8 题已删）。
   **只有用户主动给了版本号**（"这批进 9 月 22 版本"）才填真实值。
2. **APP 卡默认填占位，且分端各填各的**；**WEB 一张都别填**（createmeta 里 WEB 根本没这个字段，
   抽样 28/28 空，2026-08-27 复核 `/rest/api/2/project/WEB/versions` 返回 0 条）。

占位版本名（**2026-08-27 用 `GET /rest/api/2/project/APP/versions` 实查线上原文**，
APP 共 449 个版本、占位类 3 条，逐字如下——`_` 后面是「待评审」，中间是 ` & `，别手打）：

| 卡 | fixVersions 占位值（逐字） |
|----|---------------------------|
| iOS 故事 | `iOS_待评审 & 待排期` |
| Android 故事 | `安卓_待评审 & 待排期` |
| Flutter 故事 | `Flutter_待评审 & 待排期` |
| WEB/H5 故事 | **不填**（项目没有版本字段）|

占位的含义是"建卡时还没排期"——这在建卡阶段是常态，所以作默认；计划表照常把它列出来让用户能改，
但**不为它单开一问**。抽样佐证：APP 故事真实版本号 39 张 vs 占位 23 张，7 个人都用过真实版本号，
所以占位是默认、不是恒定值。

🔴 `validate` 会拿 fixVersions 的值去 `GET /rest/api/2/project/{项目}/versions` **核对版本是否真实存在**：
不存在或空格对不上 → ERROR（Jira 按版本名字面匹配，写错直接 400 停在这张卡）；已归档 → ERROR；
已发布 → WARN；版本表拉不到 → 只 WARN（这不是成本归属决策，不为一次网络抖动拦住整批）。

### 🔴 硬闸：Epic（史诗链接 customfield_10102）每批必问

**各产品的 Epic 各不相同，本 kit 不写死任何 Epic 卡号。** 出计划表前必须问一次：

> **「这批卡挂哪个 Epic？（给卡号；不挂也可以）」**

- 🔴 **Epic 常常不在本项目里**：2026-08 抽样的 APP 故事，挂了 Epic 的 8 张全部指向**别的项目**（`CONTRACT-` / `SPOT-` / `OPT-` 等业务项目的史诗）。所以**别只认 `APP-` 开头**，用户给什么项目前缀就填什么，`validate` 的卡号格式校验本来就不限项目。
- 🔴 **"不挂"是多数派**：抽样 APP 故事 58/66、WEB 故事 25/28 的史诗链接是空的。用户答"不挂"是完全正常的答复，别追着让他挂一个。
- ✅ 可以把上次用过的值当**候选**展示（配置里的 `last_epic`，`config-show` 读 / `config-set last_epic <卡号>` 写）：「上次挂的是 xxx-xxxxx，这批还挂它吗？」——但**每批都要问、都要拿到明确答复**。
- ❌ 禁止沿用不问；❌ 禁止从主卡/相似卡/历史卡照抄；❌ 禁止从需求名、业务线标签、所属项目推断。
- 用户明确说"这批不挂 Epic" → 留空，`validate` 只出 WARN 不拦。
- `validate` 会拿卡号**去线上 GET 一次**：不存在（404）直接 ERROR、不建卡；类型不是史诗只出 WARN 提示复核；卡名会打进计划表的「Epic 确认」区块给产品对眼。

> **Noah 2026-08-27 确认**（关于"类型不是史诗只 WARN 够不够"）："够的，反正都要产品亲自确认"——
> **校验强度维持现状**：404 拦、类型不符只提醒。真正的闸是"每批必问 + 计划表里拿线上卡名再对一眼"，
> 不靠类型校验兜底。**此项零改动**，不要再收紧成 ERROR。

## WEB/H5 故事（issuetype=故事，project=WEB）

**必填 9 个**：业务板块受益方(cf_16706)、是否需要UI(cf_11530)、是否涉及新页面(cf_15401)、是否需要埋点(cf_16301)，外加 WEB 特有：

| 字段 | id | 允许值 | 默认 |
|------|----|--------|------|
| 需求类别 | customfield_11319 | 业务需求/支撑需求/客服需求/技术需求… | 业务需求 |
| 需求归属端 | customfield_11519 | 前端 / 后端 / 前后端 / 配置变更 | 前端 |
| 是否是合规站 | customfield_17200 | 是 / 否 | 否 |
| 是否涉及运营配置 | customfield_15700 | 是 / 否 | 看 PRD 有无后台配置 |
| 是否需要SEO | customfield_12902 | 无需SEO / 需SEO判断 / 有公开落地页 | 无需SEO |

常填：description=PRD 链接、史诗链接、priority、是否为原生需求（H5 嵌 APP=`该需求是派生需求`）、**assignee=建卡人自己**（抽样 26/28，见上方 assignee 表；用户指定别人就填别人）。组件：首页业务 / 基建 / 性能 ✅（createmeta 复核就这 3 个）。**不填 fixVersions / labels / 安全级别**（WEB 建单界面根本没这几个字段）。UI/国际化/埋点子任务全部自动生成，一个都不建。

WEB 侧默认值的实证（2026-08 抽样 28 张 WEB 故事）：需求归属端=前端 21/28 ✅、是否是合规站=否 25/28 ✅、是否涉及运营配置=否 26/28 ✅、是否需要SEO=无需SEO 26/28 ✅、需求类别=业务需求 27/28 ✅、priority=P1+ 27/28 ✅。**WEB 侧的默认值全部经得起 7 人抽样**，与 APP 侧不同（APP 的 priority / fixVersions / cf_17100 已降级，见上）。
