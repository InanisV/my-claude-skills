# 卡片模型：一个需求建哪几张卡

依据：2025-09~2026-08 近一年作者本人 598 张卡实测（iOS/Android 故事 115/115 严格成对）（2.2.0 起默认 Flutter 单卡，成对结构降为可选，见下），
**并于 2026-08-27 用另外 7 位产品的 97 张真卡反查过拟合**（结论见 [04-field-survey.md](04-field-survey.md)）：
标准包结构、Cloners 方向、子任务挂载都被 7 人抽样坐实；**summary 前缀原为两层【端】【业务线】，
抽样证明那是作者个人写法（94 张真卡 0 张），已按 Noah 2026-08-27 拍板定稿为一层**（见文末 summary 命名节）。

## APP 标准包（默认 · Flutter 单卡，2.2.0 起）

一个 APP 需求 = **1 张故事 + 子任务**，全部由本 kit 创建。原因：2026-12 初 APP 全量上线 Flutter 版本，不再分 iOS / Android 端。

```
【Flutter】需求名      故事（主卡）── 挂 Epic(史诗链接)
                                      description = PRD lark 链接
  └ 子任务挂在 Flutter 故事下：
      【UI设计】需求名   UI设计任务  assignee=设计师（可空·后补）
      【国际化】需求名   国际化任务  assignee=建卡人自己
```

- **没有 Cloners / Relates 链接**——只有一张故事，没有第二张可连。
- fixVersions 占位 `Flutter_待评审 & 待排期`。
- components 用组件表的 Flutter-xxx 列（见 02 组件表）；拿不准留空，留空合法。
- 不需要 UI → 不建 UI设计任务，且故事的 是否需要UI=否；国际化同理。
- 单端需求（如 AB 实验代码下线）只建对应端一张故事，视需要配 UI/国际化子任务。

## 原生双端包（可选 · 切双端判据见 03 §2）

**默认不走这里**——切双端判据见 [03-workflow.md](03-workflow.md) §2 第 3 条。

一个 APP 双端需求 = **4 张卡 + 3 条链接**，全部由本 kit 创建：

```
【iOS】需求名          故事（主卡）─┬─ 挂 Epic(史诗链接)
【Android】需求名      故事         │   description = PRD lark 链接
                                    │
  ├ 子任务挂在 iOS 主卡下：         │
  │   【UI设计】需求名   UI设计任务  assignee=设计师（可空·后补）
  │   【国际化】需求名   国际化任务  assignee=建卡人自己
  │
  └ 链接：
      Android 故事 ─Cloners(clones)→ iOS 故事      （复刻 Jira 界面克隆的效果）
      Android 故事 ─Relates→ UI设计任务
      Android 故事 ─Relates→ 国际化任务
```

- ✅ **Cloners 方向经 7 人抽样强坐实**：26 对双端卡全是 **Android ─clones→ iOS**，0 个反例。方向反了会让克隆关系看起来是 iOS 抄的 Android，别写反。
- Android 故事的字段 = iOS 故事完整复制，仅换：summary 前缀、components（iOS-xxx → 安卓-xxx）、fixVersions（iOS_ → 安卓_）。⚠️ 例外：`双端-基础建设` 这个组件不分端，两张卡填同一个值。
- **子任务挂"主卡"，双端场景下主卡＝iOS 卡**（抽样：UI设计任务 iOS 12 / Flutter 2 / Android 2，国际化任务 iOS 7 / Flutter 3 / Android 2）。单端或 Flutter 需求就挂**那一端自己的故事卡**，不存在"必须挂 iOS"。

## WEB/H5 故事（只建 1 张卡）

WEB 项目的自动化会在建卡后几秒内**按字段答案**自动生成子任务（需要UI=是→UI设计任务；需要埋点=是→埋点四件套；国际化同理；全否的卡一张都不长，2026-08 实测），**kit 只建故事主卡本身**。summary 前缀【H5】或【WEB/H5】或【WEB】。 **设计师怎么挂**：自动生成的【UI设计任务】经办人为空是正常态——分配是项管的工作，kit 不改派；用户问起就 `show <主卡>` 确认它已生成并报卡号，别手建第二张。

## 拆分单场景（把已有大卡拆成模块卡）

研发要分批交付/测试时，会要求把已有故事卡拆成 N 张模块卡（实例：广场1.0 H5 拆 7 卡，2026-08-13）：

- 每模块 1 张故事卡，summary=`【H5】原需求名-模块名`；Epic/优先级/派生需求/组件等字段**跟随主卡实际值**（不是 kit 通用默认）；**受益方是唯一例外——不许跟随主卡，必须独立问用户**（主卡自己就可能填错，见 02 红线的广场案例）；description=主卡的 PRD 链接 +「拆分自 <主卡key>」+ 本卡范围一行
- 每张模块卡 Relates→主卡；不重复补主卡已表达的跨端依赖链接
- **UI设计/国际化不按模块重复建，集中在主卡**（Noah 2026-08-13 裁决）：模块卡填 是否需要UI=否、是否需要国际化=不需要，以抑制自动化生成；再把**主卡的** UI设计/国际化子任务 Relates 到各内容模块卡（纯技术卡如 SDK 不挂）
- 埋点按模块真实情况填（=是会自动长埋点四件套，实现分模块验收，这是拆分的目的之一）
- 若自动化已长出不该有的子任务：每张先评论说明去向再转**废弃**（团队惯例，如 WEB-19135；不删卡）

## Epic（v1.8 起可由 kit 新建）

新专项（`epic-candidates` 零命中、或产品说「新建一张，把这条线的需求都挂上去」）→ plan 里加一张 `issuetype: "Epic"` 的卡**排在最前**，故事用 `epic_ref` 指向它，apply 建完 Epic 自动回填故事的史诗链接(cf_10102)。Epic 建在哪个项目由产品定（H5 需求的 Epic 常建在 WEB）。

| 项目 | 必填（createmeta 2026-09-16 实测） | 说明 |
|---|---|---|
| APP | `summary`、史诗名称 `customfield_10104` | 史诗名称不给就 = summary |
| WEB | 以上 + 需求类别 `customfield_11319`（默认「业务需求」）+ **预期交付日期 `customfield_11802`（YYYY-MM-DD，= 产品给的上线日期，不许编）** | 少了预期交付日期 validate 直接 ERROR |

Epic 的 summary 是专项名（如 `MEXC 广场`），**不带【端】前缀**、不填受益方、不挂 Epic、不填 fixVersions。**一批只建一张 Epic**；已有 Epic 就填卡号不新建。**Epic 名称与预期交付日期都是产品拍板项**——问一句「Epic 叫什么？（WEB）预期上线日期？」，不推断。

## 跨端大需求（APP + H5 + 后端）

在上面基础上叠加 Blocks 链接表达依赖（from blocks to = from 不完成 to 没法做）：

```
AIL 后端故事 ─Blocks→ Flutter 故事（原生双端时为 iOS/Android 故事） / H5 故事
H5 故事      ─Blocks→ Flutter 故事（原生双端时为 iOS/Android 故事）      （H5 嵌 APP 场景）
```

**APP 协作卡**（APP 侧只是配合改动：入口 / 容器 / 宿主参数，实测 2026-09）：可只建 **1 张 APP 故事**，不拆双端、不带 UI / 国际化子任务，fixVersions 占位：默认 Flutter 一条；原生双端各一条；是否按协作卡建由产品定，计划表里标明「协作卡」。链接：H5 故事 ─Blocks→ APP 协作卡。

**summary 写「支持什么能力」**（如 `【H5】广场支持按币种筛选动态`），不抄 PRD 文档名 / 会议名。

AIL 等项目的**故事卡**不由 kit 创建；但**在这些项目已有的主卡下建子任务可以**（`parent` 给已有卡号，实测 AIL-151 / AIL-154 一次建成）；链接可以连到已有卡 key（`"from": "AIL-140"`）。
多篇 PRD 时 description 用多行链接（总则 + 分端），见 02-field-model 的 description 规范。

## 机器人边界（千万别建、别填）

| 谁 | 自动做什么 | 触发时机 |
|----|-----------|---------|
| `testting` | 建【开发任务_xx】【测试任务_xx】子任务；填 前端工作量/AI提效人天；传 xmind 用例 | 研发接卡后 |
| `PMO` | 填 开发者、测试负责人 | 建卡后约 2 分钟 |
| `autotask` | 填 UI负责人、期望设计完成、排优日期、assignee | 建卡后陆续 |
| 项目自动化 | 埋点=是 → 每张故事下自动建【埋点方案审核任务】+【埋点验收任务】（**经办人不写死在本 kit**，见下方「埋点两件套经办人」）；WEB/XHHD/OPT 还会自动建 UI设计任务+国际化任务 | 建卡后 <15 秒 |
| 设计流程 | 需要UI=是 的卡走到验收阶段会长出**【UI验收任务】** | UI 交付后 |

推论：**故事卡建好后子任务马上"自己长出来"是正常现象**；执行器已把机器人字段列入黑名单，plan 里出现会校验失败。
抽样佐证：7 位产品 66 张 APP 故事下共 240+ 个子任务，其中开发任务/测试任务/子任务/sub bug/UI验收任务**全部**是自动生成的——kit 只需要建 UI设计任务和国际化任务这两种。

### 埋点两件套经办人（读配置，本 kit 不写死人名）

【埋点方案审核任务】【埋点验收任务】由项目自动化生成、经办人按团队约定，**各团队不同，本 kit 不内置任何人名**。要在计划表 / 汇报里点名归属时按这条走：

1. 跑 `python3 scripts/jira_cards.py config-show` 看 `tracking_assignees`（🔴 **按任务类型两键**：`review`=方案审核 / `acceptance`=验收——**iOS/Android 两端共用同一对经办人**，别按端分）。
   🔴 **配置只经工具读写**：`config-show` 读、`config-set` 写，**禁止 `cat`/编辑 `~/.jira-card-kit/` 下的任何文件**（职责分离契约的三重禁令第 ①条，见 SKILL.md 顶部）。
2. **没有该配置（工具说文件不存在，或输出里缺这个键）→ 首跑建埋点卡前问一次**：「你们【埋点方案审核任务】和【埋点验收任务】的经办人分别是谁？（两端共用）」——拿到答复用两条命令写进去，**之后不再问**：

   ```bash
   python3 scripts/jira_cards.py config-set tracking_assignees.review <方案审核经办人 username>
   python3 scripts/jira_cards.py config-set tracking_assignees.acceptance <验收经办人 username>
   ```

   每条只合并那一个键，文件里其它配置原样保留（文件不存在会自动新建）。
3. 用户说"不用管 / 机器人自己会填" → 记为空跳过，同样不再追问。

配置格式见本包 `config.example.json`（里面的写法是给**用户手工填**看的；AI 一律走 `config-set`）：

```json
{
  "tracking_assignees": { "review": "<方案审核经办人 username>", "acceptance": "<验收经办人 username>" }
}
```

> 边界：这两张卡的经办人**仍是机器人管的字段、kit 不代填**（执行器黑名单，见上表）；配置只用于计划表/汇报里说清归属，别据此往 plan.json 里写 assignee。

## summary 命名（房规定稿 · 一层全角【端】前缀）

**房规：`【端】需求名` —— 一层全角【】，需求名与 PRD 标题一致，别自由发挥。**

> **Noah 2026-08-27 拍板**："可以的；APP 特殊，iOS/Android 分开"——即**双端两张卡各带自己的**【iOS】/【Android】，
> 这正是现有双端结构本来的样子。**kit 生成 summary 时恒用一层**，措辞写死，不再留"要不要加业务线"的余地。

2.2.0 起 APP 默认【Flutter】一张卡；切双端判据见 03 §2。

- 端：iOS / Android / Flutter / H5 / WEB/H5 / WEB
- 任务类型（子任务用）：UI设计 / 国际化 / 新页面 / UI视觉
- **业务线不再单独占一层**：要点明业务线就并进需求名（`【iOS】AI快讯弹窗展示优化`），别写成 `【iOS】【AI】…`。

### 为什么定成一层（实证）

2026-08-27 抽样 7 位产品的真卡，前缀形态分布：

| 形态 | APP 故事 | WEB 故事 |
|------|---------|---------|
| 全角【】一层 | 53 | 11 |
| 半角 `[]` 一层 | 11（一位产品整片这么写）| 10 |
| 完全没有前缀 | 2 | **7** |
| **全角两层【端】【业务线】** | **0** | **0** |

**两层是本 kit 作者一个人的写法——94 张真卡里 0 张这么写**；一层全角则是全组最通行的形态（64/94）。
所以房规取一层，不取两层。

### `validate` 的判定（实现见 `scripts/jira_cards.py` 的 `check_summary_prefix`）

| 情况 | 判定 | 为什么 |
|------|------|--------|
| 一层全角`【端】需求名` | 通过 | 房规 |
| **完全没有前缀** | **ERROR** | kit 自产的 summary 必带前缀；缺了＝手改 plan 时丢了，补回去再 validate |
| 两层【】【】 | WARN | 房规已定一层；不拦建卡，提醒把业务线并进需求名 |
| 半角 `[]` | WARN | 真卡里通行（21/94），不拦建卡；建议换成全角 |

用户自己指定的 summary 原样尊重（两层/半角只 WARN、不拦），但 **kit 自己生成时恒用一层全角**。
