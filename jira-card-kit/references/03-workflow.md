# 工作流：从需求到建单

> 🔴 **PRD 不是建卡前置**：写 PRD 与建卡不分先后，**有 PRD 就从 PRD 提取，没有就按 §2 问清楚照样建**——任何情况下都不要求用户"先去写 PRD"。

## 0. 建卡前的状态核查（用户问「建了没 / 漏建了没 / 子任务派了没」）

`find --keyword <需求词> --project <项目>` → `show <KEY>` 看子任务与经办人（UI设计任务经办人为空是正常态，项管分配）→ 主 kit `register.py demand-find --name <关键词>` 看需求收集表的 Jira 列 → 聊天记录只作旁证（配方见主 kit `13 §五`：`contact +search-user --has-chatted` 拿私聊 id、`im +chat-messages-list` 拉窗口本地过滤、结论附原话链接）。结论三选一说清：**已建（卡号）/ 未查到（说明查了哪里）/ 不确定**——查不到 ≠ 没建，让产品确认后再进 §1。

## 1. 从 PRD 提取（有 lark 链接且 lark-cli 可用时）

用 `lark-cli docs +fetch --doc <PRD链接> --as user` 读 PRD（大文档先 `--scope outline` 再按需读节），提取下表；提取不到的进入提问清单：

| 提取目标 | 在 PRD 里找什么 | 映射到 |
|---------|----------------|--------|
| 需求名 | 文档标题（去掉【端】前缀）| summary 需求名部分 |
| 涉及端 | 标题前缀/范围章节（iOS/Android/H5/WEB）| 建卡组合：**APP 默认 Flutter 单卡**（切双端判据见 §2 第 3 条）；H5 / WEB → WEB 故事 |
| 业务线 | 标题前缀（【AI】等）/所属项目 | components 选型（⚠️ **不进 summary 前缀**——房规是一层`【端】需求名`，见 [01-card-model.md](01-card-model.md)）|
| **是否需要UI** 🔎推断 | **=是**：PRD 有 UED 设计稿链接 / 元素表含新增元素 / 需求描述含 **新增页面·弹窗·卡片·入口·组件·视觉改动**；**=否**：仅纯逻辑 / 纯文案修正 / 纯后端 / 纯配置 | cf_11530（+ `meta.inference_notes.ui` 写一句依据）|
| **是否涉及新页面** 🔎推断 | **=是**：需求含全新页面 / 独立新入口页；**=否**：只在已有页面上改 | cf_15401（+ `…inference_notes.new_page`）|
| **是否需要埋点** 🔎推断 | **=是**：`需要UI=是` **或** 新增用户可见的页面/入口/交互（要曝光·点击埋点）；PRD 的 Data Requirements **埋点表非空 → 是**（直接读结论）；PRD 明写「本需求无需埋点」→ 否；**=否**：仅纯后端 / 纯配置 / 纯文案 | cf_16301（+ `…inference_notes.tracking`）|
| **依赖交付情况** 🔎推断 | **=依赖未交付**：PRD 关联方表 / 依赖行有**跨端·跨系统**条目；否则 **无需依赖** | cf_11506 + Blocks 链接（+ `…inference_notes.dependency`）|
| 是否需要国际化 | 有无文案/多语言表 | cf_11531（有文案默认「需要但英文文案暂未校对」，抽样 25:4）|
| 运营配置（WEB）| 有无后台配置章节 | cf_15700 |

🔎 **标推断的四项：自己判，不问人（v1.6.6，产品实测点名）**。产品原话——"**新页面应该要自己判断，埋点只要有新的页面和 UI 改动，默认应该是要的**"。落法：按上表判据推断出值，**再把一句依据写进 `plan.meta.inference_notes`**（键：`ui` / `new_page` / `tracking` / `dependency`），`validate` 会把「值＋依据」渲染成计划表里的**「推断项」区块**（形如 `是否需要埋点=是，依据：新增 AI 机会卡片页面 + 2 个新入口`）让产品扫一眼。**它们是可选项：不新增提问回合、不阻塞建卡**（缺依据只 WARN，不 ERROR）；产品要改直接说，改 plan 重跑 validate。**没有 PRD 时同样推断**——判据里"需求描述"就是他口头说的那段。

🔴 **和主 kit `references/09-tracking-gen.md` 的「埋点写前先问要不要」不冲突，分工写清楚**：那条管**写 PRD 时**的产品决策（这个需求到底要不要做埋点，别默认就生成埋点表）；本条管**建卡时**把已定的结论填进字段——**有 PRD 就读 PRD 的结论**（埋点表非空=是、明写「本需求无需埋点」=否），**没 PRD 才按页面/UI 改动推断**。一个是"决定要不要做"，一个是"把已定的结论落进卡"，谁也没替产品做决策。

⚠️ **受益方（cf_16706）与 Epic（cf_10102）都不在提取表里，是刻意的**——一个是成本归属决策、一个是产品每批自己定的挂载位置，都**不是文档事实**，也**不在上面那四个 🔎推断项之列**：禁止从 PRD 的项目名/Epic/业务线标签推断受益方；Epic 也**禁止静默填**（没问就填、照抄主卡、沿用上次不问）。两者都必须走下面的提问流程由用户确认。⚠️ 两者有一处区别：Epic 允许**先捞候选再问**（`epic-candidates`，候选来自**与本需求相关的**历史需求卡与主卡），受益方连候选都不给——它没有「关联卡挂了啥」这种线索，只有产品自己知道。

## 2. 一次性提问（提问纪律）

原则：**一轮问完、每题带默认值、能查的不问、能推断的不问**。**一轮问完 ≠ 揉成一团**：阻塞两问一块、登记三项一块、审批类另起一句，正文别把混合问卷叫「这三个」。

🔴 **阻塞项只有两项**：受益方确认、Epic 确认（下面 1、2 题）——只有这两件必须产品拍板才能建卡；端范围是第 3 条的默认项，不问。⚠️ 其中受益方和 Epic **没有默认值、每批必问**，不适用"带默认值"，也不适用"能推断的不问"。

**两项怎么问**：受益方**按卡确认**（同批里 H5 卡与 APP 协作卡的受益方可能不同，别一个答案套全批）；Epic **按批**。**选项多时的呈现**：受益方线上选项常有 30+，别塞进一个问卷——正文列「编号 | 选项」表让产品回编号；同一形态最多重发一次，第二次换形态。

🔴 **不再作为问题出现的（v1.6.6 起）**：**是否需要UI / 是否涉及新页面 / 是否需要埋点 / 依赖交付情况**——按 §1 提取表的判据**自己推断**，值和一句依据写进 `plan.meta.inference_notes`，跟着计划表的「推断项」区块一起摆给产品扫一眼（**默认展示、不单独问**）。原先第 7 题「有没有要连的已有卡？依赖方向？」也随之降级：**依赖交付情况自己判**，只有当产品手里确实有要连的卡号时才顺口收一下（可选、非阻塞，见下面第 7 题）。

典型问题集（按需删减）：

1. 🔴 **受益方（硬闸：产品本人亲口确认，AI 不得代为判断）**：**先拉线上选项**（`python3 scripts/jira_cards.py beneficiary-options APP|WEB`——kit 不内置枚举，各人受益方不同），**再把选项摆出来让产品亲选**：有结构化提问工具（Claude Code 的 AskUserQuestion 等）就列成选项点选、选项多按前缀分组分批问；没有就列清单并以问句收口等答复。问法："这个需求做成后收益归谁？若是产品自提，有没有业务方愿意埋单（没有就只能挂产品线）"。**禁止给任何建议值/默认值**、禁止照抄主卡（kit 早期两处都犯过：先是把历史高频值当默认，后是推断+照抄主卡，两次都错）。拿到答复后把选中项逐字填进卡、把确认人填进 `plan.meta.beneficiary_confirmed_by` + 依据填进 `beneficiary_rationale`，缺一 validate 就报错。用户没正面回答就再问一次，别自己定。判定规则见 [02-field-model.md](02-field-model.md) 红线节。
   - 🔴 **产品答简称 / 口语时**（「Jackie-直客」「AI-ealy」）：跑 `beneficiary-options <项目> --match "<简称>"`——唯一命中才填；命中多条（实测「Jackie-直客」同时命中 App / Web 两条）→ 把命中项原文列给产品点，**不得按端自选、不得同回合 apply**。
2. 🔴 **Epic（硬闸：每批必问，但先捞**相关**候选再问）**：各产品 Epic 不同，**kit 不写死卡号**。四步：

   **① 先跑 `epic-candidates` 捞候选**（只读）：

   ```bash
   python3 scripts/jira_cards.py epic-candidates --main <主卡卡号> --from <历史需求卡号>,<历史需求卡号> --keyword "<需求关键词>" --project APP
   ```

   - `--main`：**产品给的主需求卡**（不写 `--main` 时，`--from` 的**第一张**当主卡）。
   - `--from`：**背景简报里历史关联需求的 Jira 单号**（会话里跑过 prd-authoring-kit 的背景自采集，就把简报里那一行的单号直接喂进来，见主 kit `references/12-context-recall.md` 的简报第 7 段）。逗号分隔，`--from` 可重复给。
   - `--keyword`：需求关键词 / 模块名，可重复给；配 `--project`（APP 端需求给 `APP`、Web/H5 给 `WEB`），走 JQL 取同族卡最近 10 张。🔴 **别省**——主卡 sanity 的判据就是它。
   - 🔴 **候选来源只有两级，按级排序（v1.6.6）**：**①历史关联需求挂的 Epic**（`--keyword` 同族卡 + `--from` 的历史卡）→ **②主卡挂的 Epic**；同级按关联卡数降序，**已收口（已关闭/已完成/废弃）的标「🔴 已收口，不建议」压到后面**。
   - 🔴 **`last_epic`「上次用的」不再是候选**——产品原话："**epic 就应该参考相关的历史需求的，而不是把历史使用的 epic 一股脑扔上来**"。只有①②全空时工具才提一句"上次用的是「X」，但与本需求查不到关联，**不建议直接沿用**"。
   - 🔴 **主卡 sanity**：主卡卡名与需求关键词**零重合** → 工具打出「主卡「XXX」看起来不是本需求的，**确认卡号？**」，并把**只由它带出来的** Epic 降末位标注。**撞到就回头找产品核卡号**，别拿那个 Epic 往下走（`--from` 混进上一轮别的需求的卡号是实测踩过的坑：不相关的「美股现货需求集」被顶到候选首位）。
   - **零候选** → 工具明说「未找到相关 Epic」，**不编卡号**，直接进 ②。
   - 🔴 **零候选且需求是一条新线 / 产品说「新建一张」 → 走新建**（v1.8 起 kit 能建）：问两样——**Epic 名称**、**（WEB 项目）预期交付日期 = 上线日期**；plan 加一张 Epic 卡排最前、故事用 `epic_ref` 挂它（形态见 `01 §Epic`、样例 `examples/plan-epic-web.json`）；计划表「Epic 确认」区块会显示「新建 Epic「名称」（项目，预期交付 日期）」，产品点头才 apply。一批一张 Epic；已有 Epic 永远填卡号不新建。

   **② 名称化提问，形态跟着候选走**（🔴 **禁止只甩卡号、禁止平铺不相关的**）：

   - **单强候选**（工具打出「单强候选 · 推荐形态」：关联卡 ≥2 张且无同级竞争）→ **别再平铺一堆**，就问：
     **建议挂「<Epic 名称>」(卡号)——<依据>**，**就它** / **换一个**（说名字或卡号都行，我来找）/ **不挂**
   - **多候选** → 才列表：把工具输出里**每条整行原样**当选项文案。
   - 🔴 **选项文本 = 「Epic 名称」(卡号)——依据**，形如：
     `「<Epic 名称>」(APP-xxxxx)——历史需求「<历史需求名>」等 3 张挂它`
     **依据在选项文本里，不许拆去另一列、不许只留名称**——产品判断"这个 Epic 是不是本需求的"靠的就是这半句。
   - 加上固定两条：**换一个**（说名字或卡号都行，我来找）、**本批不挂**。

   有 AskUserQuestion 这类结构化工具就照这个文案列选项；没有的平台在正文列同款文字清单、以问句收口等答复。**「上次挂的是 XXX-1234，还挂它吗？」这种裸卡号问法 v1.6.3 起作废**（产品实测反馈：看不懂卡号、也判断不了对不对）；**把工具已经降级/折叠的候选重新平铺上来，v1.6.6 起同样作废**。

   **③ 产品答名字 → 工具找卡号**：`python3 scripts/jira_cards.py epic-search --name "<产品说的名称片段>"` → 返回 名称|卡号|状态 ≤10 条。**多命中一律列出来让他指一条，不许猜**；命中数大于列出数时提示他把名称说具体些再搜。零命中就请他换更短的片段或直接给卡号。

   **④ 硬闸不变**：每批必确认、**禁止沿用不问**；答复拿到后写进 `fields.customfield_10102`；`validate` 会去线上验这张卡在不在（404 就不给建）。**推荐形态省掉的只是"在一堆不相关候选里挑"，没有产品那句「就它」照样不许填。****Epic 常常挂在别的项目下**（抽样里 APP 卡挂的全是 CONTRACT/SPOT/OPT 等业务项目的史诗），别只认 `APP-` 前缀。**用户说不挂 → 留空，这是多数派答复，别追问。**

   🔴 **口径统一（别再和"禁推断"打架）**：**候选可以来自主卡 / 历史关联需求，但必须产品确认才能填——禁的是"静默填"**（没问就填、照抄主卡、沿用上次不问）**和"不相关也摆上来"**。把**相关**线索摆出来给产品选不是推断，是本步该做的事。
3. 端范围（**不主动问的默认项**，切双端判据唯一出处）：默认 Flutter 一张卡。切原生双端包只有两种情况：① 产品点名「分 iOS / Android 原生建」；② PRD 标题或范围章节**同时明写 iOS 与 Android 两端原生**。PRD 标题只带【iOS】或【Android】一端 → 仍按 Flutter 单卡建，但计划表里露一句「PRD 标题写的是 iOS，已按 Flutter 单卡建；要原生单端请说一声」。默认值照常在计划表里露出来给产品改。
4. UI 设计师是谁？（**可选、非阻塞**：产品顺口给了就用 `user-search` 解析成 username 填上；没给就 **assignee 留空建卡、后补**——七人真卡实证 APP 卡建卡时本就不填经办人。🔴 禁止把它列为"还差的信息"、禁止要求产品"明确回复先不建 UI 设计任务"）
5. **优先级：默认 P1+，但要让用户点头**——抽样 7 位产品的 APP 故事里 P0 占 30%（有人整片 P0），这不是恒定值。问法一句带过：「优先级 P1+ 对吗？（APP 侧 P0 也常见）」
6. 组件模块：有把握才按 02 的 Flutter 列填，拿不准留空（留空合法，抽样半数 APP 故事没填）
7. 有没有要连的已有卡（后端 AIL 卡 / H5 卡）？依赖方向？（**可选、非阻塞**：`依赖交付情况(cf_11506)` 已按 §1 判据自己推断了，这里只收**卡号**用来挂 Blocks 链接；产品手里没有卡号就不挂链接照常建卡，别当成"还差的信息"）

🔴 **版本(fixVersions) 不是一道题——不主动问**（Noah 2026-08-27 拍板："不用，没主动说就空的；APP 应该是 iOS/Android 待排期"）。被动规则：
**用户主动给了版本号才填真实值**，否则 APP 卡占位：默认 Flutter 卡 `Flutter_待评审 & 待排期`；原生双端包时 iOS 卡 `iOS_待评审 & 待排期` / Android 卡 `安卓_待评审 & 待排期`；**WEB 一张都别填**。占位值照常在计划表里露出来给用户改，但别为它单开一问。

**首跑一次性问、之后读 config 不再问**（🔴 **配置的读写只经工具**：`config-show` 读、`config-set <键> <值>` 写，每次只合并那一个键；**禁止 cat 或直接编辑 `~/.jira-card-kit/` 下的文件**，见 SKILL.md 顶部「职责分离契约」）：

- **你是 APP 产品线的，还是业务产品？** → `config-set product_role app|business`。决定 cf_17100「是否需要APP端产品介入」填 `已审核（APP产品选填）` 还是 `不需要（业务产品选填）`——抽样证明这个字段跟需求内容无关、只跟填卡人身份有关（见 02-field-model）。
- 埋点两件套经办人 → `config-set tracking_assignees.review <username>` / `config-set tracking_assignees.acceptance <username>`（见 01-card-model）。

不用问的：国际化任务 assignee = 建卡人自己（`whoami` 拿 name）；**WEB 故事的 assignee 也默认＝建卡人自己**（抽样 26/28，见 02 的 assignee 表）。

## 3. 生成 plan.json → validate → 用户确认

- 文件命名：`plan-<需求名拼音或英文缩写>.json`，放当前目录。
- 卡的顺序：故事在前、子任务在后（执行器要求父卡先建）。
- 🔴 **PRD 链接自动带入**：本会话里**已经有 PRD 链接**——刚用 prd-authoring-kit 发布拿到的、或用户早先贴过的——**直接写进各故事卡的 `description`**（格式按 `02-field-model` 的 description 规范：单篇裸链接、多篇带标题一行一个），**别再让用户贴一遍**；计划表里把它显示出来给用户核对即可。会话里确实没有链接才留空，事后拿到再由用户在 Jira 里补。
- `python3 scripts/jira_cards.py validate plan-xxx.json` 通过后，**把计划表原样贴给用户**，等明确的"确认/建吧/OK"。
- 🔴 **计划表里的三个区块一个都不许省**（validate 会自动打印，原样贴出去）：
  - **「受益方确认」**——值、确认人、依据三行都在，且值来自线上实时选项；
  - **「Epic 确认」**——按**展示纪律**渲染成**「名称」(卡号) · 类型/状态**（卡名从线上读回，不是本地编的），收口一句**「这批卡就挂这个 Epic 吗？（不是就说名字或给卡号，我来找）」**。哪怕本轮提问时已经问过，计划表这里也要让用户再对一眼——挂错 Epic 一眼就能看出来。
  - **「推断项」**（v1.6.6 新增）——**是否需要UI / 是否涉及新页面 / 是否需要埋点 / 依赖交付情况**四项的**推断值 + 各一句依据**（依据来自 `plan.meta.inference_notes`，缺了只 WARN 不拦建卡）。🔴 **它是"摆出来"不是"问出来"**：产品扫一眼，不吭声就按推断走，要改直接说；**别把它变成第四道提问**。
  - 🔴 **链接表同款**：`links` 里指向**已有 Jira 卡**的 from/to（后端 AIL 卡、H5 卡等），`validate` 会去线上读回卡名、同样渲染成「名称」(卡号)；读不回会出 WARN（卡号写错的话 apply 补链接那一步会失败）。**原样贴给用户，别自己缩写回裸卡号。**
- 计划表里还要把这几个**降级过的默认值**显示出来让用户扫一眼（并入同一轮确认，**不新增提问回合**）：**优先级**、**版本(fixVersions)**、**是否需要国际化**（有文案时默认「需要但英文文案暂未校对」）、**组件**。这四个原先是 kit 写死的，2026-08 抽样 7 位产品证明各人不一致，所以改成"默认展示 + 一起确认"。用户不吭声就按默认走，但必须让他看见。
  ⚠️ 版本只是**露出来**、不是**问出来**：提问清单里没有版本这道题（见 §2 末的被动规则），计划表里列出占位值即可，用户要改自然会说。
- `validate` 还会拿 fixVersions 去 `GET /rest/api/2/project/{项目}/versions` 核对版本真实存在（不存在/空格对不上/已归档 → ERROR，已发布 → WARN，拉不到 → WARN）。报错就照它给的线上版本名改，别手打。
- 用户确认后可以顺手记一下本批 Epic：`python3 scripts/jira_cards.py config-set last_epic <卡号>`（工具只合并这一个键，不碰文件里其它配置；**别自己去写那个文件**）。⚠️ **它从 v1.6.6 起不再是候选**：`epic-candidates` 只在**一个相关候选都没捞到**时提一句"上次用的是「X」，但与本需求查不到关联，不建议直接沿用"——既不是默认值、不是首选，也不进候选表。记不记都不影响流程。
- 用户改字段 → 改 plan → 重新 validate → 重新确认。没有确认绝不 apply。

## 4. apply 与异常处理

- `python3 scripts/jira_cards.py apply plan-xxx.json`
- 全部成功 → **先记一行使用采集，再进入汇报**（SKILL.md 流程第 7 步）：按 `../prd-authoring-kit/references/11-usage-telemetry.md` 执行（唯一真源，本 kit 不复制命令文本），**模式列填「建卡」**、需求名按该文件 `§需求名 = 跨技能统一去重键` 取；主 kit 不在（文件读不到）就**静默跳过**。失败静默、不打扰用户、一批只记一行。
- 中途失败：执行器停止建后续卡、保留已建卡（不自动删）。如实告诉用户已建了哪些、失败原因（常见：字段值和允许值不逐字一致、组件名写错、username 不存在）。修 plan 后重跑 apply 自动续传。
- 🔴 **认证失败（HTTP 401/403）是单独一类**：工具会打统一那句「❌ Jira 认证失败…运行 `setup-token` 重新配置」并停下（不管发生在 validate 联网核对、apply 建卡还是补链接的哪一步）。**原样转告用户去更新 token**，或直接跑 `setup-token` 带他重配；**禁止去读 `~/.jira-card-kit/` 下任何文件排查、禁止改用 curl 直连 Jira 试**（SKILL.md 顶部「职责分离契约」三重禁令）。apply 中途撞上它已建的卡照常留在 result 文件里，换好 token 重跑 apply 会自动续传。
- **apply 前会再跑一遍 validate（含联网核对受益方选项与 Epic 卡号）**，任一 ERROR 都直接停在建卡之前、一张卡都不会建。拉不到线上选项/验不了 Epic 时**不许绕过**（没有 offline 开关，这是刻意的）：把网络修好，或让用户去 Jira 界面抄选项原文 / 给准确的 Epic 卡号。
- 需要撤销：让用户在 Jira 界面删卡（kit 无删卡能力，这是刻意设计）。

## 5. 汇报格式（可直接贴群）

> 🔴 **贴群之前先把那一行使用采集记掉**（SKILL.md 流程第 7 步：按 `../prd-authoring-kit/references/11-usage-telemetry.md` 执行、模式填「建卡」、需求名用统一去重键；文件读不到就静默跳过）——采集在**汇报之前**，别等汇报完再补，也别拖到会话最终回复。

```
【需求名】Jira 卡已建：
- APP-xxxxx 【Flutter】需求名（主卡） <Jira 地址>/browse/APP-xxxxx

- APP-xxxxx 【国际化】需求名
链接：无（单卡默认）/ 已挂 Blocks/Relates（原生双端再有 Clone）。开发/测试负责人、埋点子任务等系统会自动补，无需处理。
```

🔴 **展示纪律同样管这里**：汇报里每张卡都带着卡名（模板里的 `【Flutter】需求名` 就是它），**别精简成只剩卡号**；顺带提到的 Epic 和已有关联卡（后端 AIL 卡、H5 卡）也一律写「名称」(卡号)。

汇报后提醒一句：几分钟后可以刷新主卡确认机器人已接管（PMO 填负责人、埋点子任务自动出现）。
